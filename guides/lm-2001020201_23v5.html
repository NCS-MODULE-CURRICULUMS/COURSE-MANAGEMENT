11-1. 현행 시스템 파악

개발하고자 하는 응용소프트웨어에 대한 이해를 높이기 위해, 현행 시스템의 적용 현황을 파악함으로써 개발 범위와 향후 개발될 시스템으로의 이행 방향성을 분석할 수 있다.

이 꼭지를 마치면

  • 개발하고자 하는 응용소프트웨어에 대한 이해를 높이기 위해, 현행 시스템의 적용 현황을 파악함으로써 개발 범위와 향후 개발될 시스템으로의 이행 방향성을 분석할 수 있다.

왜 하는가

새 시스템을 만들라는 일을 받으면 곧장 화면부터 그리고 싶어집니다. 하지만 세상에 아무것도 없는 자리에 짓는 시스템은 거의 없습니다. 대부분은 이미 돌아가고 있는 것 옆에, 또는 그것을 대신해서 만듭니다.

그래서 첫 일은 지금 무엇이 어떻게 돌아가고 있는지 알아내는 것입니다. 어떤 시스템들이 있고, 무슨 기능을 하고, 서로 어떤 자료를 주고받고, 어떤 소프트웨어·하드웨어·네트워크 위에서 도는지. 이것을 «현행 시스템 파악» 이라고 합니다.

이것을 건너뛰면 나중에 «그 기능 이미 있는데요», «그 서버로는 안 돌아갑니다» 같은 말을 듣게 됩니다. 그때는 이미 늦습니다.

알아야 할 것

현행 시스템 파악의 정의 및 목적
어떤 시스템으로 구성되어 있는지, 시스템이 제공하는 기능이 무엇인지, 어떤 정보를 주고받는지, 어떤 기술을 사용하고 있는지, 사용한 소프트웨어와 하드웨어는 무엇인지, 네트워크는 어떻게 구성되었는지를 파악하는 활동이다. 향후 개발하고자 하는 시스템의 개발 범위 및 이행 방향성을 설정하기 위함이다.

정의 문장이 길어 보이지만 뜯어보면 여섯 가지를 묻는 것입니다. ① 어떤 시스템으로 되어 있나 ② 무슨 기능을 하나 ③ 어떤 정보를 주고받나 ④ 어떤 기술을 쓰나 ⑤ 어떤 소프트웨어·하드웨어를 쓰나 ⑥ 네트워크는 어떻게 되어 있나.

목적은 하나입니다 — 개발 범위와 이행 방향을 정하기 위해서입니다. «어디까지 새로 만들고 어디부터는 그대로 두나», «지금 것을 어떻게 옮기나» 를 정하는 근거가 여기서 나옵니다.

해 보기 여섯 가지 질문으로 표를 만든다
  1. 스프레드시트를 열고 A열에 위 여섯 질문을 한 줄씩 적습니다.
  2. B열은 «조사 방법», C열은 «누구에게 물어보나», D열은 «받을 자료» 로 둡니다.
  3. 본인이 아는 시스템(학교 수강신청, 도서관 대출 등) 하나를 고르고 여섯 줄을 채워 봅니다. 모르면 «모름» 이라고 적으십시오 — 그것도 조사 결과입니다.

tip 이 표가 그대로 다음 단계의 조사 계획서가 됩니다.

현행 시스템 파악 절차
아래와 같이 3단계로 구분하여 수행해야 할 활동들에 관하여 기술한다.

학습모듈은 3단계로 나눕니다. 1단계 구성·기능·인터페이스 파악 → 2단계 아키텍처·소프트웨어 파악 → 3단계 하드웨어·네트워크 파악.

순서에 뜻이 있습니다. 위에서 아래로 내려갑니다. 먼저 «무슨 일을 하는 시스템인가»(업무) 를 보고, 그 다음 «어떤 기술로 만들었나»(소프트웨어), 마지막에 «어디에서 도나»(하드웨어·네트워크) 를 봅니다.

거꾸로 하면 안 됩니다. 서버 사양부터 조사하면 그 숫자가 무슨 뜻인지 알 수 없습니다.

해 보기 3단계를 한 장으로 그린다
  1. draw.io(app.diagrams.net)를 열고 Blank Diagram 을 만듭니다.
  2. 사각형 3개를 세로로 놓고 위에서부터 «구성·기능·인터페이스», «아키텍처·소프트웨어», «하드웨어·네트워크» 라고 적습니다.
  3. 사각형 사이를 화살표로 잇습니다. 오른쪽에 각 단계에서 «만들 산출물» 을 적어 둡니다(구성도·현황표 등).

tip 이 그림을 조사 내내 옆에 두십시오. 지금 어느 단계인지 헷갈리지 않습니다.

현행 시스템 구성 현황
현행 시스템의 구성 현황은 해당 조직 내 처리하는 주요 업무, 즉 기간 업무와 이를 지원하는 지원 업무로 구분해서 기술한 것이다. 각 업무를 지원하는 단위 업무 정보시스템의 주요 기능, 명칭들을 정리함으로써 조직 내 존재하는 모든 정보시스템의 현황을 파악하도록 한다.

«구성 현황» 은 업무 기준으로 시스템을 늘어놓은 것입니다. 기술 기준이 아닙니다.

기간 업무는 그 조직이 먹고사는 일입니다(도서관이면 대출·반납). 지원 업무는 그것을 돕는 일입니다(회계, 인사, 통계). 둘을 나눠 적는 이유는 «건드리면 안 되는 것» 과 «바꿔도 되는 것» 이 갈리기 때문입니다.

해 보기 구성 현황표를 채운다
  1. 스프레드시트에 «구분 / 시스템명 / 기능 / 비고» 네 칸을 만듭니다.
  2. 구분 칸에는 «기간» 또는 «지원» 만 적습니다.
  3. 고른 시스템을 5~8줄로 채웁니다. 한 줄이 시스템 하나입니다.

tip 시스템명을 «관리시스템» 처럼 두루뭉술하게 적지 마십시오. «도서 대출 관리», «열람실 좌석 관리» 처럼 일 단위로 적습니다.

기능 현황
단위 업무 시스템이 현재 제공하고 있는 모든 기능을 기술한 것이다. 단위 업무 시스템에서 제공하는 기능들의 주요 기능과 하부 기능을 구분하여 계층 형으로 표시한다.

구성 현황이 «어떤 시스템이 있나» 라면, 기능 현황은 «그 시스템이 무엇을 하나» 입니다. 한 단계 더 들어갑니다.

여기서 중요한 것은 단위 업무 기준으로 쪼개는 것입니다. «대출 관리» 를 «대출», «반납», «연장», «예약» 으로 쪼개야 «연장 기능이 없네» 같은 것이 보입니다.

해 보기 기능을 두 단계로 쪼갠다
  1. 앞 표의 시스템 하나를 고릅니다.
  2. 그 아래에 기능을 3~6개 적고, 기능마다 «누가 쓰나» 를 옆에 적습니다.
  3. 기능 이름은 반드시 동사로 끝냅니다 — «대출하기», «연장하기».

tip 이 목록이 나중에 유스케이스 후보가 됩니다. 버리지 말고 두십시오.

인터페이스 현황
단위 업무 시스템이 다른 단위 업무 시스템과 주고받는 데이터의 종류, 데이터 형식, 프로토콜, 연계 유형, 주기 등을 명시한 것이다. 인터페이스 현황 작성 시 고려 사항으로는 어떤 형식으로 데이터를 주고받는지, 어떤 통신규약 사용하고 있고, 연계 유형은 무엇인지 등이 있다.

인터페이스는 시스템끼리 자료를 주고받는 통로입니다. «무엇을, 어떤 형식으로, 어떤 방법으로, 얼마나 자주, 어떤 프로토콜로» 를 적습니다.

이 다섯 가지를 다 적어야 하는 이유는, 하나만 빠져도 «연동이 안 된다» 는 말이 나오기 때문입니다. 형식은 맞는데 주기가 안 맞거나, 프로토콜은 맞는데 암호화 여부가 다른 일이 실제로 자주 생깁니다.

해 보기 인터페이스 현황표를 만든다
  1. 위 표의 일곱 칸을 스프레드시트 머리글로 만듭니다.
  2. 고른 시스템이 바깥과 주고받는 것을 2~4줄 적습니다. «로그인할 때 학번을 학사시스템에서 받아온다» 같은 것이 한 줄입니다.

현행 시스템 아키텍처 구성도
최상위 수준에서 기간 업무를 수행하기 위하여 계층별로 어떠한 기술 요소들을 사용하고 있는지 그림으로 표현한 것이다. 단위 업무 시스템별로 아키텍처가 다른 경우, 가장 핵심 시스템을 기준으로 한다.

아키텍처 구성도는 계층으로 그린 그림입니다. 위에서 아래로 «사용자 → 화면 → 업무 처리 → 자료 저장» 처럼 층을 나누고, 각 층에 무슨 기술을 쓰는지 적습니다.

이 그림이 있으면 «어디를 바꾸면 어디까지 영향이 가나» 를 눈으로 볼 수 있습니다. 표로는 절대 안 보입니다.

해 보기 draw.io 로 계층 구성도를 그린다
  1. draw.io 에서 Blank Diagram 을 만들고 파일명을 as-is_architecture.drawio 로 저장합니다.
  2. 가로로 긴 사각형 4개를 세로로 쌓습니다. 위에서부터 «사용자», «프레젠테이션», «비즈니스», «데이터» 라고 적습니다.
  3. 각 층 안에 실제 쓰는 것을 작은 사각형으로 넣습니다 — 브라우저 / Spring / MySQL 처럼.
  4. 층 사이를 위아래 화살표로 잇습니다. File → Export as → PNG 로 내보냅니다.

tip 층을 5개 넘게 만들지 마십시오. 읽는 사람이 길을 잃습니다.

소프트웨어 구성도
단위 업무 시스템의 업무 처리를 위해 설치되어 있는 소프트웨어들의 제품명, 용도, 라이선스 적용 방식, 라이선스 수를 명시한 것이다. SW 제품명 라이선스 수 Apache Tomcat Apache License GPL 또는 시스템 구축 시 인프라 구축 비용에서 하드웨어 비용뿐만 아니라 소프트웨어 비용이 크기 때문에, 상용 소프트웨어의 경우에는 보유한 라이선스 수량 파악과 라이선스 적용 방식의 기준(사이트, 서버, 프로세서, 코어(core), 사용자 수 등)이 중요하다.

소프트웨어 구성도에서 가장 자주 빠뜨리는 칸이 라이선스입니다. 제품명과 버전만 적고 «상용인지 오픈 소스인지, 몇 개까지 쓸 수 있는지» 를 안 적습니다.

그런데 예산과 직결되는 칸이 바로 그것입니다. «오라클을 그대로 쓰자» 와 «오픈 소스로 바꾸자» 는 몇 천만 원이 갈리는 결정입니다.

해 보기 소프트웨어 구성 표를 만든다
  1. «구분 / 제품명 / 버전 / 라이선스 / 라이선스 수» 다섯 칸을 만듭니다.
  2. 구분은 OS · DBMS · WAS · 프레임워크 · 기타로 나눕니다.

하드웨어 구성도
단위 업무 시스템들이 어느 서버에서 운용되고 있는지 서버의 주요 사양(CPU 처리 속도, 메모리 크기, 하드디스크의 용량 등)과 수량, 이중화 여부를 명시한 것이다. CPU 4core: Memory: 8GB HDD: 500GB CPU 8core: Memory: 16GB HDD: 1TB 이중화는 기간 업무의 서비스 기간, 장애 대응 정책에 따라 필요성 여부가 결정되며, 현행 시스템에서 이중화가 적용되면 목표시스템에서도 이중화가 필요한 경우가 대부분이며, 이에 따라 인프라 구축 기술 난이도 및 비용 증가 가능성이 존재한다.

하드웨어 구성도에는 이중화 여부를 반드시 적습니다. 서버가 한 대인지 두 대인지에 따라 «한 대가 죽으면 서비스가 멈추나» 가 갈립니다.

사양은 CPU 처리 속도, 메모리 크기, 디스크 용량 세 가지를 적습니다. 이 숫자가 나중에 «시스템 용량 산정»(1-2 꼭지) 의 출발점이 됩니다.

왜 하는가

앞 꼭지에서 «지금 무엇이 돌아가고 있나» 를 조사했습니다. 이 꼭지는 그 조사를 바탕으로 새로 만들 시스템을 무엇 위에 올릴 것인가를 정합니다. 운영체제는 무엇으로, 데이터베이스는 무엇으로, 서버는 몇 대나.

이 결정을 «나중에 정하죠» 하고 미루면 개발이 시작되지 않습니다. DBMS 가 안 정해지면 테이블을 못 만들고, WAS 가 안 정해지면 배포를 못 합니다. 게다가 이 결정은 돈과 직결됩니다. 상용 제품 하나가 수천만 원입니다.

정하는 기준은 취향이 아닙니다. 현행 시스템·예산·인력·성능 네 가지입니다. 그래서 앞 꼭지의 조사 결과가 없으면 이 꼭지를 할 수 없습니다.

개발 기술 환경
개발 기술 환경을 정의할 때 고려할 사항을 운영체제, DBMS, 미들웨어, 오픈 소스 순으로 살펴본다. 본 학습에서는 모든 미들웨어에 대하여 기술하지는 않으며 자주 사용되는 웹 애플리케이션 서버(WAS: Web Application Server)를 선정할 경우 고려해야 할 사항에 대해서 기술하고, 오픈 소스 사용 시 주의해야 할 내용과 저작권 관련 정보를 제시한다.
운영체제 주요 특징 및 고려 사항
운영체제(OS: Operating System)는 하드웨어와 소프트웨어 리소스를 관리하고 컴퓨터 프로그램을 위한 공통 서비스를 제공하는 소프트웨어를 의미한다. 관련 사이트 참고 (https://en.wikipedia.org/wiki/Operating_system) 주요 운영체제로는 마이크로소프트 윈도우(Microsoft Windows), 유닉스(UNIX), 리눅스(Linux), 아이오에스(iOS), 안드로이드(Android) 등이 있다.

고를 수 있는 것은 사실상 셋입니다 — 유닉스 · 리눅스 · 윈도우. 학습모듈이 드는 기준은 «예산 · 기술 인력 · 처리량 · 기술 지원» 입니다.

실무에서는 대개 이렇게 갈립니다. 예산이 넉넉하고 대량 처리가 필요하면 유닉스, 비용을 줄이면서 기술 인력이 있으면 리눅스, 관리 인력을 구하기 쉬워야 하면 윈도우. 요즘 신규 구축은 리눅스가 기본이고, 유닉스는 기존 시스템을 그대로 쓰는 경우가 많습니다.

중요한 것은 «리눅스가 좋다» 가 아니라 왜 그것을 골랐는지 근거를 적는 것입니다. 평가에서 보는 것도 결론이 아니라 근거입니다.

해 보기 운영체제 비교표를 만들고 하나를 고른다
  1. 스프레드시트에 «후보 / 비용 / 필요 기술인력 / 처리 성능 / 기술 지원 / 점수» 여섯 칸을 만듭니다.
  2. 후보 줄에 유닉스·리눅스·윈도우 세 줄을 넣고 각 칸을 상·중·하로 채웁니다.
  3. 맨 아래에 «선정 결과» 와 «선정 사유» 를 두 줄 적습니다. 사유는 반드시 앞 꼭지에서 조사한 현행 시스템을 근거로 씁니다.

tip «무난해서» 는 사유가 아닙니다. «현행이 CentOS 7 이고 운영 인력이 리눅스만 다룰 수 있어서» 가 사유입니다.

DBMS 주요 특징 및 고려 사항
사용자, 다른 애플리케이션, 데이터베이스와 상호작용 하여 데이터를 저장하고 분석 하기 위한 컴퓨터 소프트웨어 애플리케이션으로, 데이터베이스 생성, 조회, 변경 등의 관리가 주요 기능이다.

DBMS 도 «상용이냐 오픈 소스냐» 가 첫 갈림길입니다. 상용(Oracle, MS SQL Server)은 안정적이고 기술 지원을 받기 쉽지만 비쌉니다. 오픈 소스(MySQL, MariaDB, PostgreSQL)는 싸지만 문제가 생기면 스스로 풀어야 합니다.

학습모듈이 덧붙이는 말이 중요합니다 — 많이 쓰이는 것을 고르라. 쓰는 사람이 많으면 인터넷에 해결책이 있고, 사람을 구하기도 쉽습니다. 아무리 좋은 DBMS 라도 아무도 안 쓰면 문제가 생겼을 때 물어볼 데가 없습니다.

해 보기 DBMS 를 하나 골라 실제로 설치해 본다
  1. MySQL Community(dev.mysql.com/downloads/mysql) 또는 MariaDB(mariadb.org/download) 를 내려받아 설치합니다.
  2. 설치 중 root 비밀번호와 포트(기본 3306)를 적어 둡니다. 이것이 나중에 «개발 환경 정의서» 에 들어갑니다.
  3. 설치 후 명령창에서 mysql -u root -p 로 들어가 SELECT VERSION(); 를 실행하고 결과를 캡처합니다.
  4. 그 버전 번호를 소프트웨어 구성표의 «버전» 칸에 적습니다.

tip 설치가 막히면 DBMS 를 고르는 감이 생기지 않습니다. 한 번은 직접 깔아 보십시오.

미들웨어의 주요 특징 및 고려 사항
운영체제와 소프트웨어 애플리케이션 사이에 위치하는 미들웨어(Middleware)는 소프트웨어 애플리케이션에 운영체제가 제공하는 서비스를 추가 및 확장하여 제공하는 컴퓨터 소프트웨어를 말한다. 동적인 웹사이트, 웹 애플리케이션, 웹 서비스의 개발을 지원하기 위하여 설계된 소프트웨어로서 데이터 접근, 세션 관리, 트랜잭션 관리 등을 위한 라이브러리를 제공하고 있다.

미들웨어는 «운영체제와 응용 프로그램 사이» 에 있는 것들을 통틀어 부르는 말입니다. 범위가 넓어서 학습모듈도 그중 WAS(웹 애플리케이션 서버) 하나만 다룹니다.

WAS 는 웹 요청을 받아 프로그램을 실행해 주는 프로그램입니다. 자바면 Tomcat·JBoss·WebLogic·JEUS, 요즘 스프링부트는 Tomcat 이 안에 들어 있습니다.

고르는 기준은 DBMS 와 같습니다 — 성능 · 기술 지원 · 비용. 그리고 «개발용은 가볍게, 운영용은 안정적으로» 나눠 쓸 수 있다는 점을 기억하십시오.

해 보기 Tomcat 을 띄워 본다
  1. tomcat.apache.org 에서 Tomcat 10 zip 을 내려받아 압축을 풉니다.
  2. bin 폴더에서 startup.bat(윈도우) 을 실행합니다.
  3. 브라우저에서 http://localhost:8080 에 들어가 고양이 화면이 나오면 성공입니다.
  4. shutdown.bat 으로 내립니다. 포트 8080 을 «개발 환경 정의서» 에 적습니다.

tip 8080 이 이미 쓰이고 있으면 안 뜹니다. conf/server.xml 에서 포트를 8081 로 바꾸면 됩니다.

오픈 소스 사용에 따른 고려 사항
오픈 소스(Open Source)는 소스 코드를 공개해 누구나 특별한 제한 없이 그 코드를 보고 사용할 수 있는 오픈 소스 라이선스를 만족하는 소프트웨어를 말한다. 오픈 소스를 사용하는 경우에는 라이선스의 종류, 사용자 수, 기술의 지속 가능성 등을 고려해야 한다. 어떠한 오픈 소스를 사용해야 라이선스의 문제가 없을지 판단이 어려운 경우에는 전자정부 표준 프레임워크 포털(https://www.egovframe. go.kr/home/main.do)에서 사용 중인 오픈 소스 소프트웨어를 참조할 수 있다.

오픈 소스는 공짜가 아니라 조건부 무료입니다. 조건이 라이선스입니다.

크게 두 갈래입니다. GPL 계열은 «이걸 쓴 내 소스도 공개하라» 고 요구할 수 있고, MIT·Apache 계열은 «출처만 밝히면 마음대로» 입니다. 공공 사업에서 GPL 을 잘못 쓰면 소스 공개 문제가 생깁니다.

판단이 어려우면 학습모듈이 알려 준 대로 전자정부 표준프레임워크 포털(egovframe.go.kr)에서 «이미 검증해서 쓰고 있는 것» 목록을 참고하면 안전합니다.

해 보기 쓰려는 오픈 소스의 라이선스를 확인한다
  1. 앞에서 만든 소프트웨어 구성표에 «라이선스» 칸을 채웁니다.
  2. 각 제품의 GitHub 저장소에 가서 LICENSE 파일을 열어 맨 윗줄(MIT / Apache-2.0 / GPL-3.0 …)을 그대로 적습니다.
  3. GPL 이 하나라도 있으면 그 줄을 빨갛게 표시하고 «검토 필요» 라고 적습니다.

tip «오픈 소스니까 괜찮다» 가 가장 위험한 문장입니다. 라이선스 이름을 못 적으면 쓰면 안 됩니다.

시스템 용량 산정 방법
시스템을 구축하기 위하여 필요한 하드웨어 규모는 부록에 제시한 한국정보통신기술협회의 ‘정보시스템 하드웨어 규모 산정 지침’ TTAK.KO-10.0292 관련 내용을 참조하여, CPU 용량, 메모리 용량, 디스크 용량을 산정할 수 있다. 수행 tip 지침으로, 주요 내용은 다음과 같이 요약할 수 있다. 성능 요구사항(처리 건수, 응답 시간, 동시 사용자 수 등)을 기반으로 산정 기준을 설정한다. 대규모 거래 요청 처리 성능 다양한 설정 옵션 지원 가비지 컬렉션(GC: Garbage Collection)의 다양한 옵션 공급 벤더들의 안정적인 기술 지원 다수의 사용자들 간의 정보 공유 오픈 소스 여부 라이선스 정책 및 비용 유지 및 관리 비용 총 소유 비용(TCO: Total Cost of Ownership) / 개발 기술 환경 요구사항 파악하기 기기(장비･공구) 안전･유의 사항 면담 기록에 필요한 자료의 존재 여부를 파악한다.

용량 산정은 «서버를 몇 대, 얼마짜리로 살 것인가» 를 숫자로 정하는 일입니다. 기준 문서가 한국정보통신기술협회의 TTAK.KO-10.0292 입니다.

산정하는 것은 셋입니다 — CPU · 메모리 · 디스크. CPU 는 «트랜잭션 수 × 단위 처리 시간», 메모리는 «프로세스 수 · 캐시 · 버퍼», 디스크는 «데이터 크기 + 백업 + 로그 + 증가분» 으로 계산합니다.

빠뜨리기 쉬운 두 가지가 있습니다. 피크타임(수강신청 첫날 같은 순간)과 연간 증가율입니다. 평상시 기준으로 사면 개통 첫날 멈춥니다.

해 보기 디스크 용량을 실제로 계산해 본다
  1. 스프레드시트에 «항목 / 1건 크기 / 1일 건수 / 보관 기간 / 소계» 를 만듭니다.
  2. 예: 대출 기록 1건 = 0.5KB, 1일 1,200건, 3년 보관 → 0.5KB × 1200 × 365 × 3 = 약 657MB.
  3. 합계에 백업 2배와 여유 30%를 곱해 최종 용량을 냅니다.
  4. 결과를 하드웨어 구성표의 «디스크» 칸에 적습니다.

tip 계산식을 셀에 수식으로 넣어 두십시오. 건수가 바뀌면 숫자가 따라 바뀌어야 합니다.

왜 하는가

요구사항을 «확인» 한다는 말은 남이 적어 놓은 문장을 읽고 고개를 끄덕이는 일이 아닙니다. 그 문장이 정말로 만들 수 있는 것인지, 누가 언제 쓰는 것인지, 다 만들었는지 어떻게 판단할 것인지를 따져 보는 일입니다.

글로만 적힌 요구사항은 사람마다 다르게 읽힙니다. “회원이 좌석을 예약한다” 한 줄을 두고, 개발자는 예약 버튼 하나를 생각하고 기획자는 취소·변경까지 생각합니다. 그래서 그림 한 장과 표 한 장으로 못을 박습니다. 그림이 유스케이스 다이어그램이고, 표가 유스케이스 명세서입니다.

이 꼭지에서 만들 것은 그 둘입니다. 도구는 draw.io 와 스프레드시트면 충분하고, 둘 다 설치 없이 브라우저에서 됩니다.

알아야 할 것

요구사항 확인
분석가가 요구사항을 이해하였는지 확인(Validation)하는 것이 필요하고, 요구사항 문서가 회사의 표준에 적합하고 이해가 가능하고, 일관성이 있고, 완전한지 검증(Verification)하는 것이 중요하다. 이해관계자들이 문서를 검토해야 하고, 요구사항 정의 문서들에 대해 형상 관리를 해야 하는데 일반적으로 요구사항 관리 툴을 이용한다. 리소스가 요구사항에 할당되기 전에 문제를 파악하기 위하여 검증을 수행한다.
요구사항 확인 기법
(가) 요구사항 검증의 가장 일반적인 방법으로, 여러 검토자들이 에러, 잘못된 가정, 불명 확성, 표준과의 차이 등을 찾아내는 작업을 수행하며, 검토자 그룹을 어떻게 구성하 느냐가 중요하다. (나) 예를 들어 고객 중심 프로젝트에서는 검토자 그룹에 고객 대표자가 1명 이상 포함되어야 한다. 스프레드시트

유스케이스 명세서를 씁니다. 엑셀·LibreOffice Calc·구글 시트 아무거나 됩니다. 인쇄할 일이 많으니 A4 가로로 잡아 두면 편합니다.

따라 하기

1무엇을 그릴지 한 줄로 정한다
  1. 종이나 메모장에 «누가 / 무엇을 한다» 를 아는 대로 적습니다. 예: «회원이 좌석을 예약한다», «관리자가 좌석을 등록한다».
  2. 그 문장에서 누가에 해당하는 말을 모으면 액터(Actor)가 되고, 무엇을 한다에 해당하는 말을 모으면 유스케이스(Use Case)가 됩니다.
  3. 이 단계에서 완벽할 필요는 없습니다. 그림을 그리다 보면 빠진 것이 보입니다.

tip «회원 정보» 처럼 명사만 있는 것은 유스케이스가 아닙니다. 유스케이스는 반드시 동사로 끝나는 행동입니다.

2draw.io 를 열고 빈 다이어그램을 만든다
  1. 브라우저에서 app.diagrams.net 으로 들어갑니다.
  2. 저장 위치를 묻습니다. 학원 PC 라면 Device(내 장치)를 고릅니다. 구글 계정이 있으면 Google Drive 도 됩니다.
  3. Create New Diagram → 왼쪽 목록에서 Blank Diagram → 파일 이름을 usecase_좌석예약.drawio 처럼 적고 Create.

tip 저장 위치를 잘못 골라도 됩니다. 나중에 File → Save as 로 다시 고를 수 있습니다.

3UML 도형을 꺼낸다
  1. 왼쪽 도형 목록 맨 아래 More Shapes… 를 누릅니다.
  2. Software 묶음에서 UML 에 체크하고 Apply.
  3. 왼쪽 검색창에 actor 를 치면 사람 모양이, use case 를 치면 타원이 나옵니다.

tip 검색이 더 빠릅니다. 도형 목록을 뒤지지 말고 이름으로 찾으십시오.

4시스템 경계를 먼저 그린다
  1. 왼쪽에서 Rectangle(사각형)을 끌어다 화면 가운데에 크게 놓습니다.
  2. 사각형을 더블클릭하고 시스템 이름을 적습니다. 예: 좌석예약 시스템.
  3. 오른쪽 Style 탭에서 Fill 을 None 으로 바꿉니다. 안이 비어야 유스케이스를 올려놓을 수 있습니다.

tip 경계를 먼저 그리는 이유는 무엇이 시스템 안이고 무엇이 밖인지를 정하기 위해서입니다. 액터는 항상 밖에 있습니다.

5액터와 유스케이스를 놓는다
  1. 액터(사람 모양)를 사각형 바깥 왼쪽에 놓고 더블클릭해 회원 이라고 적습니다. 관리자가 있으면 오른쪽 바깥에 하나 더.
  2. 유스케이스(타원)를 사각형 안쪽에 놓고 좌석 예약하기 처럼 적습니다.
  3. 앞 단계에서 적어 둔 행동 수만큼 타원을 만듭니다. 보통 5~9개면 충분합니다.

tip 타원이 15개를 넘어가면 너무 잘게 쪼갠 것입니다. «로그인 화면을 연다» 는 유스케이스가 아니라 화면 조작입니다.

6선으로 잇는다
  1. 액터 가장자리에 마우스를 대면 파란 화살표가 뜹니다. 그것을 끌어 타원에 놓으면 선이 생깁니다.
  2. 이 선(연관, Association)에는 화살표가 없어야 합니다. 화살표가 생겼다면 선을 고르고 오른쪽 Style 에서 Line end 를 None 으로.
  3. 액터 하나가 여러 유스케이스에 이어질 수 있고, 반대도 됩니다.

tip 선이 엉키면 Arrange 탭에서 위치를 숫자로 맞추거나, 타원을 옮겨 선이 겹치지 않게 합니다. 읽는 사람이 먼저입니다.

7포함과 확장을 표시한다
  1. 여러 유스케이스가 반드시 거치는 공통 단계가 있으면 그것을 따로 타원으로 만들고, 점선 화살표로 이은 뒤 <<include>> 라고 적습니다. 예: «좌석 예약하기» → «로그인하기».
  2. 어쩌다 한 번만 일어나는 곁가지는 점선 화살표를 반대 방향으로 긋고 <<extend>> 라고 적습니다. 예: «예약 취소하기» → «좌석 예약하기».
  3. 점선으로 바꾸려면 선을 고르고 Style 에서 Dashed 를 켭니다. 글씨는 선을 더블클릭해서 적습니다.

tip 헷갈리면 둘 다 안 쓰는 것이 낫습니다. 잘못 쓴 include 는 안 쓴 것보다 나쁩니다.

8저장하고 그림으로 내보낸다
  1. File → Save 로 .drawio 파일을 저장합니다. 이것이 원본이고, 나중에 고칠 때 씁니다.
  2. File → Export as → PNG… 에서 Zoom 200%, Transparent Background 는 끄고 Export.
  3. 제출물에는 PNG 를 넣고, .drawio 원본도 같이 냅니다.

tip PNG 를 100% 로 뽑으면 인쇄했을 때 글씨가 뭉갭니다. 200% 로 뽑으십시오.

9유스케이스 명세서를 쓴다
  1. 스프레드시트를 열고 아래 예제의 표를 그대로 만듭니다. 칸 이름은 바꾸지 마십시오 — 평가에서 그 이름으로 찾습니다.
  2. 다이어그램의 타원 하나마다 표 하나를 씁니다. 타원이 6개면 표가 6장입니다.
  3. 기본 흐름은 «1. 회원이 …한다. 2. 시스템이 …한다.» 처럼 번갈아 적습니다. 사람과 시스템이 주고받는 모양이 되어야 합니다.

tip 사전 조건과 사후 조건을 비워 두는 사람이 많습니다. 거기가 «다 만들었는지» 판단하는 자리라 평가에서 먼저 봅니다.

1요구사항목록에 업무 기능에 대한 요구사항이 모두 반영되었는지 확인한다.
2요구사항 정의서의 작성 여부를 확인한다.
  1. 요구사항목록 중 수용 여부가 수락인 경우, 요구사항 정의서인 유스케이스 명세서가 작성되 었는지 확인한다. 유스케이스 명세서가 시스템이 어떻게 동작하여야 하는지를 명확하고 구체 적으로 기술하고 있는지 검토한다.
  2. 로그인 화면에서 회원은 공인 인증서 로그인을 선택한다.
  3. 로그인 화면에서 비회원은 비회원 로그인을 선택한다.
  4. 공인 인증서 로그인을 선택한 후 유효한 비밀번호가 제시되었으나, 사전에 회원 가입이 되어 있지 않은 경우, 회원 가입이 필요하다는 메시지를 보여 준다.
3비기능적 요구사항이 명확하게 도출되었는지 확인한다.
  1. 기능적 동작으로 표현되지 않는 시스템 특성, 품질, 제약사항 등 비기능적 요구사항이 명확 하게 도출되었는지 검토한다.
  2. 성능, 가용성, 사용 용이성, 유지보수 용이성, 안전성, 보안성 등에 대한 요구사항이 문서화 되었는지 확인한다.
  3. 비기능적 요구사항의 품질 목표가 정량적으로 정의되어 있으며 검증이 가능한 것인지 검토한다.
  4. 정상 업무 수행, 시스템 부하가 높은 경우 등 상황에 따라 응용시스템의 성능(응답 시간, 데이터 처리량 등) 목표치가 구체적으로 정해져 있는지 검토한다.
4타 시스템과 연계 및 인터페이스에 대한 요구사항이 적절히 도출되었는지 확인한다.
  1. 타 시스템 또는 하위 시스템 등과의 모든 인터페이스 요구사항이 정의되어 있는지 확인한다.
  2. 연계할 기관과 연계에 대한 합의나 계약이 체결되어 있는지 확인한다.
  3. 인터페이스 구분(내부/외부)이 명확하게 정의되어 있는지, 인터페이스 주기, 방법, 제공자, 요청자 등이 명확하게 정의되어 있는지 확인한다.
  4. 인터페이스 기능 구현과 관련된 제약사항 및 조건들이 기술되어 있는지 검토한다.
  5. 회원이 입력한 공인 인증서의 비밀번호가 유효하지 않은 경우, 로그인 실패 메시지와 실패 횟수를 보여 준다.
  6. 로그인 실패 횟수가 연속하여 5회 이상이 되면 해당 회원의 로그인 잠금을 설정하여 1시간 이내에는 로그인이 불가능하게 한다.
  7. 회원이 관리자에게 로그인 잠금 해제를 요청하면, 관리자는 유효한 회원 인지 검증을 한 후 잠금을 해제한다.

42-2. 요구사항의 시스템화 타당성 분석

업무 분석가가 수집하고 분석한 요구사항이 개발하고자 하는 응용소프트웨어에 미칠 영향에 대해서 검토하고 확인할 수 있다.

이 꼭지를 마치면

  • 업무 분석가가 수집하고 분석한 요구사항이 개발하고자 하는 응용소프트웨어에 미칠 영향에 대해서 검토하고 확인할 수 있다.

왜 하는가

요구사항을 다 모았다고 끝이 아닙니다. 그중에는 만들 수 없는 것과 만들면 안 되는 것이 섞여 있습니다.

«실시간으로 전국 데이터를 1초 안에 보여 주세요» 는 말은 되지만, 지금 예산과 서버로는 안 됩니다. 이런 것을 미리 걸러내는 일이 타당성 분석입니다. 개발이 시작된 뒤에 발견하면 이미 돈과 시간을 쓴 뒤입니다.

거르는 잣대가 넷입니다 — 성능·용량이 맞나 / 다른 시스템과 붙나 / 시장에서 쓰는 기술인가 / 위험이 큰가.

알아야 할 것

요구사항의 기술적 타당성 검토
‘정보화사업 사전타당성분석 방법론 연구’(한국전산원 2004)에서 “기술적 타당성 분석에서는 적용 기술의 적합성 및 기술 실현의 가능성이 분석의 핵심적 내용이 된다.”라고 명시하면서, 성능 및 용량 산정의 적정성, 시스템 간 상호 운용성, IT 시장 성숙도 및 트렌드 부합성, 기술적 위험 분석을 언급하고 있다.
성능 및 용량 산정의 적정성
‘1-2. 개발 기술 환경 정의 숕 시스템 용량 산정 방법’에서 목표시스템의 용량이 산정 되면, 과거 유사 프로젝트 경험치를 적용하여 필요시 재조정한 후, 성능 관련 비기능 요구사항과 비교하여 적정성 여부를 판단한다.

앞 꼭지(1-2)에서 산정한 용량을 요구사항과 맞대어 보는 일입니다. «동시 접속 5,000명» 이라는 요구사항이 있는데 산정한 서버가 1,000명짜리면 안 맞습니다.

학습모듈이 «과거 유사 프로젝트 경험치를 적용하여 재조정» 하라고 하는 이유가 여기 있습니다. 계산식만으로는 현실과 어긋나기 때문에, 비슷한 규모의 시스템이 실제로 어땠는지를 옆에 놓고 맞춰 봅니다.

해 보기 성능 요구사항과 산정치를 맞대어 본다
  1. 요구사항 목록에서 숫자가 들어간 것만 뽑습니다 (응답 시간 · 동시 사용자 · 처리 건수).
  2. 옆 칸에 1-2 에서 산정한 값을 적고, 세 번째 칸에 «충족 / 미충족 / 확인 필요» 를 적습니다.
  3. «미충족» 이 하나라도 있으면 아래에 «어떻게 할 것인가» 를 한 줄 적습니다 (서버 증설 / 요구사항 조정 / 캐시 도입 등).

tip 숫자가 없는 요구사항(«빠르게», «쾌적하게»)은 여기서 걸러 «숫자로 다시 받기» 목록에 넣으십시오.

시스템 간 상호 운용성
상호 운용성이란 다른 목적을 지닌 2개 이상 시스템들이 상호 간 정보 및 서비스를 교환하면서 효과적으로 운용될 수 있는 시스템의 능력을 의미한다(한국전산원 2004). 요구사항 중에서 목표시스템이 조직 내외 타 시스템과의 연동을 요구하는 경우, 상호 운용이 가능한지 여부를 판단해야 한다.

상호 운용성은 «다른 시스템과 말이 통하는가» 입니다. 1-1 에서 만든 인터페이스 현황표가 여기서 다시 쓰입니다.

볼 것은 셋입니다. 연동 대상이 그 인터페이스를 열어 주는가, 자료 형식이 맞는가, 우리가 원하는 주기로 줄 수 있는가. «그쪽에서 안 열어 준다» 는 기술 문제가 아니라 협의 문제라 더 오래 걸립니다.

해 보기 연동 가능성 점검표를 만든다
  1. 1-1 의 인터페이스 현황표를 복사해 옵니다.
  2. 오른쪽에 «연동 가능 / 협의 필요 / 불가» 칸과 «확인한 날짜 · 담당자» 칸을 더합니다.
  3. «협의 필요» 가 있으면 그것만 따로 모아 «협의 목록» 을 만듭니다.

tip 여기서 나온 «협의 목록» 이 프로젝트에서 가장 자주 일정을 늦추는 항목입니다. 빨리 시작할수록 좋습니다.

IT 시장 성숙도 및 트렌드 부합성
시스템 구축 시 요구되는 영역별 정보 기술들의 시장 성숙도 및 발전 방향을 파악하고, 요구사항이 이에 부합하는지 판단해야 한다. 시장 성숙도가 낮거나, 발전 방향에 부합 되지 않는 기술들은 향후 더 이상 사용되지 않을 가능성이 높아 시스템의 유지보수가 어려운 상황이 발생할 수 있다.

너무 낡은 기술도, 너무 새로운 기술도 위험합니다. 낡으면 사람과 자료가 사라지고, 새로우면 아직 검증이 안 됐습니다.

판단하는 법은 간단합니다 — 쓰는 사람이 늘고 있는가. GitHub 별 수와 최근 커밋 날짜, 채용 공고에 그 기술이 몇 번 나오는지를 보면 대체로 답이 나옵니다.

해 보기 고른 기술의 성숙도를 실제 자료로 확인한다
  1. 고른 기술(예: Spring Boot, MariaDB)의 GitHub 저장소에 들어갑니다.
  2. 마지막 커밋 날짜와 최근 릴리스 날짜를 적습니다. 1년 넘게 조용하면 위험 신호입니다.
  3. 채용 사이트에서 그 기술 이름으로 검색해 공고 수를 적습니다. 사람을 구할 수 있는지가 곧 유지보수 가능성입니다.

tip «요즘 뜨는 기술» 이라는 말 대신 날짜와 숫자를 적으십시오. 그것이 타당성 분석입니다.

기술적 위험 분석
요구사항을 만족시키기 위하여 적용한 기술의 복잡성, 검증 여부, 의존성 등에 대하여 위험 발생 가능성, 영향도를 파악한다. 기술의 특성 기술의 안정성, 시장성, 개방성을 저해하는 모든 요소 하드웨어, 소프트웨어, 솔루션의 적용이 아키텍처와 불일치 적용 기술에 대한 조직 내 무경험 외부 지원 불가능 특허 및 라이선스에 따른 문제 특정 업체 기술에 대한 의존 / 요구사항의 시스템화 타당성 분석하기 의서), 시스템 용량 산정 결과 엑셀(Excel) 파일 기기(장비･공구) 안전･유의 사항 내리지 않도록 신중히 검증하고, 분석 결과는 반드시 이중 확인 후 저장한다.

위험은 «일어날 가능성 × 일어났을 때의 영향» 으로 봅니다. 둘 다 높은 것만 먼저 손보면 됩니다.

학습모듈이 드는 위험 요소는 복잡성 · 검증 여부 · 의존성 셋입니다. 특히 의존성 — «그 회사 제품이 없으면 아무것도 안 되는» 구조는 나중에 값을 올려도 벗어날 수 없습니다.

해 보기 위험 등록부(Risk Register)를 만든다
  1. «번호 / 위험 내용 / 가능성(상중하) / 영향(상중하) / 대응 방안 / 담당» 여섯 칸을 만듭니다.
  2. 고른 기술마다 떠오르는 위험을 3~5개 적습니다. «처음 써 보는 기술이다», «담당자가 한 명뿐이다» 같은 것도 위험입니다.
  3. 가능성과 영향이 둘 다 «상» 인 줄을 맨 위로 정렬합니다. 그것부터 대응합니다.

tip 대응 방안에 «주의한다» 라고 적지 마십시오. «사전 검증용 시제품을 2주간 만든다» 처럼 할 일로 적습니다.

  • 연동 가능성 점검표와 «협의 목록»

왜 하는가

업무 분석가가 만든 분석모델(유스케이스 모델, 클래스 모델 등)을 받아서 «이걸로 개발할 수 있나» 를 따져 보는 꼭지입니다.

그림은 그럴듯한데 막상 만들려고 보면 «이 화면에서 저 자료를 어떻게 가져오지?» 하고 막히는 일이 흔합니다. 요구사항에는 있는데 모델에는 없거나, 모델끼리 서로 어긋나 있기 때문입니다.

그래서 두 방향으로 봅니다. 밖으로 — 요구사항과 모델이 하나씩 맞물리나. 안으로 — 모델끼리 모순이 없나. 뒤쪽을 «정합성» 이라고 부릅니다.

알아야 할 것

분석모델의 정의
분석모델이란 사용자의 요구사항을 기능적으로 정리하고, 이를 기반으로 시스템이 수행해야 할 구조와 동작을 논리적으로 표현한 모델이다. 설계 및 구현 이전 단계에서, 요구사항을 구체화하고 구조화된 형태로 표현함으로써 시스템의 전체적인 모습과 기능을 명확히 파악할 수 있게 한다.

분석모델은 설계 직전 단계의 그림입니다. 요구사항(말)과 설계(구현 방법) 사이에 있습니다.

«회원이 좌석을 예약한다» 는 말이고, «회원 클래스와 좌석 클래스가 있고 예약 클래스가 둘을 잇는다» 는 모델이며, «members 테이블에 PK 를 …» 은 설계입니다. 분석모델은 가운데입니다 — 무엇을 하는지는 정했지만 어떻게 만들지는 아직.

그래서 분석모델을 보면서 «어떤 DB 를 쓸까» 를 따지면 단계를 건너뛴 것입니다.

해 보기 말 → 모델 → 설계를 한 줄씩 써 본다
  1. 앞 꼭지(2-1)에서 만든 유스케이스 하나를 고릅니다.
  2. 세 칸짜리 표를 만들고 «요구사항(말)», «분석모델», «설계» 를 머리글로 둡니다.
  3. 고른 유스케이스를 세 칸에 각각 한 줄씩 옮겨 적어 봅니다. 설계 칸이 잘 안 써지면 그것이 정상입니다 — 아직 할 단계가 아닙니다.

tip 세 단계를 구분하지 못하면 회의에서 말이 엉킵니다. «지금 우리가 어느 단계를 이야기하는지» 를 늘 확인하십시오.

분석모델 검증의 목적
분석모델 검증은 업무 분석가가 제시한 분석모델이 실제 요구사항을 정확하게 반영하고 있는지를 확인하고, 응용소프트웨어 개발을 위해 적절한지를 평가하는 과정이다. 이 단계에서는 분석모델의 정확성, 완전성, 일관성 등을 점검하며, 모델이 소프트웨어 개발에 실질적으로 활용될 수 있는지를 판단한다.

검증에서 보는 것은 셋입니다 — 정확성 · 완전성 · 일관성.

정확성은 «요구사항을 잘못 옮기지 않았나», 완전성은 «빠뜨린 요구사항이 없나», 일관성은 «같은 것을 다른 이름으로 부르지 않았나» 입니다.

가장 흔한 사고가 완전성입니다. 요구사항 목록에는 «예약 취소» 가 있는데 유스케이스 다이어그램에 그 타원이 없는 식입니다. 그래서 눈으로 보지 말고 표로 맞대어 봐야 합니다.

해 보기 요구사항 추적표(Traceability Matrix)를 만든다
  1. 스프레드시트에 «요구사항 ID / 요구사항 / 유스케이스 ID / 클래스 / 확인» 다섯 칸을 만듭니다.
  2. 요구사항 목록을 왼쪽에 전부 붙여 넣습니다. 하나도 빼지 마십시오.
  3. 각 줄에 대응하는 유스케이스 ID 를 적습니다. 적을 것이 없는 줄이 곧 빠뜨린 요구사항입니다.
  4. 반대로 유스케이스 중 요구사항이 없는 것도 찾습니다. 그것은 아무도 요청하지 않은 기능입니다.

tip «확인» 칸은 체크가 아니라 확인한 사람 이름과 날짜를 적습니다. 평가에서 그것을 봅니다.

정합성의 개념 및 주요 검토 관점
정합성이란 모델이 논리적으로 일관되고 모순이 없으며, 구조적으로 정리된 상태를 의미한 다. 소프트웨어공학에서는 여러 개의 요구사항 또는 모델 간의 논리적 모순, 중복되거나 충돌되는 내용, 구조적 불일치와 같은 문제가 없어야 한다. -요구사항과 모델이 일대일 대응 -요구사항이 모델에 정확히 반영 -누락된 요구사항/과도한 기능 여부 사용자가 “주문 취소 기능이 필요하다”고 했는데, 유스케이스 다이어그램에 미존재 / 분석모델 검증하기 유스케이스 목록, 개념 수준 분석 클래스 다이어그램 및 명세서, 분석 클래스 다이어그 램 및 명세서, 분석 클래스 목록 기기(장비･공구) 안전･유의 사항 검토 기록지에 명확히 기록한 후, 담당자 또는 지도 교사에게 보고하여 공식 절차에 따라 수정하도록 한다.

정합성은 모델 안쪽의 문제입니다. 요구사항과 상관없이, 모델끼리 서로 모순되지 않아야 합니다.

자주 나오는 모순 셋입니다. ① 유스케이스 명세서의 «회원» 과 클래스 다이어그램의 «사용자» 가 같은 것인데 이름이 다름. ② 시퀀스 다이어그램에 나오는 메서드가 클래스에 없음. ③ 같은 기능이 유스케이스 두 곳에 중복으로 들어감.

눈으로 찾기 어렵습니다. 용어집(Glossary)을 만들어 이름을 하나로 못 박고, 다이어그램을 그 이름으로 다시 훑는 것이 가장 빠릅니다.

해 보기 용어집을 만들고 모델을 훑는다
  1. «대표 용어 / 같은 뜻으로 쓰인 말 / 정의» 세 칸짜리 표를 만듭니다.
  2. 지금까지 만든 문서(요구사항 목록 · 유스케이스 명세서 · 다이어그램)에서 사람·사물을 가리키는 명사를 전부 모읍니다.
  3. 같은 것을 다르게 부른 것을 한 줄로 합치고 대표 용어 하나를 정합니다.
  4. draw.io 로 돌아가 다이어그램의 이름을 대표 용어로 고칩니다.

tip 용어집은 프로젝트 내내 씁니다. 여기서 만들어 두면 설계·개발·시험에서 계속 덕을 봅니다.

왜 하는가

앞 꼭지에서 «모델이 요구사항과 맞나» 를 봤습니다. 이 꼭지는 한 걸음 더 나갑니다 — 이 모델대로 정말 만들 수 있나.

맞물리는 것과 만들 수 있는 것은 다릅니다. 요구사항과 완벽히 대응하는 모델이어도, 그대로 만들려면 서버가 열 배 필요하거나 아직 세상에 없는 기술이 필요할 수 있습니다.

그래서 유스케이스 하나하나에 대해 «필요한 자원 / 다른 시스템과의 연동 / 성능» 을 따져 보고, 개발자로서 의견을 적어 돌려줍니다. 이 꼭지의 산출물은 그림이 아니라 의견입니다.

알아야 할 것

분석모델의 기술적 타당성 검토
분석모델이 실제 시스템으로 구현하는 것이 가능한지를 판단하는 단계이다. 유스케이스 모델의 개별 유스케이스에 대한 분석모델을 작성한 이후, 해당 분석모델로 시스템을 개발하는 경우에 어떠한 영향을 미치는지 필요한 자원, 상호 운용성, 시장 성숙도, 기술적 위험 분석 측면에서 타당성을 조사한다. 성능 및 용량 - 요구사항을 기초로 하는 분석모델에 따라 시스템을 구현할 때, 필요로 하는 시스템의 자원을 식별한다. - 분석 클래스에서 불필요하고 지나치게 많은 속성을 포함하게 되면 객체 생성 시 시스템의 메모리 자원을 많이 요구하게 되며, 이로 인한 JVM에서 과도한 가비지 컬렉션(Garbage Collection)이 발생하여 전체 시스템의 성능 저하가 빈번히 발생한다.

학습모듈이 말하는 절차는 «앞의 요구사항 추적표에 타당성 검토 의견 칸을 하나 더 붙이는 것» 입니다. 새 문서를 만들지 않습니다.

검토하는 관점은 2-2 와 같습니다 — 필요 자원 · 상호 운용성 · 성능. 다만 대상이 «요구사항 한 줄» 이 아니라 «유스케이스 하나» 입니다. 더 구체적이라 더 정확한 판단이 나옵니다.

의견은 세 갈래로 씁니다. 그대로 가능 / 조건부 가능(무엇을 바꾸면) / 불가(왜, 대안은). «어려울 것 같다» 는 의견이 아닙니다.

해 보기 추적표에 타당성 의견 칸을 붙이고 채운다
  1. 3-1 에서 만든 요구사항 추적표를 엽니다.
  2. 오른쪽에 «필요 자원 / 연동 / 성능 / 판정 / 의견» 다섯 칸을 더합니다.
  3. 유스케이스마다 한 줄씩 채웁니다. 판정은 «가능 / 조건부 / 불가» 셋 중 하나만 씁니다.
  4. «조건부» 나 «불가» 인 줄은 의견 칸에 대안을 반드시 적습니다. 예: «실시간 대신 5분 주기 배치로 바꾸면 가능».

tip 의견을 적을 때 «개발자 입장에서» 를 잊지 마십시오. 업무 분석가가 모르는 것을 알려 주는 것이 이 꼭지의 값어치입니다.

«불가» 를 적는 것을 두려워하지 마십시오. 여기서 안 걸러진 것은 개발 막바지에 터집니다.

흔한 실수

  • 새 문서를 만든다. 추적표에 칸을 더하는 것이 맞습니다. 문서가 갈라지면 둘이 어긋납니다.
  • 전부 «가능» 으로 적는다. 그러면 검토한 것이 아닙니다.
  • 대안 없이 «불가» 만 적는다. 개발자가 할 일은 막는 것이 아니라 다른 길을 알려 주는 것입니다.
  • 혼자 정하고 끝낸다. 학습모듈 절차의 3·4단계가 «이해관계자 검증» 과 «배포·공유» 입니다. 의견은 돌려줘야 뜻이 있습니다.

내야 할 것

  • 타당성 검토 의견이 붙은 요구사항 추적표
  • «조건부 / 불가» 항목의 대안 목록
  • 이해관계자 검증 기록 (누가 언제 확인했는지)
  • 최종 배포본 (검토 의견 반영 후)

학습모듈이 제시한 실습 절차

분석모델의 시스템화 타당성 분석하기
재료·자료현행 시스템 분석서, 사용자 면담 기록, 요구사항목록, 요구사항 정의서, 유스케이스 다 / 이어그램, 유스케이스 명세서, 유스케이스 목록, 개념 수준 분석 클래스 다이어그램 및 / 명세서, 분석 클래스 다이어그램 및 명세서, 분석 클래스 목록기기·도구컴퓨터, 프린터, 인터넷, 문서 작성 프로그램, 엑셀(Excel) 프로그램, UML 저작 프로그램유의 사항타당성 분석 과정에서 산출된 시스템 용량, 기술 난이도, 인력·비용 추정 결과는 프로 / 젝트 의사결정에 직접 영향을 미치므로, 계산 오류나 잘못된 가정을 방지하기 위해 분 / 석 근거와 수치를 반드시 이중 검증하고 기록을 남긴다.
1분석모델까지 요구사항 추적표를 작성하고, 타당성 검토 의견 칼럼을 추가한다.
2작성된 요구사항 추적표에 타당성 검토 의견을 작성한다.
  1. 타당성 검토 의견을 제외한 나머지 속성들은 분석모델 검증 수행 내용의 작성 절차와 동일하다.
  2. 유스케이스 모델, 개념 수준 분석 클래스 모델, 분석 클래스 모델의 기술적 타당성 검토를 위하여 필요 지식에 명시된 바와 같이 성능 및 용량, 시스템 간 상호 운용성, 시장 성숙도 및 트렌드 부합성, 기술적 위험 분석을 참조하여 검토 의견을 작성한다. 각 모델별로 다음 사항을 특히 유의해야 한다.
3타당성 분석 결과를 관련 이해관계자가 검증한다.
  1. 타당성 분석 결과를 관련 이해관계자에게 배포하여 사전 검토를 요청한다.
  2. 관련 이해관계자가 모여 분석모델 타당성 분석 결과를 검증한다.
  3. 타당성 분석 결과에 이견이 있는 경우 프로젝트 관리자(Project Manager)의 중재하에 합의를 도출한다.
4관련 이해관계자 검증을 거친 타당성 분석 결과를 확인하고 배포 및 공유한다.
  1. 관련 이해관계자 검증을 거친 타당성 분석 결과를 의사 결정자가 확인한다.
  2. 의사 결정자가 확인한 타당성 분석 결과를 이해관계자에게 배포하여 공유한다.

스스로 확인

  • 분석모델까지 요구사항 추적표를 작성하고, 타당성 검토 의견 칼럼을 추가한다.
  • 작성된 요구사항 추적표에 타당성 검토 의견을 작성한다.
  • 타당성 분석 결과를 관련 이해관계자가 검증한다.
  • 관련 이해관계자 검증을 거친 타당성 분석 결과를 확인하고 배포 및 공유한다.
  • 업무 분석가가 제시한 분석모델에 대해서 응용소프트웨어를 개발하기 위해 필요한 추가적인 의견을 제시할 수 있다.

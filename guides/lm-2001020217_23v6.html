알아야 할 것

리팩토링 개념
리팩토링(Refactoring)은 소프트웨어 기능(동작)에는 변함이 없도록 하면서 내부 구조를 개선하여 소프트웨어의 가독성, 유지보수성, 확장성, 재사용성, 그리고 궁극적으로 성능을 향상하기 위한 개발 기법을 말한다.
리팩토링 시점
한 번에 대대적으로 진행하거나 너무 빈번한 리팩토링보다는 작은 단위로, 테스트할 수 있는 상태에서 점진적으로 수행하는 것이 좋다.
기능 추가 시
새로운 기능을 추가하기 전에 기존 코드를 충분히 이해하고 구조를 개선하기 위해 리팩토링을 수행한다. 이를 통해 코드의 중복과 잠재적인 결함을 미리 줄일 수 있으며, 이후 기능 추가나 수정 작업을 더 빠르고 원활하게 진행할 수 있다.
버그 수정 시
버그를 수정하기 어렵거나, 같은 유형의 버그가 반복적으로 발생한다면 리팩토링이 필요 하다. 소스코드를 정리하여 버그뿐만 아니라 잠재적인 결함을 제거할 수 있다.
지속 수행
별도의 시간을 내서 리팩토링을 수행하는 것이 아니라 틈틈이 지속해야 소스코드의 잠재적인 위험을 제거하게 되며 소프트웨어의 생명력을 지속할 수 있다.
가독성이 좋은 코드
단순하고 직접적으로 잘 쓰인 문장처럼 읽히고 설계자의 의도가 보이는 코드로, 추상화와 단순한 제어문으로 구성된 코드를 말한다.
변경이 쉬운 코드
작성자가 아닌 사람도 읽기 쉽고 고치기 쉬운 코드로, 이를 위해서는 의미 있은 이름이 부여되고 특정한 목적을 달성하는 방법은 하나만 제공한다.
중복 없는 코드
같은 작업을 여러 차례 반복하지 않는 코드로, 같은 작업을 여러 차례 반복한다면 코드가 문제 해결을 제대로 하지 못한다는 증거이다.
주의 깊게 짜인 코드
고치려고 살펴봐도 딱히 손댈 곳이 없는, 작성자가 이미 모든 상황을 고려하여 작성된 소스코드를 말한다.
리팩토링 주의 사항
리팩토링은 코드 품질을 높이고 유지보수를 쉽게 하지만, 잘못 진행하면 오히려 위험을 초래할 수 있다. 리팩토링은 작고 안전하게, 테스트와 함께, 협업과 소통을 바탕으로 진행해야 하며, 언제든 복구가 가능한 환경에서 단계적으로 실행하는 것이 핵심이다.
기능 보존의 원칙
리팩토링의 목적은 코드의 구조 개선이지, 동작하는 기능을 변경하는 것이 아니기 때문에 리팩토링 전후로 모든 기능이 동일하게 동작하는지 반드시 확인해야 한다.
작은 단위로 점진적으로 진행
한 번에 많은 부분을 수정하면 오류 발생 가능성이 커지므로 작은 단위로 나누어 리팩 토링하고, 단계마다 테스트를 수행한다.
자동화된 테스트의 활용
자동화된 테스트(단위/통합 테스트)를 활용하여 리팩토링 전후로 테스트를 반복 실행하고 기존 기능에 문제가 생기지 않도록 확인한다.
버전 관리 시스템 적극 활용
변경 이력을 추적할 수 있도록 Git 등 버전 관리 시스템을 사용하여 문제가 생겼을 경우 언제든 이전 상태로 롤백할 수 있어야 한다.
코드 리뷰와 협업
혼자만의 판단으로 대규모 리팩토링을 진행하지 말고, 동료와 코드 리뷰를 통해 개선 방향을 논의한다. 협업 환경에서는 변경 사항을 충분히 공유하고, 팀의 합의를 끌어내는 것이 중요하다.
문서화와 공유
리팩토링 후 변경된 코드 구조나 설계 의도를 문서화하여 팀원과 공유하면 향후 유지 보수 시 큰 도움이 된다.

애플리케이션의 안정적인 운영과 유지보수를 위해, 성능 및 가독성을 보장하는 코드 작성 규칙에 따라 소스코드 저장 구조를 준수해야 한다.
애플리케이션 개발 보안
개발 과정에서 개발자 실수, 논리적 에러 등으로 인해 소스코드에 내재된 보안 취약점을 최소화하고, 보안 위협에 대응할 수 있는 안전한 애플리케이션을 개발하기 위한 일련의 과정을 의미한다.
애플리케이션 보안 약점
애플리케이션 결함, 오류 등으로 사이버 공격, 정보 유출 등을 유발할 가능성이 있는 잠재적인 취약점을 말한다.
애플리케이션 보안 약점 진단 도구
개발 중에 소스코드상의 애플리케이션 보안 취약점을 식별하고 식별된 소스코드의 위치를 정리할 수 있도록 지원하는 도구를 말한다.
불필요한 코드(Dead Code)
애플리케이션에서 불필요한 코드는 실행은 되지만 결과가 다른 응용 프로그램에 사용될 수 없는 코드이다. 불필요한 코드의 실행은 연산 처리 시간과 메모리의 낭비를 초래한다.
불필요한 코드(Dead Code) 예시
int foo (int a, int b) int c = ab; return a*b; 비록 a를 b로 나누는 것이 연산 처리되고 전혀 사용되 지 않더라도 0으로 나누기가 발생할 때는 예외 처리될
불필요한 코드 분석 방법
유효 변수 분석을 통하여 소스코드의 정적 코드 분석과 데이터 흐름 분석을 수행하 여 제어 흐름 분석을 통한 코드 분석의 미흡한 부분을 보완한다.

1개발 표준을 만족하지 않는 소스코드를 식별한다.
  1. 소스코드 분석 도구에 개발 표준 기준 적용 개발 표준에 정의된 내용을 만족하지 않는 소스코드를 식별하기 위해 분석 도구의 룰을 세팅한다. 동료 검토 등 육안 식별을 위해서 점검 항목을 작성한다.
  2. 정적 소스코드 분석 도구 활용 정적 소스코드 분석 도구는 소스코드를 실행하지 않고 코드의 잠재적인 오류, 취약점, 그리고 코딩 표준 준수 여부를 분석하는 자동화 도구이다. ‘정적’이라는 용어는 프로그 램을 실행하지 않고 코드 자체를 검사한다는 점에서 유래하였으며, 주요 기능은 다음과 같다.
  3. 동적 소스코드 분석 도구 활용 동적 소스코드 분석 도구는 실제로 프로그램을 실행하여 발생하는 동작을 분석하고 잠재적인 문제점을 파악하는 데 사용되는 자동화 도구이다. 프로그램이 실행되는 동안의 메모리 사용, 함수 호출, 네트워크 활동 등을 모니터링하여 정적 분석 도구로는 발견하 기 어려운 런타임 오류나 성능 병목 지점, 보안 취약점을 찾아낸다.
  4. 소스코드 리뷰 수행 소스코드 분석 도구를 활용하여 개발 표준을 준수하지 않은 사항을 식별한다. 일부 주석 작성 규칙, 표준 용어 미적용 사례, 보안 취약점 등은 분석 도구에서 전체를 식별할 수 없으므로 샘플링하여 리뷰를 수행한다.
  5. 개발 표준을 준수하지 않은 소스코드 목록 작성 소스코드 분석 도구의 분석 결과를 출력하여 코드 위치, 우선순위, 위반 룰 등의 항목으로 개발 표준을 위반한 소스코드 목록을 작성한다.

  2. 소프트웨어 개발 보안 기준을 활용하여 분석한다.
  3. 소프트웨어 개발 보안 기준을 활용한 분석 결과를 정리한다.

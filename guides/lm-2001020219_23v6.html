알아야 할 것

요구사항의 정의
요구사항이란 실세계(Real-world)의 문제를 해결하는 데 도움을 줄 제품이나 시스템에 부여되는 필요 사항 또는 제약 사항을 의미한다.
요구사항의 중요성
요구사항은 소프트웨어의 개발 및 유지･보수의 단계에서 필요한 기준과 근거를 제공하 므로 요구사항이 제대로 정의되어야만 이후 단계의 목표와 계획을 수립할 수 있다.
사용자 요구사항(User Requirements)
사용자 요구사항이란 시스템을 사용하는 주체인 사용자 관점으로 시스템이 제공할 것을 요구하는 서비스 사양과 제약 사항을 의미한다.
시스템 요구사항(System Requirements)
시스템 요구사항이란 전체 시스템이 만족시켜야 하는 요구사항을 의미한다. 시스템의 의미를 소프트웨어뿐만 아니라 하드웨어에 해당하는 컴퓨터를 모두 포함하는 개념으로 보면, 시스템의 요구사항이란 시스템 외부의 사용자와 주변 환경(타 시스템)에 제공해야하는 서비스 요구사항을 의미한다.
기능 요구사항(Functional Requirements)
기능 요구사항이란 소프트웨어로 수행하고자 하는 기능에 관해 기술한 것으로, 목표 시 스템이 반드시 수행해야 하거나 목표 시스템을 이용하여 사용자가 반드시 수행할 수 있어야 하는 기능(동작)에 대해 기술한 것으로 문서의 서식을 맞춘다든지 이미지나 각종 신호를 처리하는 등 특정 목적에 따라 소프트웨어에 요구되는 기능을 서술한 것이다.
비기능 요구사항(Non-Functional Requirements)
비기능 요구사항이란 SW 시스템이 기능 요구사항을 만족시키면서 정상적으로 작동하기 위한 시스템 내부 또는 외부의 제약 조건을 의미한다.
요구사항 도출을 위한 자료 수집
요구사항 도출을 위한 자료의 원천은 컴퓨터 관련 특정 업무 서비스에 사용하는 애플리케이션 개발 자료와 일반적인 사용자들이 사용하는 범용 애플리케이션 개발 자료로 구분할 (Business Process Reengineering) 사업 시작 시 업무 절차를 분석하여 업무의 전반을 개선하는 결과 문서 사업 시작 초기에 (Information Strategy Planning) BPR 이후에 정보화
요구사항의 개발 프로세스
소프트웨어공학 지식 체계(SWEBOK: Software Engineering Body of Knowledge) 의 요구사항 개발 프로세스는 요구사항의 도출(Elicitation), 분석(Analysis), 명세 (Specification), 확인(Validation)으로 구분하고 있다.
요구사항 도출
요구사항 도출은 소프트웨어 시스템에 요구되는 기능 및 제약 사항을 수집해야 한다. 한국직업능력개발원. p.64. (가) 인터뷰 소프트웨어 개발에 참여하는 이해관계자들과의 직접적인 질문과 대화를 통해 정보를 추출하는 일반적인 요구사항 도출 방법이다.
자료 정리
요구사항 관련 자료 수집과 도출 활동이 완료된 후 최종 자료에 대해 정리한다. 이때, ISO/IEC 25010의 기능적 적합성, 사용성, 보안성 등을 기준으로 요구사항을 재분류하 거나 태깅할 수 있다.

정리된 자료의 접근 통제
요구사항에 관련된 자료는 조직 내에서 매우 중요하게 관리해야 하며, 해당 자료에 대해 권한 그룹을 생성하고, 문서･정보의 보안이 이루어질 수 있도록 한다.

알아야 할 것

기능 분할
시스템 관점에서 외부에 제공해야 하는 서비스(기능)를 유형별로 최하위 단위 구성 요소에 도달할 때까지 분할해 가는 방식으로 분석하는 방법이다.
유스케이스와 사용자 스토리
유스케이스(Use Case)란 시스템 경계 밖에 위치한 액터가 특정 목적을 달성하기 위해 시스템이 제공하는 기능을 이용하여 시스템과 일련의 상호작용을 주고받는 시나리오로 나타낸 것이다.
유스케이스 접근법
UML의 근간이 되는 주요 기법의 하나로, 유스케이스 다이어그램은 시스템에 대한 이해관계자인 액터(Actor)와 상호작용을 나타내는 유스케이스(Use Case) 간의 관계와 구조를 가장 개괄적으로 보여 주는 도표이다.
개념 모델링(Conceptual Modeling)
실세계 문제에 대한 모델링이 소프트웨어 요구사항 분석의 핵심이며, 모델은 문제가 발생하는 상황에 대한 이해를 증진시키고 해결책을 설명한다.
요구사항 분류
요구사항 분석과 협상을 위해 도출된 각각의 요구사항을 좀 더 풍부하고 상세하게 이해하고, 이를 여러 가지 방법으로 표현함으로써 요구사항을 분류하고 조직화하여 명세를 구체 화해 나가는 것이다.
요구사항 우선순위 할당
고객의 기대치가 높고 일정이 짧은 경우, 제품이 가장 중요하거나 가치 있는 기능을 가능 한 한 빨리 제공할 수 있는지 확인해야 한다.
우선순위 할당
우선순위 할당 요청 시 고객의 반응은 “모든 기능이 필요하다. 그냥 모두 다 해 주세 요.”이다. 우선순위가 프로젝트 수행에 반드시 필요하지만 우선순위를 줄이기는 매우 어렵다.
우선순위 할당 기법
모든 우선순위 할당 방법 중 가장 간단한 것은 요구사항목록 작업을 수행할 이해관 계자 그룹을 확보하고, 요구사항 각각에 대해 할지, 하지 말지 양자택일을 하는 것 사람들은 종종 각 요구사항에 고유한 우선순위 번호를 할당하려고 한다.
가치와 비용, 위험에 따른 우선순위
이해관계자가 상대적으로 비정형 기법으로 할당된 요구사항 우선순위에 동의하지 않는 경우 분석적인 방법을 사용하는 것이 유용하다.
요구사항 협상(Requirement Negotiation)
이해관계자가 서로 상충되는 내용을 요구하거나 또는 기능과 비기능 요구사항들이 서로 상충되는 경우, 어느 한쪽을 지지하기보다는 적절한 균형(trade-off) 지점에서 합의가 중요하다.

  2. 요구사항을 정제한다.
2기능 요구사항과 비기능 요구사항을 분류한다.
  1. 기능 요구사항에 관련된 내용을 정리하고 분류한다.
  2. 비기능 요구사항에 관련된 내용을 정리하고 분류한다.
  3. 요구사항 작성 시 유의 사항을 파악한다.
  4. 요구사항을 분류하고 식별자(ID: Identifier)를 부여한다.
3우선순위를 할당한다.
  1. 우선순위 결정 과정의 참가자를 선정한다.
  2. 가치와 비용, 위험에 따른 우선순위를 부여한다.
  3. 요구사항 우선순위 평가 템플릿을 작성한다.
  4. 전기 안전 규제 자료 인쇄
  5. 판매 업체 주문 상태 조회
  6. 컴퓨터 부품 재고 보고서 생성
4비기능 요구사항을 분석한다.
  1. 비기능 요구사항목록을 1차 정제한다.
  2. 우선순위를 부여한다.
  3. 특정 부품 이력 보기
  4. 특정 부품에 대한 판매 업체 카탈로그 검색
  5. 위험 전기 규제품 목록 관리
  6. 보류 중인 규제 부품 요청 변경
  7. 실험실 재고 보고서 생성
  8. 규제 부품 교육 기록 데이터베이스 확인
  9. 긴급 부품 수배 도구에서 불러오기 합계 (2) 매트릭스의 대각선 상단 행렬(Upper Triangular Matrix)의 각 항목은 해당 행과 열의 비기능 요구사항의 상대적 중요도를 평가하여 표시한다. 만약 행(Row)의 요구사항이 더중요하면 ‘˂’로, 열(Column)의 요구사항이 더 중요하면 ‘˄’로 표시한다.

33-1. 요구사항 명세

애플리케이션 사용자 또는 활용 분야의 관점에서 요구사항을 분석한 결과를 정리한 상위 수준의 사용자 요구사항 정의서를 작성할 수 있다.

이 꼭지를 마치면

  • 애플리케이션 사용자 또는 활용 분야의 관점에서 요구사항을 분석한 결과를 정리한 상위 수준의 사용자 요구사항 정의서를 작성할 수 있다.
  • 구현하고자 하는 애플리케이션이 구동되는 시스템이나 하드웨어 관련 내용을 구체화하여 시스 템 요구사항 문서를 작성할 수 있다.
  • 구현하고자 하는 애플리케이션에 대해 설명, 검증 및 테스트, 계약을 위해 사용자 요구사항 정의서와 시스템 요구사항 문서를 토대로 요구사항을 구체화하여 소프트웨어 요구사항명세서 (SRS, Software Requirement Specification)를 작성할 수 있다.

알아야 할 것

요구사항 문서화
요구사항 개발의 결과는 개발해야 하는 프로젝트에 대한 이해관계자 간의 문서화로 나타나며, 비전 범위 문서와 사용자 요구사항 문서, 소프트웨어 요구사항명세서로 구분할 수 있다.
비즈니스 요구사항 문서화
재무, 시장, 고객이나 개발 조직이 제품에서 얻고자 하는 비즈니스 혜택을 포함해야 한다. 예를 들면 “중부 지역의 시장 점유율을 6개월 안에 10% 향상시킨다.”, “전기료를 1년 내에 15% 절감한다.” 등으로 나타낸다.
비즈니스 규칙 문서화
고객이 특정 조건하에서 특정 사용자만 어떤 활동을 수행해야 한다고 말하는 것이다. 예를 들면 “반드시 준수해야 하는 ~ ”, “만약 어떤 조건이 참(true)이라면 어떤 일이 발생한다.”, “신규 고객은 컨설팅 비용과 경비의 20%를 사전에 지불해야 한다.”, “휴가 승인은 사내 인사 관련 휴가 정책을 준수해야 한다.” 등으로 나타낸다.
사용자 요구사항 문서화
사용자가 수행해야 하는 업무를 표현한 일반적인 문장으로, 일반적으로 유스케이스, 시 나리오, 사용자 스토리로 표현된다.
기능적 요구사항 문서화
기능적 요구사항은 특정 조건하에서 시스템이 보여 주거나 사용자가 시스템을 사용할 수 있게 하는 행동을 식별할 수 있는 행위이다.
품질 속성 문서화
시스템이 무엇을 얼마나 잘 제공하느냐에 대한 설명으로 빠르게, 쉽게, 신뢰할 수 있는 등의 특성을 설명하는 단어를 사용한다.
외부 인터페이스 문서화
시스템과 시스템을 제외한 모든 것의 연결로서 “∼로부터 신호를 읽어야 한다.”, “포맷의 파일을 읽을 수 있어야 한다.” 등이며, 예를 들면 “주문 실행 시스템은 상품 목록과 연계해야 합니다.”, “모바일 앱은 A가 입금하는 수표를 촬영하고 그 이미지를 은행 전 송과 연계해야 합니다.” 등으로 나타낸다.
제약 조건 문서화
개발자가 실행할 수 있는 정당한 방법으로 제한해야 한다. “특정 프로그래밍 언어로 작성해야 한다.” 등으로, 예를 들면 “컴퓨터를 통한 파일 전송은 그 크기가 5기가바이트 (GB)를 초과할 수 없다.”, “브라우저는 모든 보안 처리에 64비트(bit) 암호화를 사용해야 한다.” 등으로 나타낸다.
데이터 요구사항 문서화
데이터 요소에 대한 포맷 타입, 허용된 값, 기본값 또는 복잡한 비즈니스 요구사항의 보고서 출력 등을 나타낼 때 데이터 요구사항도 포함해야 한다.
솔루션(solution) 아이디어 문서화
사용자로부터 얻는 대부분의 요구사항은 실제로 솔루션 아이디어이다. 누군가가 어떤 행동을 수행하기 위해 시스템과 상호작용 하는 방법을 설명한다면 솔루션을 제안한다고 볼 수 있다.
소프트웨어 요구사항명세서 정의
소프트웨어 요구사항명세서는 다양한 이름으로 불리는 경우가 많다. 이를 비즈니스 요구 문서(BRD: Business Requirements Document)나 기능 명세서, 제품 명세서, 시 스템 명세서, 아니면 단순히 요구사항 문서라 부르기도 한다.
요구사항 명명하기
모든 요구사항은 유일하고 영구적인 식별자가 필요하다. 가장 간단한 방법은 모든 요구사항에 UC(Use Case)-9이나 FR-26과 같은 고유한 일련번호를 부여하는 것이다.
불완전한 요구사항 다루기
때로는 특정 요구사항에 대한 정보가 누락된 것을 알고 있을 것이다. 이러한 격차를 표시하기 위해 TBD(To Be Determined) 표기법을 사용한다.
사용자 인터페이스와 SRS
사용자 인터페이스 디자인을 SRS에 통합하는 것은 장단점을 모두 갖고 있다. 장점으로는 가용 사용자 인터페이스 탐색, 시뮬레이션 도구 등을 통해 요구사항을 현실화한다는 것이다.
소프트웨어 요구사항명세서 템플릿
모든 소프트웨어의 개발은 프로젝트에 대해 표준 SRS 템플릿을 도입해야 한다. SRS 템플 릿은 여러 종류가 있는데, 프로젝트 유형에 맞는 템플릿을 도입하는 것이 좋다.

  17. 기타 요구사항을 작성한다.
  18. 용어 사전을 작성한다.

스스로 확인

  • 비전 범위 문서를 작성한다.
  • 소프트웨어 요구사항명세서를 작성한다.
  • 애플리케이션 사용자 또는 활용 분야의 관점에서 요구사항을 분석한 결과를 정리한 상위 수준의 사용자 요구사항 정의서를 작성할 수 있다.
  • 구현하고자 하는 애플리케이션이 구동되는 시스템이나 하드웨어 관련 내용을 구체화하여 시스 템 요구사항 문서를 작성할 수 있다.
  • 구현하고자 하는 애플리케이션에 대해 설명, 검증 및 테스트, 계약을 위해 사용자 요구사항 정의서와 시스템 요구사항 문서를 토대로 요구사항을 구체화하여 소프트웨어 요구사항명세서 (SRS, Software Requirement Specification)를 작성할 수 있다.

4. 요구사항 검증하기능력단위요소 · 2001020219_23v6.4

44-1. 요구사항 검증

소프트웨어 요구사항명세서가 문서 표준을 준수하여 사용자가 이해 가능한 내용으로 일관성 있고, 완성도 있게 작성되었는지를 검증할 수 있다.

능력단위요소

원문 86쪽

분량

이 꼭지를 마치면

  • 소프트웨어 요구사항명세서가 문서 표준을 준수하여 사용자가 이해 가능한 내용으로 일관성 있고, 완성도 있게 작성되었는지를 검증할 수 있다.
  • 작성한 요구사항명세서의 오류, 잘못된 가정, 불명확한 설명, 비표준적인 내용 등이 있는지 확인을 위해 조사(Inspection) 혹은 검토(Review)를 실시할 수 있다.
  • 기술 환경, 구현 가능성, 안정성 등을 고려하여 요구된 도출 사항들을 검증할 수 있다.
  • 분석 단계의 개념 모델링 결과물이 있을 경우 표기법, 모델 원칙 준수 여부 판단 등을 통해 모델을 검증할 수 있다.

알아야 할 것

SW 요구사항 검증
SW 요구사항 검증이란 SW 개발의 기준선(Baseline)이 되는 요구사항명세서가 올바르 게 작성되었는지 점검하는 것을 의미한다.
SW 요구사항 검증(Verification)과 확인(Validation)의 차이
SW 제품을 만드는 각 공정의 중간 산출물의 품질을 지속적으로 점검하는 두 가지 점 검 방식은 크게 검증(Verification)과 확인(Validation)으로 나뉜다.
SW 요구사항 검증 범위
SW 요구사항 검증은 요구사항명세서가 미리 정해진 산출물 작성 품질 기준에 부합하도록 올바르게 작성되었는지 점검하는 것이다.
SW 요구사항 검증 기준
요구사항명세서를 검증하기 위한 품질 기준을 의미하며, 이해관계자의 기대와 품질 표준을 만족시킬 수 있도록 요구사항을 올바르게 기술하였는지를 검증하기 위해서는 이해 관계자들이 합의한 객관적인 검증 기준이 필요하다.
요구사항 검증 기법
동료 검토(Peer Review)는 산출물 작성자와 이해관계자가 참여하여 요구사항명세서에서 결함을 찾는 것으로, 명문화된 산출물 표준을 준수하여 기록하였는지, 검토자가 요구사항 내용을 동일하게 이해할 수 있도록 쉽고 명확하게, 그리고 일관성 있게 작성하였는지 등을 점검한다.
ISO/IEC 25010 – 시스템 및 SW 품질 요구사항 및 평가 모델
ISO/IEC 25010은 SW 품질 평가를 위해 광범위한 기준을 제공하는 품질 요구사항 및 평가 모델로서, SW 제품의 품질을 평가할 때 어떤 특성이 고려되어야 한는지를 결정하는 데 도움을 준다.

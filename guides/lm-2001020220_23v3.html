알아야 할 것

기능 모델링의 개념
기능이란 입력물을 받아 결과물을 제공하는 활동을 말하며, 이러한 기능을 수행하는 활동을 프로세스라고 말한다.
기능 모델링 절차
기능 모델링은 소프트웨어 요구공학 절차에서 요구사항 분석 및 요구사항 명세 부분에 시스템의 특성에 따른 기능모델 기법을 선정한 후 해당 기능모델 다이어그램을 작성한다.
소프트웨어 시스템의 특성
기능 모델링을 작성하기 위해서는 소프트웨어 시스템의 특성을 파악하고 그에 따른 기능모 델 설계 기법을 선정해야 한다.
개발 방법론
자료의 흐름과 구조에 따라 프로세스를 구분하고 점차적으로 세분화하여 사용자 요구사항에 맞는 시스템을 구축하는 방법론이다.
프로그래밍 언어
프로그래밍 언어는 소프트웨어공학 방법론의 패러다임과 연관되므로 프로그래밍의 패러 다임 형태에 따라 구분한다.
기능모델 분석 기법
시스템 요구사항을 분석하는 기법에는 구조적 분석 기법, 객체지향 분석 기법, 정보공학 분석 기법, 정형화 분석 기법 등이 있다.
구조적 분석 기법(Structured Analysis Method)
방법론은 불명확한 사용자 요구사항 도출과 변경으로 의사소통에 어려움이 있고, 하위 모듈에서 상위 모듈로 가는 상향식(Bottom-up) 방식의 개발로 인해 상위 모듈의 에러 (Error) 발생 시 오류 수정의 어려움이 있었다.
객체지향 분석 기법(Object Oriented Analysis Method)
객체지향 분석 기법은 구조적 분석 기법과 근본적으로 접근 방식을 달리한다. 둘은 개념화하는 방식이 서로 달라 문제를 정의하고 분할하는 방법 또한 다르다.

1기능모델 작성을 위한 기능모델 다이어그램의 선정 준비를 다음과 같은 절차로 진행한다.
  1. 기능 모델링 다이어그램 선정을 위해서 시스템 환경을 이해한다.
  2. 환경에 대한 이해가 끝나고 나면 목표 시스템의 제약사항에 따른 특성을 파악해야 한다.
  3. 목표 시스템의 환경과 특성, 개발 방법론과 프로그래밍 언어의 특성에 따라 기능모델 기법을 선정한다.
  4. 선정한 기능모델 기법에 알맞은 기능모델 다이어그램을 선정한다.
2기능 모델링 기법 선정을 위해 목표 시스템의 환경을 분석한다.
  1. 목표 시스템의 정보시스템 구성 및 인터페이스를 파악한다.
  2. 목표 시스템의 정보시스템 기능 구조도를 파악한다.
  3. 목표 시스템의 정보시스템 아키텍처를 파악한다.
3기능 모델링을 위해 목표 시스템의 특성(제약조건)을 분석한다.
  1. 요구사항 정의서 중 개발 제약사항을 통해 개발 방법론을 확인한다.
  2. 시스템은 컴포넌트 기반 개발(CBD: Component-Based Development) 방법론을 적용한다.
  3. 시스템은 제시된 방법론의 절차와 과정(개발 표준, 기술표준 문서화)에 따라 개발되어야 한다.

  7. 시스템은 ‘전자정부서비스 호환성 준수지침(행안부 고시)’를 준수해야 한다.
  8. 목표 시스템 환경 및 개발 방법론에 따라 프로그래밍 언어 유형을 확인한다.
4분석된 목표 시스템 특성에 맞는 기능모델 기법을 선정한다.
  1. 목표 시스템의 환경과 특성에 따라 구조적 분석 기법을 선정한다.
  2. 목표 시스템의 환경과 특성에 따라 객체지향 분석 기법을 선정한다.

알아야 할 것

구조적 분석 기법 개념
1970년대 말 디마르코(DeMarco)와 유어든(Yourdon) 등이 제안한 구조적 분석 기법은 시스템을 기능적 관점에서 나누고 추상화 개념을 접목한 상위 프로세스에서 하위 프로세스로 점차적으로 세분화한다.
구조적 분석 기법 작업 구성 요소
구조적 분석에서의 모델은 자료 흐름도(Data Flow Diagram), 배경도(Context Diagram), 자료 사전(Data Dictionary), 소단위 명세서(mini-specification)로 시스템 안의 프로세스 및 자료 저장소들 사이의 자료 흐름을 도식화한 그래프이다.
구조적 분석 기법 절차
구조적 분석 기법은 두 가지 가정에서 시작된다. 하나는 시스템이 무엇을 하느냐(what) 에 관심을 두고, 하나는 하향식(Top-down)으로 문제를 다룬다.
객체지향 분석 기법(Object Oriented Analysis Method)
최근 소프트웨어 시스템을 개발하는 방법론으로 객체지향 접근 방법을 사용하는 경우가 많다. 응용 소프트웨어, 웹 소프트웨어, 게임 프로그램 등 다양한 소프트웨어를 개발할 때 객체지향 개발 방법론을 사용한다.
객체지향 분석 기법 개념
객체지향 분석 기법은 구조적 분석 기법과 접근하는 방식이 다르다. 객체지향 분석 기법에서 가장 먼저 할 일은 사용자 요구사항을 고객 관점에서 추출하고 추출된 요구사 항을 기반으로 삼아 유스케이스로 표현한다.
객체지향 분석 기법 구성 요소
객체지향 분석 기법은 대표적으로 유스케이스 다이어그램(Use Case Diagram)으로 표현하므로 유스케이스 다이어그램의 구성 요소로 기능모델 설계를 진행한다.
객체지향 분석 기법 절차
유스케이스 다이어그램을 통한 기능 모델링의 절차는 다음과 같다 시스템의 이해관계자인 액터와 식별한 액터의 책임을 확인 특정한 목적의 관점에서 볼 때 쓰임새(Use)와 시스템의 특성을 확인 (가) 액터와 유스케이스에서 정제할 부분이 있는지 평가 (나) 유스케이스에서 <<include>> 의존성이 있는지 평가 (다) 유스케이스에서 <<extend>> 의존성이 있는지 평가 (라) 액터와 유스케이스

알아야 할 것

기능모델 설계 명세서의 개념
기능모델 설계 명세서는 기능모델 다이어그램을 설명하기 위해 제약조건, 입력에서 출력으로 변환되기 위한 기능 등을 구체적으로 기술한 문서이다.
기능모델 설계 명세서의 유형
구조적 분석 기법과 객체지향 분석 기법에서 사용되는 설계 명세서 표현 방식이 다르 다. 분석 기법별 기능모델 설계 명세서의 대표적인 유형은 다음과 같다.
소단위 명세서(mini-specification)
위 명세서는 자료 흐름도의 원시 프로세스(최하위 프로세스)가 어떤 기능을 하는가를 기술하는 것이다. 프로세스 명세서(process-specification), 미니 명세서(mini-specification), 소작 업 명세서(activity-specification)라고 부르기도 한다.
구조적 영어(structured English)
말 그대로 구조를 가진 영어로서, 영어 단어 중 제어나 연산을 표현하는 단어로 제한하여 사용한다. 예를 들면 GET, SET, PUT, COMPUTE, ADD, FIND, MOVE, REPLACE, SORT 등이 해당한다.
의사결정표(decision table)
프로세스가 여러 가지 조건에 대하여 각기 다른 처리를 할 때 적합한 표현 방법이다. 결정에 영향을 주는 변수, 각 변수의 상태 값, 각 경우에 대한 처리 방식을 체계적으로 표현하는 방법이다.
유스케이스 명세서(Use Case Specification)
유스케이스 명세서란 각 유스케이스 별로 개요, 제약조건, 특별 요구사항 등 상세한 사항을 정리하는 문서이다.
유스케이스 명세서 구성 요소
유스케이스에 대한 고유 식별 번호 유스케이스에 대한 간결한 명세로서 시스템의 기능을 명확한 동사구 형태로 표현한다.

알아야 할 것

동료 검토(Peer Review)의 정의
프로젝트 수행 과정에서 각 진행 단계별로 발생하는 산출물 또는 제품에 대해서 동료 들이 상호 교차하여 검토하는 활동이다.
동료 검토의 효과
페이건(Fagan)이 발표한 생산성 향상 모형을 살펴보면 동료 검토를 수행한 경우 약 6개월 정도 기간이 단축될 뿐만 아니라 전체적인 재작업 비율을 25~35%까지 절감할 수 있다.
동료 검토의 종류
동료 검토에는 Walk-through(워크 스루, 비공식적 검사), Inspection(검사), Technical Review(기술 검토), Management Review(경영 검토) 등 종류가 다양하다.
동료 검토의 절차
동료 검토는 계획, 사전 교육, 준비, 동료 검토 회의, 수정, 시정 조치의 순서로 진행한 다. 절차 중 사전 교육은 생략 가능하며, 준비 단계는 원활한 동료 검토 회의를 위해 반드시 수행해야 할 절차이다.
동료 검토의 구성원 역할
동료 검토는 진행자, 작성자, 제출자, 검토자, 기록자로 구성된다. 워크 스루의 경우 작성자가 진행자와 제출자를 겸한다.
기능모델의 표준 표기법 및 산출물
구조적 분석 기법과 객체지향 분석 기법에 따라 기능모델의 표준 표기법 및 산출물은 달라진다.
구조적 분석 기법의 표준 표기법 및 산출물
1970년대 말에 디마르코(DeMarco)가 발표하고 1980년대부터 널리 활용되고 있는 구조적 분석 기법이 표준 표기법으로 사용되고 있다.
객체지향 분석 기법의 표준 표기법 및 산출물
한국정보화진흥원의 “정보시스템 감리지침: 시스템개발사업 객체지향 컴포넌트 모델 V1.0”에 따르면 시스템 기능에 대한 유스케이스 모형의 상세화 수준 및 적정성에 대하 여 다음과 같은 사항을 점검토록 하고 있다.

  2. 기능모델 검증 수행 결과 (1) 결함이 발견된 검토 대상 산출물의 위치( 페이지 및 라인 수)를 기록한다.
5작성자가 시정 조치를 수행한 후 조치 결과를 기술한다.
  1. 기능모델 검증 결과의 검토 의견별 조치 결과 내용을 요약하여 기록한다.
  2. 검토 의견에 대해 조치 완료 예정일을 기록한다.
  3. 기능모델 검증 의견에 따라 시정된 항목을 기술한다.
  4. 관련자들로부터 재작업, 사후 조치 및 조치 사항 완료에 대해 확인한다.

스스로 확인

  • 기능모델의 표준 표기법, 산출물 양식과 지침의 검증을 위한 동료 검토 계획을 수립한다.
  • 도식된 기능모델이 표준 표기법을 준수하는지 검증한다.
  • 작성된 기능모델이 표준으로 제시된 산출물 양식과 지침을 준수하는지 검증한다.
  • 검증이 완료된 후 작성자에게 결과물을 전달하여 시정 조치를 요청한다.
  • 작성자가 시정 조치를 수행한 후 조치 결과를 기술한다.
  • 도식된 기능모델이 표준 표기법을 준수하고 있는지 검증할 수 있다.
  • 작성된 기능모델이 표준으로 제시된 산출물 양식과 지침을 따르고 있는지 검증할 수 있다.

알아야 할 것

요구사항 분석 명세서의 개념
소프트웨어 시스템이 수행하여야 할 기능과 시스템 환경의 제약조건 및 개발자와 사용 자가 합의한 성능에 관한 사항 등을 분석하여 명확하고 일관성 있게 명세한 문서이다.
요구사항 분석 명세서의 관점
사용자는 시스템의 현황과 문제점은 잘 알고 있으나, 문제점에 대한 기술적인 해결 방안에 대한 이해가 부족하다.
요구사항 분석 명세서 작성 시 주의 사항
이 기술되어야 한다.
요구사항 분석 명세서의 표준, IEEE Std 830-1988 SRS
IEEE Std 830-1988 문서는 요구사항 분석 명세서(SRS)를 표준화한 가이드이다. 요구사항 분석 명세서를 작성하는 데 필요한 내용을 제공하여 요구사항을 분석하는 프로젝트 관리자나 개발자들의 표준 템플릿을 제공한다.
요구사항 분석 명세서 검증
시스템 구축 과정에서 가장 중요한 일은 산출물에 대한 검토 및 검증이다. 요구사항 분석 명세서는 분석 단계부터 종료 단계까지 지속적으로 작성하면서 요구사항을 확인하고 검증 함으로써 시스템의 품질을 보증해야 한다.
지속적인 요구사항 검증의 필요성
요구사항 검증은 요구사항 분석, 설계, 개발 등 각 과정에서 주기적으로 이루어져야 한다. 대부분의 결함들이 요구사항의 모호함과 설계의 부정확함에서 시작된다.
요구사항 분석 명세서 검증 사항
요구사항 분석 명세서는 요구사항을 파악한 후 이를 검토하고 설계하는 데 도움을 줄수 있도록 문서화하여야 한다.

1기능모델 검증을 위해 요구사항 분석 명세서를 작성한다.
  1. 요구사항 분석 명세서의 목차를 정의한다.
  2. 소개(Introduction)
  3. 일반적인 기술 사항(General Description)
  4. 상세 요구사항(Specific requirements)
  5. 작성된 목차에 맞게 요구사항 분석 명세서를 작성한다.
  6. 상세 요구사항(Specific requirements) ‧ ‧ ‧ 부록(Appendices) 인덱스(Index) 본 문서는 OO프로젝트를 수행하기 위한 요구사항을 분류하고 기술하기 위한 목적으로 만들어졌다.
  7. 일반적인 기술 사항 본 시스템은 사용자가 쉽고 간편하게 사용할 수 있도록 설계되었다. 사용자는 웹 화면을 통해 지원 사업 및 공고 사항을 확인할 수 있으며, 지역별로 회원사의 현황을 확인할 수 있다.
  8. 상세 요구사항 직원은 근태 관리 시스템을 통해 아이디, 비밀번호를 입력하여 로그인한다.
2인스펙션(Inspection. 검사)을 통해 작성된 기능모델이 요구사항을 모두 포함하고 있는지 검증
  1. 인스펙션 계획서를 작성한다.
  2. 기능모델 검증 활동 프로세스 활동 개발자 파트 리더 동료 검토자 (●:주관 ○:지원) 기능모델 검증자 선정 게 기능모델 검증자 선정을 요청한다.
  3. 인스펙션 수행 활동에 따른 요구사항을 검증한다.
  4. 요구사항이 일관되게 기술되었는가?
  5. 요구사항이 명백하게 기술되었는가?
  6. 정의된 모든 요구사항은 소프트웨어로 구현될 수 있는가?
  7. 하나의 요구사항은 여러 요구사항에 중복됨이 없이 유일하게 존재하는가?
  8. 기능적 요구사항이 작성되었는가?
  9. 기능적 요구사항에 대해서는 기능 개요, 입력물, 처리 방법, 출력물 등을 기술하였는가?
  10. 고객의 성능 요구사항이 테스트 가능 하도록 정량화되어 있는가?
  11. 인터페이스 관련 요구사항이 기술되었나?
  12. 보안 관련 요구사항이 기술되었나?
  13. 하드웨어 환경(제약사항 포함)이 완전하게 정의되었는가?
  14. 설치 및 마이그레이션 요구사항이 완전하게 정의되었는가?
  15. 에러 복구 및 백업 요구사항이 완전하게 정의되었는가?
  16. 요구사항이 Safety/Standard를 준수하는가?
  17. 주요 기능 요구사항에 대해 계층적으로 세분화하여 기술하였는가?

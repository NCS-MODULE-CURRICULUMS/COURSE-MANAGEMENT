알아야 할 것

UML(Unified Modeling Language)의 이해
UML은 소프트웨어의 청사진을 작성하는 표준 언어로, 이를 이용하여 산출물을 통한 가시 화, 명세화, 문서화가 가능한 도구이다.
UML의 구성 요소
UML은 모델의 기본 요소인 사물과 사물 간의 관계를 나타내는 관계, 사물들 간의 관계를 도식화한 다이어그램 등으로 구성된다.
정적 다이어그램과 동적 다이어그램
시스템의 정적인 부분을 가시화하기 위하여 다이어그램을 이용하여 표현한 것으로 주요 다이어그램은 아래와 같다.
UML을 이용한 모델링
요구사항의 정의 단계에서 주로 유스케이스 다이어그램을 사용하여 시스템으로부터 도출된 기능적 요구사항을 표현한다.
설계 패턴, MVC(Model-View-Controller) 패턴 이해
소프트웨어 아키텍처 설계 가이드 라인에 정의된 설계 패턴을 바탕으로 해당 패턴 요소별 정적모델 설계 요소들을 상세 분석하고, 이를 바탕으로 소프트웨어 응용 설계를 진행하게 되므로 설계 패턴에 대한 이해가 중요하다.
컨트롤러(Controller) 컴포넌트
전체적인 제어 흐름을 관리하는 역할을 하는 영역으로 모델과 뷰 영역 간 흐름을 조정하는 역할을 한다. 사용자 인터페이스에서 발생된 이벤트를 입력받아 처리한다.
모델(Model) 컴포넌트
애플리케이션에서 비즈니스 핵심 기능 로직과 데이터를 다루는 영역이다. 데이터를 캡슐화하고 애플리케이션에 특화된 프로세스 로직을 수행하는 영역이다.
뷰(View) 컴포넌트
클라이언트에게 보여지는 프레젠테이션 로직이 구현되는 영역이다. 다양한 뷰로 구현이 가능하며 다양한 방법으로 모델 컴포넌트 영역에서 처리한 정보를 보여 준다.

알아야 할 것

소프트웨어 분석 단계와 설계 단계에서의 정적모델
소프트웨어 분석 단계에서의 관점이 요구사항을 이해하는 관점이라면, 설계 단계에서는 구체적으로 요구사항을 어떻게 해결할 것인가의 관점이라고 할 수 있다.
정적모델의 구성 요소
소프트웨어 설계 단계에서 활용되는 정적모델인 클래스 다이어그램의 구성 요소는 아래 공통의 속성과 메서드, 관계, 의미 등을 공유하는 객체들의 집합이다.
정적모델 검증에 필요한 정적 분석 규칙
정적모델의 각 요소들에 대한 명명 규칙과, 정의된 플랫폼 환경에 따라 규칙을 정의함으로써 정적 분석모델을 검증할 수 있다.
정적모델 명명 규칙
소프트웨어 설계 가이드라인에 정의된 명명 규칙을 준수하는지 검증할 수 있는 규칙들을 정의한다. 상세 설계 단계에서는 실제 구현 단계에서 명명된 이름을 사용할 수 있도록 영문으로 된 이름을 기술해야 한다.
개발 플랫폼 기반 설계 패턴 규칙
개발 플랫폼의 종류에 따라 정적모델 요소 식별 및 식별된 요소들 간의 관계, 예를 들어 인프라 클래스의 상속 여부 등을 규칙으로 정한다.

  2. 보안, 성능, 외부 인터페이스 등 비기능적인 행위(동작)들이 플랫폼에 기반하여 기술적으로 고려되었는지 검증한다.

32-1. 정적 설계모델 상세화

분석된 정적모델을 정적 설계모델로 변환하기 위해 변환 규칙을 정의할 수 있다.

이 꼭지를 마치면

  • 분석된 정적모델을 정적 설계모델로 변환하기 위해 변환 규칙을 정의할 수 있다.
  • 정적 설계모델의 엔티티 클래스, 경계 클래스, 제어 클래스를 상세화할 수 있다.

알아야 할 것

분석 클래스 모델의 이해
분석 클래스 모델을 구성하는 분석 클래스들은 그 역할과 책임에 따라 경계 클래스, 제어 클래스, 엔티티 클래스로 분류할 수 있다.
경계 클래스(Boundary Class)
시스템과 외부 액터와의 상호 작용을 표현하는 데 사용되는 클래스로 주로 화면, 외부 시스템과의 인터페이스 등이 정의된다.
제어 클래스(Control Class)
비즈니스 로직의 처리 흐름을 제어 또는 조정하거나 트랜잭션을 처리할 때 사용되는 클래스이다. 경계 클래스에서 입력된 값을 전달받아 제어 클래스에서 정의한 비즈니스 로직에 따라 출력값을 제공한다.
엔티티 클래스(Entity Class)
비즈니스 로직 처리 흐름이 수행되는 과정에서 저장소에 저장되어야 하는 정보를 표현하는 클래스이다. 엔티티 클래스의 정보는 시스템이 종료된다 해도 정보값이 유지되어야 하므로 영구적인 데이터가 파일 또는 데이터베이스로 구현된다.
클래스 설계 원칙의 이해
클래스 설계 원칙은 객체지향 설계에서 클래스의 구조와 동작을 정의하는 데 있어 중요한 지침을 제공한다.
객체지향 프로그래밍의 4대 핵심 원칙
객체지향 프로그래밍은 현실 세계의 개체들을 소프트웨어 객체로 모델링을 할 때 네가지 원칙을 기반으로 한다. 캡슐화는 객체의 데이터와 메서드를 하나의 단위로 묶고, 외부에서의 직접적인 접근을 제한하는 원칙이다.
SOLID 원칙: 객체지향 설계의 핵심
SOLID 원칙은 Robert C. Martin이 제시한 다섯 가지 객체지향 설계 원칙으로, 현대 소프트웨어 개발에서 클래스의 구조와 동작을 정의하는 데 있어 가장 중요한 지침 중 클래스는 하나의 책임만 가져야 하며, 단일 기능만을 수행해야 한다.
클래스 설계 품질 요소, 응집도와 결합도의 이해
응집도(Cohesion)와 결합도(Coupling)는 클래스 설계의 품질을 결정짓는 핵심 요소이 다. 두 개념은 객체지향 설계의 기본 원칙과 밀접하게 관련 있으며, 잘 설계된 클래스는 높은 응집도와 낮은 결합도를 가진다.

1정적 분석모델 상세화는 다음과 같은 순서로 진행한다.
2정적 분석모델을 정적 설계모델로 변환하기 위한 규칙을 정의한다.
  1. 정적 설계모델의 명명 규칙을 정의한다.
  2. 정적 분석모델과 설계 클래스 변환 규칙을 정의한다.
  3. 정적 설계모델 상세화 규칙을 숙지하고 이를 기준으로 상세화를 진행하도록 한다.
  4. 경계 클래스는 외부에 구체적인 구현 방법이 노출되어서는 안 된다.
  5. 경계 클래스의 변경이 경계 클래스를 이용하는 제어 클래스의 불필요한 변경을 유발하지 않아야한다.
  6. 제어 클래스는 경계 클래스와 엔티티 클래스에 독립적으로 표현해야 한다.
  7. 제어 클래스의 비즈니스 로직을 구현하는 방법이 노출되지 않아야 한다.
  8. 엔티티 클래스는 데이터 로직만을 제공해야 한다.
  9. 엔티티 클래스는 구현 방법이 외부에 노출되지 않아야 한다.
  10. 정적 설계모델 클래스별 변환 규칙을 정의한다.
3경계 클래스를 상세화한다.
  1. UI 클래스를 상세화한다.
  2. SI 클래스를 상세화한다.
  3. DI 클래스를 상세화한다.
4제어 클래스를 상세화한다.
  1. 시스템이 처리해야 할 비즈니스 로직 및 제어 로직을 제어 클래스의 오퍼레이션으로 표현한다.
  2. 제어 클래스의 오퍼레이션들이 공유하는 정보를 속성으로 표현한다.
  3. 영속적으로 유지되어야 하는 정보를 엔티티 클래스의 속성으로 표현한다.
  4. 영속적인 정보의 관리를 위한 기능을 엔티티 클래스의 오퍼레이션으로 표현한다.
  5. 클래스 모델 간의 관계를 검토하여 보완한다.
  6. 클래스 모델을 통합, 분할하여 작성한다.
  7. 클래스 모델을 제거하여 작성한다.
  8. 체크리스트를 작성하여 클래스 모델을 검토 후 개선한다.
  9. 설계 클래스와 클래스 유형과의 관계를 숙지한다.
  10. 설계 클래스 속성과 오퍼레이션을 상세 정의한다.
  11. 클래스 간의 상호 관계를 상세 정의한다.
  12. 인스펙션을 통해 설계 클래스 모델을 검토하고 보완한다.

  • 정적 분석모델 상세화는 다음과 같은 순서로 진행한다.
  • 정적 분석모델을 정적 설계모델로 변환하기 위한 규칙을 정의한다.
  • 경계 클래스를 상세화한다.
  • 제어 클래스를 상세화한다.
  • 분석된 정적모델을 정적 설계모델로 변환하기 위해 변환 규칙을 정의할 수 있다.
  • 정적 설계모델의 엔티티 클래스, 경계 클래스, 제어 클래스를 상세화할 수 있다.

알아야 할 것

정적 설계모델 명세서의 작성 방법
소프트웨어 관점이나 설계 관점에서 구현 단계를 고려하여 각 클래스별로 상세한 명세를 기술한다. 패키지를 이용하여 조직화된 정적 설계모델 정보를 상세히 기술한다.
작성 방법
분석 패키지를 이용하여 계층적으로 구조화하고, 클래스 이름, 속성 및 오퍼레이션을 정확하고 구체적으로 정의하고, 각각의 클래스는 상세하게 명세를 기술한다.
작성 항목
소프트웨어 관점이나 설계 관점에서의 설계 클래스 모형을 작성하고 클래스별 상세한 명세를 기술한다. 정적 설계모델 명세서의 작성 목적과 개략적인 요약 내용을 기술한다.
정적 설계모델 명세서 검토
효율적인 애플리케이션 구현과 유지 관리를 위해 각 클래스들이 패키지에 적절하게 배치되 어야 한다. 정적 설계모델 명세서를 작성한 후 아래 기준에 따라 검토한다.
분석 클래스 모델의 조직화 검토 기준
(가) 패키지의 이름은 패키지에 속한 모든 클래스를 대표하는가? (나) 패키지는 높은 응집도와 낮은 결합도를 가져야 한다.
분석 클래스 명세서 검토 기준
각 분석 패키지 내의 분석 클래스 다이어그램을 구성하는 경계 클래스, 제어 클래스, 엔티티 클래스와 이들 간의 관계에 대해 검토한다.

  5. 검토된 사항을 정리하여 정적 설계모델 명세서를 보완한다.

클래스 다이어그램은 정적 설계모델의 대표적인 다이어그램으로 시스템을 구성하는 클래 스, 클래스 요소들, 클래스 간의 관계를 표현한다.
클래스 다이어그램의 기본 구성 요소
클래스는 사각형으로 표현되고 클래스명, 속성, 오퍼레이션으로 구성된다. 클래스는 구체적으로 의미 있는 이름으로 명명하고 <<stereotype>>을 정의할 수 있다.
정적 설계모델 설계서의 작성 방법
소프트웨어 관점이나 설계 관점에서 구현 단계를 고려하여 정적 설계모델을 상세하게 작성
작성 방법
설계 클래스를 도출하기 위해서는 우선 유스케이스별로 시퀀스다이어그램을 작성하도록하고, 여기서 도출된 객체 및 클래스의 연관 관계를 파악하여 유스케이스별로 클래스 다이어그램를 작성한다.
작성 항목
소프트웨어 관점이나 설계 관점에서의 설계 클래스 모형을 작성하고 클래스별로 상세한 명세를 기술한다. 유스케이스별로 대응되도록 작성한다.

정적 설계모델 도식화하기
재료·자료상세화된 분석 클래스 모델 / 정적 설계모델 명세서기기·도구전산 장비(컴퓨터, 프린터, 빔 프로젝터, 네트워크 장비 등) / OA 도구(워드프로세서, 스프레드시트, 프레젠테이션 도구 등) / 설계용 소프트웨어(UML 모델링 도구)유의 사항UML의 정적 다이어그램(클래스, 패키지 등)은 국제 표준 표기법이므로 기본 구조와 표 / 기 규칙을 반드시 숙지한 후, 실습한다. / 팀원과 협업할 때 파일 덮어쓰기나 충돌 방지를 위해 공용 폴더나 클라우드 공유 시 주 / 의하여 파일을 저장한다. / UML 작성 도구(예: StarUML)는 저장을 주기적으로 수행하고, 작업한 파일은 버전 이 / 름을 명확히 기재하여야 한다. / 실습 예제에 실제 사용자 이름, 전화번호, 이메일 등 개인정보와 민감정보를 입력하지 / 않도록 주의한다.
1설계용 도구를 설치하고, 도구 사용자 가이드 문서를 참고하여 사용법을 익힌다.
  1. 설계용 도구 다운로드 사이트에 접속하여 설치 파일을 다운로드받는다.
  2. 다운로드받은 설치 파일을 이용하여 설치한다.
  3. 설치된 UML 설계 도구의 사용법을 숙지한다.
2도식화할 클래스 다이어그램을 종이에 미리 스케치한다.
3정적 설계모델 가운데 클래스 다이어그램을 도식화한다.
  1. 다이어그램 모델을 선택한다.
  2. 클래스를 생성한다.
  3. 클래스의 속성을 추가한다.
  4. 클래스의 오퍼레이션을 추가한다.
  5. 클래스 간의 관계를 추가한다.
  6. 클래스를 보완하여 완성한다.
  7. 다음과 같이 완성된 로그인 관리 클래스 다이어그램의 사례를 참조한다.
4정적 설계모델 설계서를 작성한다.
  1. 정적 설계모델 설계서를 작성한다.
  2. 작성된 정적 설계모델 설계서를 검토하고 수정하여 완성한다.

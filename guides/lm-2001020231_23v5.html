알아야 할 것

구조적 프로그래밍의 이해
구조적 프로그래밍은 구조화 프로그래밍으로도 불리며 절차적 프로그래밍 기반 아래 만들 어진 프로그래밍 기법으로 GOTO문 없이 순차, 분기, 반복 구조를 기반으로 프로그램을 설계하고 개발하는 것이다.
구조적 프로그래밍 설계의 이론적 근거
빔-야코피니 정리(Böhm-Jacopini Theorem, 1966년)에 따르면 이탈리아의 컴퓨 터 과학자 코라도 빔과 주세페 야코피니는 순차, 선택, 반복의 단 3가지의 제어 구조만으로 모든 계산 가능한 알고리즘(튜링 머신으로 표현 가능한 모든 것)을 구현할 수 있음을 수학적으로 증명하였다.
구조적 프로그래밍 언어의 변화 과정
이 시기는 GOTO문이 여전히 널리 쓰였지만, 구조적 프로그래밍의 핵심 아이디어를 담은 선구적인 언어가 등장한 중요한 시기이다.
if-then-else, while, for 등 명확한 구조의 제어문을 제공하며, GOTO문의 사
용을 의도적으로 어렵게 만듦
시스템 프로그래밍을 위한 저수준 제어 기능과 효율성을 중시하면서도, ALGOL
의 철학을 이어받아 강력한 구조적 프로그래밍 문법을 제공
C언어의 성공은 구조적 프로그래밍이 전 세계의 표준으로 자리 잡는 데 결정적
인 역할을 함구조적 프로그래밍으로 코드의 논리 구조를 잡는 것에서 더 나아가, 데이터를 중심으로 프로그램을 구성하는 객체지향 프로그래밍(OOP)이 부상하였다.
goto가 예약어로는 존재하지만 실제 기능은 구현되지 않아 사용이 불가능하
며, 이는 GOTO를 쓰지 못하도록 한 매우 의도적인 설계 C#(2000년), Go(2009년), Swift(2014년), Kotlin(2011년), Rust(2010년) 등은 구조적 프로그래밍을 당연한 기본으로 삼고, 함수형 프로그래밍 등 다양한 패러다임을 지원하며 코드의 안정성과 표현력을 높이는 언어들이다.
구조적 프로그래밍의 설계
프로그램 설계는 ‘요구사항을 코드로 구현하기 전에 문제 해결 방안을 계획하고 명세화하는 과정’이다. 프로그램뿐만 아니라 제작을 하는 모든 일은 설계(디자인)를 기반으로 이루 어진다.
구조적 프로그래밍 구조
구조적 프로그래밍은 1960년대 후반, 무분별한 GOTO문의 사용으로 인해 코드가 스파게티처럼 얽혀 해독과 유지보수가 거의 불가능해지는 ‘스파게티 코드(Spaghetti Code)’ 문제를 해결하기 위해 등장한 프로그래밍 방법론이다.
선택(Selection): 특정 조건의 참/거짓에 따라 두 개 이상의 갈림길 중 하나를 선택하여 실
행하는 구조이다. (if-then-else, switch-case 등)
반복(Repetition/Iteration): 특정 조건을 만족하는 동안 정해진 코드 블록을 되풀이하여 실
행하는 구조이다. (while, for, do-while 등)
구조적 프로그래밍 설계 절차
구조적 프로그래밍은 하향식 설계(Top-Down Design) 또는 단계적 세분화(Stepwise Refinement)라는 절차를 통해 설계된다.

구조적 프로그래밍 언어 개요
구조적 프로그래밍 언어란 1960년 이전의 초창기 언어들이 GOTO문을 사용하여 프로그 램의 실행 흐름을 자유롭게 점프하여 코드가 서로 얽히는 문제를 해결하기 위해 등장한 프로그래밍 방법론이다.
선택(Selection): 특정 조건의 참/거짓에 따라 두 개 이상의 갈림길 중 하나를 선택하여 실
행하는 구조이다. (if-then-else, switch-case 등)
반복(Repetition/Iteration): 특정 조건을 만족하는 동안 정해진 코드 블록을 되풀이하여 실
행하는 구조이다. (while, for, do-while 등)
서브 루틴 또는 함수의 지원
서브 루틴 또는 함수는 특정 작업을 수행하는 독립된 단위로 호출과 함께 동작하며, 종료 시 호출된 곳으로 제어가 돌아간다.
코드 블럭
코드 블록은 여러 개의 명령문(statements)을 하나의 논리적인 단위로 묶는 기능이다. C, Java, C++ 등에서는 중괄호 { }를 사용하여 코드 블록을 표현하며, 파이썬(Python) 에서는 들여쓰기(indentation) 자체가 코드 블록 기능을 갖는다.
GOTO문 사용 배제
구조적 프로그래밍 기법이 ‘GOTO문 사용 배제’를 목표로 나온 것이므로, 현재의 대부 분의 프로그래밍 언어는 goto 명령어가 제공되어도 실제로 동작하지 않거나, 키워드로서 배제하였다.
구조적 프로그래밍 절차와 오류
프로그래밍 중에 예기치 않은 상황이 발생하며, 이를 오류라 부른다. 오류는 설계를 검토하는 과정에서 논리적인 부분으로 발견되기도 하며, 프로그래밍 후 컴파일 중에 발견되기
프로그래밍 절차
프로그램은 [그림 1-4]와 같은 절차에 의해 개발된다.
번역 방식
우리가 사용하는 C언어, Java, Python 등은 고급 언어로서 컴퓨터가 동작하기 위해서는 기계어로 번역되어야 한다.
예약어(키워드)를 변수 이름으로 사용하려는 경우 등
코드가 문법적으로는 이상이 없으므로 컴파일은 성공하였지만, 프로그램이 실행되는 도중에 예기치 않은 문제로 인해 더 이상 진행하지 못하고 비정상적으로 종료되는 경우이다.
0으로 나누기: 특정 변수의 값이 0이 된 상태에서 그 변수로 다른 숫자를
나누려고 할 때
배열 인덱스 초과: 크기가 5인 배열(인덱스 0~4)의 5번째 인덱스
(array[5])에 접근하려고 할 때
널 포인터 참조(Null Pointer Exception): 객체가 메모리에 생성되지 않
아 null 상태인데, 이 객체의 메서드나 속성을 사용하려고 할 때
스택 오버플로(Stack Overflow): 함수가 자기 자신을 무한히 호출(무한
재귀)하여 메모리가 가득 찰 때 런타임 오류 중 번역 중에 오류가 없으며 실행 중 비정상적으로 종료되지도 않지만, 프로그래머가 의도한 것과 전혀 다른 또는 잘못된 결과를 내놓는 경우이다.
할인율을 계산할 때, 곱해야 할 것을 나누거나 더해야 할 것을 빼는 등
계산식이 잘못된 경우
반복문이 10번 실행되어야 하는데, 조건식을 잘못 써서 9번만 실행되거나
11번 실행되는 경우 (Off-by-one 오류)
if 조건문에서 '이상(>=)'을 써야 할 곳에 '초과(>)'를 써서 경곗값이 잘못
처리되는 경우
디버깅(Debugging)
디버깅은 프로그램에 문법, 런타임, 논리 오류를 수정하는 작업으로 다음과 같은 방법을 사용한다. 컴파일 오류, 런타임 오류
런타임 오류의 경우, '호출 스택(Call Stack)' 정보를 통해 어떤 함수가 어떤
함수를 호출하다가 오류가 났는지 그 경로를 추적 주로 논리 오류
오류가 발생할 것으로 의심되는 부분의 앞, 뒤, 중간에 print()나 log()를 사용
하여 문장의 실행 여부나 변수의 값을 추적
특정 변수의 값이 어떻게 변하는지를 직접 눈으로 확인하는 원시적이지만 매우
효과적인 방법이다. 런타임 오류, 논리 오류
중단점 (Breakpoint): 실행을 멈추고 싶은 코드 라인에 빨간 점을 찍어 프로
그램을 해당 위치에서 일시 정지시킴
단계별 실행 (Step-by-step Execution): 프로그램이 멈춘 상태에서, 코드를
한 줄씩 실행(Step Over), 함수 안으로 들어가기(Step Into), 함수 밖으로 나가기(Step Out) 등을 통해 실행 흐름을 정밀하게 제어
변수 조사 (Variable Inspection): 프로그램이 멈춘 시점의 모든 변수들의 값
을 실시간으로 확인할 수 있다. print문을 일일이 넣지 않아도 변수의 변화 추주로 논리 오류
동료 검토(Peer Review): 동료 개발자에게 코드를 보여주고 설명하면서 함께
오류를 찾아내는 코드 리뷰 기법
러버덕 디버깅(Rubber Duck Debugging): 동료가 없어도, 마치 옆에 있는
오리 인형에게 내 코드가 어떻게 동작하는지 한 줄 한 줄 말로 설명하다 보면 스스로 논리의 모순점을 깨닫게 되는 방법 오류 예방 및 조기 발견
프로그램 전체가 아닌, 가장 작은 단위인 함수(모듈) 하나하나가 올바르게 동작
하는지를 검증하는 테스트 코드를 미리 작성해 두는 방법
새로운 기능을 추가하거나 코드를 수정한 후, 기존에 통과했던 단위 테스트가
실패한다면 문제의 원인을 쉽게 발견할 수 있음
버그를 사전에 예방하고, 발생 시 신속하게 해결할 수 있음

알아야 할 것

객체지향 프로그래밍의 개념
객체지향 프로그래밍(OOP: Object-Oriented Programming)은 컴퓨터 프로그램을 명령 어의 목록으로 보는 시각에서 벗어나, 여러 개의 독립된 단위, 즉 ‘객체(Object)’들을 중심으로 프로그램을 구현하는 프로그래밍의 한 패러다임이다.
기본 개념
클래스는 객체를 만들기 위한 설계로, 클래스로 선언될 객체가 어떤 데이터(속성)를 가지고, 어떤 행동(기능)을 할 수 있는지 정의한다.
객체지향 속성
캡슐화는 객체의 속성과 행위를 하나로 묶고, 실제 구현 내용 일부를 외부에 감추어 은닉하는 기법이다. 외부 객체는 객체 내부의 구조를 알지 못하게 하고, 내부 객체에서 제어하여 제공하는 필드와 메서드만 이용할 수 있다.
객체지향 설계 원칙
모든 클래스는 각각 하나의 책임만 가져야 한다. 클래스는 그 책임을 완전히 캡슐화해야 함을 말한다. 확장에는 열려 있고 수정에는 닫혀 있어 기존의 코드를 변경하지 않고(Closed), 기능을 추가할 수 있도록(Open) 설계가 되어야 한다는 원칙을 말한다.
UML(Unified Modeling Language)의 이해
객체지향 개념에서 UML을 한마디로 정의하면, 소프트웨어를 만들기 위한 ‘표준 설계도’이 다. 집을 짓기 전에 건축 설계도를 먼저 그리는 것처럼, 프로그램을 개발하기 전에 시스템의 구조와 흐름을 그림(다이어그램)으로 표현하여 전체적인 모습을 파악하고 설계하기 위한 시각적인 언어(Modeling Language)이다.
유스케이스 다이어그램(Use Case Diagram)
요구 분석, 시스템 설계, 시스템 구현 등의 시스템 개발 과정에서, 개발자 간의 의사소 통이 원활하게 이루어지도록 표준화한 대표적인 객체지향 모델링 언어이다.
클래스 다이어그램(Class Diagram)
클래스 다이어그램은 UML의 구조 다이어그램으로서 클래스 내부 구성 요소 및 클래스 간의 관계를 도식화하여 시스템의 특정 모듈이나 일부 또는 전체 구조를 나타낸다.
시퀀스다이어그램
문제 해결을 위한 객체를 정의하고 객체 간의 상호작용 메시지 시퀀스를 시간의 흐름에 따라 나타내는 다이어그램이다.

  2. 중단점을 설정한다.
  3. 단계별로 코드를 실행한다.
  4. 콘솔에서 테스트한다.
  5. 소스를 수정한다.

스스로 확인

  • 화면을 구현한다.
  • 스크립트 언어로 개발한다.
  • 디버깅으로 오류를 확인한다.
  • 스크립트 언어를 활용하여 애플리케이션을 작성할 수 있다.
  • 작성된 애플리케이션의 오류를 식별하고 수정할 수 있다.

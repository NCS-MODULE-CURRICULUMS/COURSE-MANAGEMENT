형상관리의 정의
형상관리(SCM: Software Configuration Management)란 소프트웨어의 개발 과정에서 발생하는 산출물의 변경 사항을 버전관리하기 위한 일련의 활동으로, 다음과 같은 특성이 있다.
형상관리 절차
형상관리는 품질 보증을 위한 중요한 요소로서 다음과 같은 절차를 통해 수행된다. (가) 형상관리 대상을 식별하여 이름과 관리 번호를 부여하고, 계층(Tree) 구조로 구분하여 수정 및 추적이 용이하도록 하는 작업으로 베이스라인의 기준을 정하는 활동이다.
형상관리 구성
형상관리는 기준선(Baseline), 형상 항목(Configuration Item), 형상 버전(Configurat ion Version), 형상 제품(Configuration Product)으로 구성된다.
소스코드 관리도구 유형

알아야 할 것

소스코드 관리 지침
소스코드 관리 지침은 소스코드 관리를 위해 역할별로 준수해야 할 내용이 기록된 지침
소스코드 관리 지침의 목적
소스코드 관리 지침의 목적은 소스코드의 생성, 변경, 삭제 등 소스코드의 안전한 관리를 위해 준수하여야 할 관리 방법을 정의함으로써 소스코드의 변경 사항 추적, 오류 복구, 복원, 백업 등 정보 자산을 보호하는 데 있다.
소스코드 관리 지침의 구성
소스코드 관리 지침의 구성은 소스코드 관리 지침의 목적, 적용 범위, 역할 및 책임, 소스코드 분류 체계, 소스코드 변경관리 방법 등의 내용으로 구성되어 있다.
소프트웨어 버전 작성(Software Versioning)
소프트웨어 버전은 단순히 숫자를 나열하는 것이 아니라, 사용자와 개발자 간의 중요한 소통 수단이다. 버전 번호를 통해 소프트웨어의 변경 이력, 호환성 여부, 새로운 기능 추가, 버그 수정 등을 명확하게 전달할 수 있다.
소프트웨어 버전 작성 방법
유의적 버전(SemVer)의 핵심 규칙은 ‘MAJOR. MINOR. PATCH’ 세 부분으로 구성된 숫자 조합을 사용한다.
소프트웨어 버전 작성 규칙
소프트웨어 버전은 다음 규칙에 따라 변경한다. 상위 버전이 올라가면, 하위 버번은 0 으로 초기화해야 한다.
정식 출시 전 버전 (Pre-release)
소프트웨어 버전 1.0.0은 첫 번째 정식 버전을 의미한다. 그 이전까지는 초기 개발 단계임을 나타내기 위해 MAJOR 버전을 0으로 사용한다.
빌드 메타데이터(Build Metadata)
버전 번호 뒤에 플러스(+) 기호를 붙여 빌드 정보를 추가할 수 있다. 이 정보는 버전 우선순위에 영향을 주지 않는다.
1.2.3-beta+build.1024.a9c3e1f
의존성 관리 시스템은 + 뒤의 정보를 무시한다. 즉, 1.0.0과 1.0.0+build.123은 같은 버전으로 취급한다.

알아야 할 것

백업의 개념과 필요성
소프트웨어 개발 환경을 안정적으로 운영하고 예기치 않은 사고로부터 보호하기 위해서는 백업과 복원(복구)은 필수적이다.
백업(Backup)
백업은 특정 시점의 데이터 또는 시스템의 상태를 그대로 복사하여 별도의 저장 매체에 보관하는 행위 또는 그 결과물(복사본)을 의미한다.
복원(Restore)
복원은 백업해 둔 데이터 사본을 사용하여 특정 시점의 상태로 시스템이나 데이터를 되돌리는 과정을 의미한다. 백업의 궁극적인 목표는 성공적인 복구를 통해 서비스를 신속하게 정상화하는 것이다.
백업의 필요성
개발 환경은 수많은 시간과 노력이 투입된 결과이다. 이러한 개발 환경이 손실될 경우, 그 피해는 단순한 데이터 유실을 넘어 프로젝트 전체의 실패로 이어질 수 있다.
백업 대상의 식별과 유형
성공적인 복원을 위해서는 개발 환경을 구성하는 모든 핵심 요소를 빠짐없이 백업해야 한다. 또 백업의 효율성과 안정성을 높이려면 무엇을 백업할지를 명확히 구분해야 한다.
백업 대상
백업의 목적은 문제 상황 시 원래 상태로 완전한 복구가 이루어지는 것이다. 따라서 일부만 백업하는 것은 의미가 없다.
SSL 인증서 파일
개발 환경 속에서 동작하는 프로그램들은 수많은 외부 라이브러리나 패키지와 함께 동작한다. 따라서 프로그램 동작에 필요한 라이브러리나 패키지도 함께 백업해 둘필요가 있다.
의존성 패키지 목록을 정의한 매니페스트 파일
(package.json, requirements.txt, pom.xml,build.gradle)
단점: 용량이 매우 크고 OS에 따라 호환성 문제가 발생할 가능성 있음
응용소프트웨어 개발과 운영을 자동화하는 데 사용되는 모든 스크립트와 사용자가 업로드한 파일 등도 중요한 백업 대상이다.
CI/CD(지속적 통합/배포) 파이프라인 스크립트
(예: Jenkinsfile, .github/workflows/*.yml)
백업 유형
데이터의 양, 복구 시간의 중요도, 저장 공간의 한계 등을 고려하여 가장 적합한 백업 전략을 선택해야 한다.

백업 도구 및 기술
(가) 압축 도구 (‘tar’, ‘zip’) - 여러 파일과 디렉터리를 하나의 아카이브 파일로 묶어 관리 (나) 파일 동기화 도구 (‘rsync’, ‘Robocopy’) - 원본과 대상 디렉터리를 비교하여 변경된 파일만 복사하므로, 빠르고 효율적 인 파일 단위 백업 가능 버전관리 시스템은 파일의 변경 이력을 시간 순서대로 기록하고 관리하는 시스템이 다.
유연성 및 이식성
- 파일이 텍스트 기반이므로 사람이 읽고 수정 용이 - 다른 버전 또는 다른 종류의 DBMS로 데이터 이전(마이그레이션) 용이 (예: MySQL → PostgreSQL 마이그레이션)
늦은 처리 속도 : 대용량 데이터베이스의 경우, 데이터를 텍스트로 변환하고
다시 불러오는 과정에서 많은 시간이 소요될 수 있음 (나) 물리적 백업 물리적 백업은 데이터베이스를 구성하는 데이터 파일, 로그 파일 등 디스크에 저 장된 파일 자체를 그대로 복사하는 방식이다.
빠른 처리 속도
파일 시스템 수준에서 대용량 데이터를 빠르게 복사하므로 백업과 복원 속도가 매우 빠름
이식성 제한
: 동일한 버전과 아키텍처를 가진 DBMS 환경에서만 복원이 가능함
유연성 부족
전체 데이터베이스 단위로만 복원이 가능하며, 특정 테이블만 선택하는 등의 세부적인 제어가 어려움가상 머신(VMware, VirtualBox)이나 클라우드 환경(AWS, Google Cloud)에서 주로 사용된다.
백업 주기
‘얼마나 자주 백업할 것인가?’와 ‘어디에 보관할 것인가?’는 비즈니스의 요구사항에 따라 결정된다. 이를 위해 복구 목표 시점(RPO: Recovery Point Objective)과 복구 목표 시간(RTO: Recovery Time Objective)라는 개념이 사용된다.

복원(Restore)의 개념과 필요성
복원은 백업된 데이터나 파일의 ‘사본’을 원래의 위치나 새로운 위치에 그대로 가져다 놓는 것이다. 복원하는 방법은 백업한 tar 압축을 풀거나, Git 저장소를 clone 받거나, 데이 터베이스 덤프 파일을 임포트 하는 등의 기술적인 작업으로 구현된다.

소스코드 복원

데이터베이스 복원
mysqldump나 expdp로 생성된 .sql 또는 .dmp 파일을 다시 데이터베이스에 적용하여 데이터를 재구성하는 방식이다.
서버 환경 및 설정 복원
서버 환경 및 설정 복원은 대부분 백업해 둔 설정 파일을 원래의 위치에 덮어쓰는 방식으로 진행된다. (가) Tomcat의 server.xml, context.xml 파일들을 [TOMCAT_HOME]/conf/ 폴더에 복사하거나 덮어쓴다.

업무 담당자는 복원 계획을 확인한다. · 업무 담당자는 복원 계획에 따른 복원 대상을 점검한다. · 업무 담당자와 업무 팀장은 서비스의 상태를 확인한다. · 정상적일 때 서비스의 정상 상태 결과를 유관 부서에 공유한다.

0. 제출물의 구성과 배점

이미 있는 시스템을 조사하고, 더할 기능을 그림과 표로 정리합니다.

제출 형식

PPT 한 파일

참고

작업지시서

이 교과의 제출물은 네 가지를 한 파일에 담은 PPT 한 벌입니다. 앞의 세 교과와 달리 새로 만드는 화면이 없습니다. 이미 만들어져 있는 시스템을 받아, 그것을 조사하고 무엇을 더할지 정리하는 일입니다.

과제만들어야 할 것 확인하는 것배점
1현행 시스템 조사 운행환경 · 기능 · 문제점 · 목표 시스템25
2유스케이스 다이어그램과 명세서 액터 · 목록 · 표기법 · 명세서 · 현행과의 일치25
3시퀀스 다이어그램 객체 · 순서 · 동기와 비동기 · 프래그먼트 · 표기법 50
4API 명세서 엔드포인트 · 요청 · 응답 · 형식 통합 · 구체성

평가방법이 평가자 체크리스트 입니다. 채점 항목 20개를 하나씩 보며 있으면 5점, 없으면 0점으로 매깁니다. 부분 점수가 없습니다. 스무 칸을 모두 채우는 것이 이 교과의 목표입니다.

배점의 절반이 과제 3과 4에 몰려 있습니다. 과제 1의 조사에 시간을 다 쓰고 시퀀스와 API 를 서둘러 만들면 50점을 잃습니다. 조사는 주어진 파일을 읽어 옮기는 일이므로 오래 걸리지 않습니다.

1. 요구사항 확인의 범위

만드는 사람이 아니라 받아 읽는 사람의 일입니다.

능력단위요소

현행 시스템 분석하기 · 요구사항 확인하기 · 분석모델 확인하기

교과목

데이터베이스 구축

이 능력단위의 수행준거는 거의 모두 「업무 분석가가 …한 것을 확인할 수 있다」 로 끝납니다. 요구사항을 처음부터 만들어 내는 일이 아니라, 남이 정리해 온 것을 받아 그대로 만들 수 있는지 따져 보는 일입니다.

현행 시스템 분석하기
지금 돌아가고 있는 시스템이 무엇 위에 올라가 있는지 조사합니다. 운영체제 · DBMS · 미들웨어 · 언어 · 형상관리 · 망 구성입니다. 이것을 모르면 무엇을 바꿀 수 있고 무엇을 바꿀 수 없는지 판단할 수 없습니다.
요구사항 확인하기
더할 기능이 정말 그대로 만들 수 있는 것인지 따져 봅니다. 유스케이스로 옮겨 보면 빠진 것과 어긋난 것이 드러납니다.
분석모델 확인하기
기능이 실제로 어떤 순서로 돌아가는지(시퀀스), 그리고 어떤 통로로 주고받는지(API)를 정리합니다. 여기까지 나와야 개발자가 받아서 만들 수 있습니다.

1.1 현행 시스템 분석의 개념

학습 목표운행환경 조사 항목 일곱 가지를 설명할 수 있다.
자신의 PC 를 대상으로 조사를 수행하고 조사표를 작성할 수 있다.

현행 시스템 분석이란 새로운 기능을 추가하기에 앞서, 이미 운영 중인 시스템이 어떤 환경 위에서 동작하고 있는지를 조사하여 문서로 정리하는 작업을 말합니다. 운영체제, 데이터베이스, 개발 언어, 망 구성 등이 조사 대상입니다.

이 작업이 필요한 이유는 분명합니다. 기존 시스템의 환경을 알지 못하면 어떤 기능을 추가할 수 있고 어떤 기능은 추가할 수 없는지 판단할 수 없기 때문입니다. 비유하자면 이사를 앞두고 지금 사는 집의 구조를 먼저 확인하는 것과 같습니다. 방의 개수와 전기 용량을 알아야 어떤 가구를 옮길 수 있는지 정할 수 있습니다.

참고 — 이 능력단위의 수행준거는 「업무 분석가가 분석한 것을 확인할 수 있다」로 서술되어 있습니다. 요구사항을 새로 만들어 내는 작업이 아니라, 전달받은 내용이 구현 가능한지를 검토하는 작업입니다.

1.2 조사 항목

운행환경 조사표는 일곱 개 항목으로 구성됩니다. 이 일곱 줄이 채점 항목 ① 01 ~ 05 에 대응하며 배점은 25점입니다. 각 항목의 의미와 확인 방법은 다음 표와 같습니다. 확인 방법은 Windows 환경을 기준으로 정리하였습니다.

조사 항목의미 예확인 방법
운영체제
OS		 컴퓨터의 자원을 관리하고 응용 프로그램의 실행 환경을 제공하는 소프트웨어 Linux (CentOS 7) ⊞ + R 을 누른 뒤 winver 입력
데이터베이스
DBMS		 데이터를 저장하고 검색·변경할 수 있도록 관리하는 소프트웨어 MySQL 5.7 명령 프롬프트에서 mysql --version
미들웨어
WAS		 웹 요청을 받아 서블릿 등 프로그램을 실행하고 결과를 반환하는 서버 Apache Tomcat 8.5 브라우저에서 localhost:8080 접속
사용 언어 응용 프로그램을 작성한 언어. 프레임워크가 있으면 함께 적는다 Java 서블릿, JSP 기반 java -version
IDE 소스 코드를 작성하고 실행·디버깅하는 개발 도구 이클립스, 인텔리제이 설치된 프로그램 목록에서 확인
형상 관리 도구 소스 코드의 변경 이력을 기록하고 이전 상태로 되돌릴 수 있게 하는 도구 Git / GitHub git --version
네트워크 환경 망 구성과 보안 장비. 없으면 없다고 적는다 내부망, 방화벽 없음 ipconfig
주의 — 종류만 적고 판(버전)을 빼면 감점됩니다. 「MySQL」이 아니라 「MySQL 5.7」이라고 적습니다. 해당 장비나 도구가 없는 경우에는 빈칸으로 두지 말고 「없음」이라고 적습니다.
용어 — WAS(Web Application Server)는 웹 서버와 달리 프로그램을 실행합니다. 포트는 하나의 컴퓨터에서 여러 프로그램을 구분하기 위한 번호이며, Tomcat 은 8080, MySQL 은 3306 을 기본값으로 사용합니다.

1.3 시스템의 계층 구조

여섯 개 항목은 서로 독립적이지 않습니다. 아래 계층이 위 계층을 받치는 구조이며, 아래 계층이 동작하지 않으면 위 계층도 동작하지 않습니다. 따라서 조사 역시 상위 계층에서 하위 계층으로 내려가며 수행합니다.

같은 내용을 draw.io 로 작성하면 다음과 같습니다. [실습 1-2] 에서 직접 작성하게 되며, 조사 결과를 상자 안에 기입하는 방식입니다.

1.4 실습 환경

별도로 설치할 프로그램은 없습니다. 실습에는 다음 환경을 사용합니다.

운영체제Windows 10 이상 명령 프롬프트⊞ + R → cmd 입력 → Enter 문서 작성Excel, 한셀, Google 스프레드시트 중 하나 다이어그램app.diagrams.net (설치 및 회원 가입 불필요) 화면 캡처⊞ + Shift + S
실습 1-1 자신의 PC 를 대상으로 현행 시스템 조사하기

목적 — 조사 항목 여섯 가지를 실제 환경에서 확인하는 절차를 익힙니다. 조사 대상은 평가에서 제공되는 시스템이지만, 절차를 익히기 위해 먼저 자신의 PC 를 대상으로 수행합니다.

준비물 — PC, 명령 프롬프트, 스프레드시트

절차 1. 명령 프롬프트 실행
⊞ + R 을 누르고 cmd 를 입력한 뒤 Enter 를 누릅니다. 아래와 같은 검은 창이 열립니다.

Microsoft Windows [Version 10.0.26200.9457] (c) Microsoft Corporation. All rights reserved. C:\Users\hong>_

절차 2. 운영체제 확인
ver 을 입력합니다. 출력된 버전을 조사표의 「운영체제」 항목에 기록합니다.

C:\Users\hong>ver Microsoft Windows [Version 10.0.26200.9457]

절차 3. 개발 언어 확인
Java, Python, Node.js 의 설치 여부와 버전을 차례로 확인합니다. 버전 번호가 출력되면 설치된 상태입니다.

C:\Users\hong>java -version openjdk version "21.0.2" 2024-01-16 OpenJDK Runtime Environment (build 21.0.2+13-58) OpenJDK 64-Bit Server VM (build 21.0.2+13-58, mixed mode, sharing) C:\Users\hong>python --version Python 3.12.10 C:\Users\hong>node --version v24.11.1

C:\Users\hong>git --version git version 2.52.0.windows.1

절차 5. DBMS 확인
출력에 제품명과 버전, 그리고 라이선스 표기가 함께 나타납니다. 라이선스 표기는 소프트웨어 구성표를 작성할 때 사용합니다.

C:\Users\hong>mysql --version mysql Ver 8.0.44 for Win64 on x86_64 (MySQL Community Server - GPL)

절차 6. 네트워크 구성 확인
출력 결과 중 「IPv4 주소」 한 줄을 조사표에 기록합니다.

C:\Users\hong>ipconfig Windows IP 구성 이더넷 어댑터 이더넷: 연결별 DNS 접미사. . . . : IPv4 주소 . . . . . . . . : 192.168.0.25 서브넷 마스크 . . . . . . : 255.255.255.0 기본 게이트웨이 . . . . . : 192.168.0.1

결과 확인 — 설치되지 않은 소프트웨어를 조회하면 다음과 같이 출력됩니다. 이 경우 조사표에는 「설치되지 않음」이라고 기록합니다. 항목을 비워 두지 않는 것이 원칙입니다.

C:\Users\hong>oracle --version 'oracle'은(는) 내부 또는 외부 명령, 실행할 수 있는 프로그램, 또는 배치 파일이 아닙니다.

마지막으로 ⊞ + Shift + S 로 명령 프롬프트 화면을 캡처하여 조사표 아래에 첨부합니다.

1.5 조사표 작성

조사 결과는 다음과 같은 형식으로 정리하여 제출합니다. 실제 평가에서 제공되는 도서 대여 시스템을 조사한 예입니다. 일곱 줄이 모두 채워져야 하며, 각 줄이 채점 항목에 대응합니다.

생각해 보기 — 조사표를 채우는 것으로 끝내지 말고, 각 줄에서 무엇이 가능하고 무엇이 불가능해지는지를 함께 생각해 봅니다. 예를 들어 DBMS 가 MySQL 5.7 이면 Oracle 전용 함수를 쓸 수 없고, 네트워크가 내부망이면 외부 API 를 호출할 수 없습니다. 이 판단이 이후 「요구사항 확인」과 「분석모델 확인」의 근거가 됩니다.
실습 1-2 현행 시스템 조사표 및 구성도 작성하기

목적 — 조사 결과를 문서와 다이어그램으로 산출합니다.

절차

  1. 스프레드시트를 실행하고 [그림 1-3] 과 같이 「구분 / 조사 결과 / 적는 요령」 세 개의 열을 작성합니다.
  2. 운영체제, 데이터베이스, 미들웨어, 사용 언어, IDE, 형상 관리 도구, 네트워크 환경의 일곱 행을 만듭니다.
  3. 「조사 결과」 열을 채웁니다. 평가에서 제공된 현행 시스템 파일을 사용하며, 연습 단계에서는 실습 1-1 에서 조사한 자신의 PC 값을 사용합니다.
  4. 종류와 함께 판(버전)을 반드시 적습니다. 해당 사항이 없으면 「없음」이라고 적고 빈칸으로 두지 않습니다.
  5. app.diagrams.net 에 접속합니다. 저장 위치를 묻는 창이 나타나면 Device 를 선택하고, Create New Diagram → Blank Diagram 을 차례로 누릅니다. 파일 이름은 as-is_architecture.drawio 로 지정합니다.
  6. 왼쪽 도형 목록에서 사각형을 끌어다 다섯 개를 세로로 배치합니다. 도형을 더블클릭하면 글자를 입력할 수 있습니다. [그림 1-2] 와 같은 형태가 되도록 조사 결과를 기입합니다.
  7. 도형 가장자리에 마우스를 올리면 나타나는 파란 화살표를 아래 도형으로 끌어 연결선을 만듭니다.
  8. File → Export as → PNG 를 선택하고 Zoom 을 200% 로 지정하여 내보냅니다.

제출물 — 현행 시스템 조사표 1부, 계층 구성도 .drawio 원본 및 PNG 각 1부

정리 현행 시스템 분석은 운영체제 · 데이터베이스 · 미들웨어 · 사용 언어 · IDE · 형상 관리 도구 · 네트워크 환경의 일곱 항목을 조사하는 작업입니다. 조사 결과에는 종류와 판(버전)을 함께 적으며, 일곱 줄이 그대로 채점 항목 ① 01 ~ 05 의 25점에 대응합니다.

네 산출물은 앞의 것이 뒤의 것의 재료가 됩니다. 조사표에서 유스케이스가 나오고, 유스케이스의 기본 흐름에서 시퀀스가 나오고, 시퀀스의 메시지에서 API 가 나옵니다. 순서를 건너뛰면 뒤에서 지어내게 됩니다.

2. 산출물 작성 실습

레벨 1부터 5까지 따라가면 네 산출물이 완성됩니다.

시간

레벨 3과 4에 몰아 씁니다

예제

도서 대여 시스템

다섯 단계로 나누었습니다. 예제는 평가도구의 작업지시서에 실린 것을 그대로 씁니다. 이미 있는 도서 관리 시스템(등록 · 수정 · 삭제 · 조회)에 유저 인증과 도서 대여 두 가지를 더하는 경우입니다.

실제 평가에서는 현행 시스템 파일이 제공됩니다. 그 파일을 열어 조사하는 것이 첫 단계이므로, 이 교안의 조사 결과와 숫자가 다를 수 있습니다. 절차는 같습니다.

기능 조사

소스를 열어 지금 무엇이 되는지 적습니다. 화면과 메뉴를 훑고, 컨트롤러나 서블릿의 이름을 보면 기능 목록이 나옵니다.

문제점은 없는 기능으로 적습니다. 「불편하다」 「느리다」 같은 느낌이 아니라 무엇이 없는지를 적어야 그것이 그대로 요구사항이 됩니다.

약함 보안이 취약함

권함 인증 기능 부재 — 누구나 도서를 등록 · 삭제할 수 있음

아래처럼 적으면 「유저 인증 기능 추가」 라는 요구사항이 그대로 따라 나옵니다. 문제점 하나에 요구사항 하나가 대응하게 만드는 것이 이 단계의 목표입니다.

확인
  1. 문제점 칸의 줄 수와 요구사항 칸의 줄 수가 같습니까.
  2. 요구사항 가운데 현행 조사에 나오지 않은 것을 전제로 하는 것이 있습니까.
  3. 주요 모듈 칸에 적은 라이브러리가 실제 프로젝트에 들어 있습니까.

근거

수행준거 1.3

목표 시스템 표

현행을 조사했으면 앞으로 어떻게 할 것인지를 적습니다. 수행준거 1.3 이 「명확하고 구체적으로 기술할 수 있다」 로 되어 있습니다. 구체적이라는 말은 제품 이름과 판이 적혀 있다는 뜻입니다.

바꾸지 않기로 하는 것도 결정입니다

모든 칸을 「전환」 으로 채울 필요가 없습니다. 데이터베이스를 그대로 쓰기로 했다면 「MySQL 을 그대로 사용」 이라고 적고 그 이유를 「데이터 이관 비용이 크고 현행 구조로 요구사항을 모두 담을 수 있음」 처럼 적습니다.

바꾸는 쪽을 택했다면 왜 지금인지를 적습니다. 「최신이라서」 는 이유가 되지 않습니다. 「인증과 권한 관리를 직접 만들지 않고 쓰기 위해」 처럼 이번 요구사항과 이어야 설득이 됩니다.

해 보기 목표 시스템 표를 다 쓴 뒤 요구사항 두 줄을 다시 읽어 보십시오. 요구사항을 만들기 위해 필요한 것이 목표 시스템에 빠짐없이 들어 있어야 합니다. 인증을 더한다면 인증을 무엇으로 할지가 표에 있어야 합니다.

사전조건과 사후조건

두 칸을 헷갈리는 경우가 많습니다. 기준은 시점입니다.

사전조건 — 시작하기 전에 참이어야 하는 것
「회원이 로그인한 상태이고, 도서 상태가 대여 가능이다」 처럼 상태로 적습니다. 「회원이 로그인한다」 는 동작이므로 사전조건이 아닙니다.
사후조건 — 끝난 뒤에 달라져 있는 것
「대여 신청이 승인 대기로 저장되고 관리자 목록에 나타난다」 처럼 무엇이 바뀌었는지를 적습니다. 화면에 무엇이 보이는지가 아니라 데이터가 어떻게 되었는지를 적는 것이 낫습니다.

기본 흐름의 번호

기본 흐름은 번호를 붙인 문장으로 적습니다. 이 번호가 다음 단계에서 시퀀스 다이어그램의 메시지 번호가 됩니다. 번호가 없으면 시퀀스를 그릴 때 순서를 다시 정해야 하고, 그러면 둘이 어긋납니다.

채점 항목 ② 10 이 「명세서 내용이 현행 시스템의 실제 기능과 일치하는가」 입니다. 조사하지 않은 기능을 흐름에 적으면 여기서 걸립니다. 이를테면 현행에 알림 기능이 없는데 「대여 신청 시 문자를 보낸다」 고 적는 경우입니다.

시퀀스에서 액터가 컨트롤러로 보내는 화살표가 API 한 건이 됩니다. 대여 요청 시퀀스의 1번 메시지가 POST /rentals 입니다. 유스케이스 하나에 API 한둘이 나옵니다.

URL 을 정하는 규칙

규칙을 하나 정해 두고 끝까지 지킵니다. 가장 무난한 것은 자원을 명사 복수로 쓰는 방식입니다.

하는 일메서드 URL비고
목록 조회GET/books검색은 질의 문자열로

만들기POST/books—
일부 고치기PATCH/rentals/{id}/approve 상태를 바꾸는 동작

권함 GET /books · POST /rentals — 동작은 메서드가 나타냅니다

채점 항목 ③ 16 이 「추가 기능에 해당하는 엔드포인트가 빠짐없이 정의되었는가」 입니다. 유스케이스 목록의 추가 기능마다 API 가 하나 이상 있어야 합니다. 대여 승인과 반납 처리처럼 관리자만 쓰는 것도 빠뜨리지 않습니다.

상태 코드 고르기

채점 항목 ③ 18 이 「응답 형식 및 상태 코드가 구체적으로 명시되었는가」 입니다. 성공만 적으면 구체적이라고 보기 어렵습니다. 실패했을 때 무엇이 오는지까지 적습니다.

코드뜻이 예제에서 쓸 자리
200잘 됐다조회 · 승인
201새로 만들었다회원가입 · 대여 신청 · 도서 등록
204됐는데 돌려줄 내용이 없다로그아웃
400보낸 값이 잘못됐다필수 항목 누락
401로그인하지 않았다대여 신청 · 반납 요청
403로그인했지만 권한이 없다회원이 대여 승인을 시도
404그런 것이 없다없는 도서 번호
409지금 상태와 부딪친다중복 아이디 · 이미 대여 중

여덟 개를 다 쓸 필요는 없습니다. API 한 건에 성공 하나 + 실패 하나나 둘이면 됩니다. 요구사항 명세서의 검증 기준에 적어 둔 거절 상황이 곧 실패 코드가 됩니다.

채점 항목 ③ 19 가 「기존 시스템 API 와 일관된 형식으로 통합 작성되었는가」 입니다. 기존 기능을 표로, 추가 기능을 글로 적으면 둘을 견줄 수 없어 여기서 걸립니다.

현행을 그대로 두기로 했다면 목표 칸에 현행과 같은 주소를 적고 비고에 「현행 유지」 라고 적습니다. 칸을 비우지 않습니다.

구체적이라는 것의 기준

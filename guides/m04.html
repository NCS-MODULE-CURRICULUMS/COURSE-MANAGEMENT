0. 제출물의 구성과 배점

이미 있는 시스템을 조사하고, 더할 기능을 그림과 표로 정리합니다.

제출 형식

PPT 한 파일

참고

작업지시서

이 교과의 제출물은 네 가지를 한 파일에 담은 PPT 한 벌입니다. 앞의 세 교과와 달리 새로 만드는 화면이 없습니다. 이미 만들어져 있는 시스템을 받아, 그것을 조사하고 무엇을 더할지 정리하는 일입니다.

과제만들어야 할 것 확인하는 것배점
1현행 시스템 조사 운행환경 · 기능 · 문제점 · 목표 시스템25
2유스케이스 다이어그램과 명세서 액터 · 목록 · 표기법 · 명세서 · 현행과의 일치25
3시퀀스 다이어그램 객체 · 순서 · 동기와 비동기 · 프래그먼트 · 표기법 50
4API 명세서 엔드포인트 · 요청 · 응답 · 형식 통합 · 구체성

평가방법이 평가자 체크리스트 입니다. 채점 항목 20개를 하나씩 보며 있으면 5점, 없으면 0점으로 매깁니다. 부분 점수가 없습니다. 스무 칸을 모두 채우는 것이 이 교과의 목표입니다.

배점의 절반이 과제 3과 4에 몰려 있습니다. 과제 1의 조사에 시간을 다 쓰고 시퀀스와 API 를 서둘러 만들면 50점을 잃습니다. 조사는 주어진 파일을 읽어 옮기는 일이므로 오래 걸리지 않습니다.

1. 요구사항 확인의 범위

만드는 사람이 아니라 받아 읽는 사람의 일입니다.

능력단위요소

현행 시스템 분석하기 · 요구사항 확인하기 · 분석모델 확인하기

교과목

데이터베이스 구축

이 능력단위의 수행준거는 거의 모두 「업무 분석가가 …한 것을 확인할 수 있다」 로 끝납니다. 요구사항을 처음부터 만들어 내는 일이 아니라, 남이 정리해 온 것을 받아 그대로 만들 수 있는지 따져 보는 일입니다.

현행 시스템 분석하기
지금 돌아가고 있는 시스템이 무엇 위에 올라가 있는지 조사합니다. 운영체제 · DBMS · 미들웨어 · 언어 · 형상관리 · 망 구성입니다. 이것을 모르면 무엇을 바꿀 수 있고 무엇을 바꿀 수 없는지 판단할 수 없습니다.
요구사항 확인하기
더할 기능이 정말 그대로 만들 수 있는 것인지 따져 봅니다. 유스케이스로 옮겨 보면 빠진 것과 어긋난 것이 드러납니다.
분석모델 확인하기
기능이 실제로 어떤 순서로 돌아가는지(시퀀스), 그리고 어떤 통로로 주고받는지(API)를 정리합니다. 여기까지 나와야 개발자가 받아서 만들 수 있습니다.

1.1 현행 시스템 분석의 개념

학습 목표운행환경 조사 항목 일곱 가지를 설명할 수 있다.
자신의 PC 를 대상으로 조사를 수행하고 조사표를 작성할 수 있다.

현행 시스템 분석이란 새로운 기능을 추가하기에 앞서, 이미 운영 중인 시스템이 어떤 환경 위에서 동작하고 있는지를 조사하여 문서로 정리하는 작업을 말합니다. 운영체제, 데이터베이스, 개발 언어, 망 구성 등이 조사 대상입니다.

이 작업이 필요한 이유는 분명합니다. 기존 시스템의 환경을 알지 못하면 어떤 기능을 추가할 수 있고 어떤 기능은 추가할 수 없는지 판단할 수 없기 때문입니다. 비유하자면 이사를 앞두고 지금 사는 집의 구조를 먼저 확인하는 것과 같습니다. 방의 개수와 전기 용량을 알아야 어떤 가구를 옮길 수 있는지 정할 수 있습니다.

참고 — 이 능력단위의 수행준거는 「업무 분석가가 분석한 것을 확인할 수 있다」로 서술되어 있습니다. 요구사항을 새로 만들어 내는 작업이 아니라, 전달받은 내용이 구현 가능한지를 검토하는 작업입니다.

1.2 조사 항목

운행환경 조사표는 일곱 개 항목으로 구성됩니다. 이 일곱 줄이 채점 항목 ① 01 ~ 05 에 대응하며 배점은 25점입니다. 각 항목의 의미와 확인 방법은 다음 표와 같습니다. 확인 방법은 Windows 환경을 기준으로 정리하였습니다.

조사 항목의미 예확인 방법
운영체제
OS		 컴퓨터의 자원을 관리하고 응용 프로그램의 실행 환경을 제공하는 소프트웨어 Linux (CentOS 7) ⊞ + R 을 누른 뒤 winver 입력
데이터베이스
DBMS		 데이터를 저장하고 검색·변경할 수 있도록 관리하는 소프트웨어 MySQL 5.7 명령 프롬프트에서 mysql --version
미들웨어
WAS		 웹 요청을 받아 서블릿 등 프로그램을 실행하고 결과를 반환하는 서버 Apache Tomcat 8.5 브라우저에서 localhost:8080 접속
사용 언어 응용 프로그램을 작성한 언어. 프레임워크가 있으면 함께 적는다 Java 서블릿, JSP 기반 java -version
IDE 소스 코드를 작성하고 실행·디버깅하는 개발 도구 이클립스, 인텔리제이 설치된 프로그램 목록에서 확인
형상 관리 도구 소스 코드의 변경 이력을 기록하고 이전 상태로 되돌릴 수 있게 하는 도구 Git / GitHub git --version
네트워크 환경 망 구성과 보안 장비. 없으면 없다고 적는다 내부망, 방화벽 없음 ipconfig
주의 — 종류만 적고 판(버전)을 빼면 감점됩니다. 「MySQL」이 아니라 「MySQL 5.7」이라고 적습니다. 해당 장비나 도구가 없는 경우에는 빈칸으로 두지 말고 「없음」이라고 적습니다.
용어 — WAS(Web Application Server)는 웹 서버와 달리 프로그램을 실행합니다. 포트는 하나의 컴퓨터에서 여러 프로그램을 구분하기 위한 번호이며, Tomcat 은 8080, MySQL 은 3306 을 기본값으로 사용합니다.

1.3 실습 환경

조사 대상은 강사가 올려 둔 서버입니다. 훈련생 PC 에는 아무것도 설치하지 않습니다. Windows 10 · 11 에는 원격 접속 도구가 기본으로 들어 있으므로 주소와 포트만 받으면 바로 접속할 수 있습니다.

팀마다 서로 다른 환경이 배정됩니다. 조사 결과가 팀마다 다르므로 옆 팀의 답을 옮겨 적을 수 없고, 발표 때 비교할 거리가 생깁니다.

팀접속 포트 배정된 현행 시스템
A2201 오래된 자바 웹 — Tomcat 8.5 · Java 8 · MySQL 5.7
B2202 최신 자바 웹 — Tomcat 10.1 · Java 17 · MariaDB 10.6
C ~ E2203 ~ 수업 당일 강사가 안내합니다
접속 주소강사가 칠판에 적어 줍니다 (예: 192.168.0.10) 계정survey 비밀번호강사가 안내합니다 접속 도구Windows 기본 ssh (권장) 또는 PuTTY
주의 — 이 서버는 강의실 안쪽 망에서만 접속됩니다. 수업이 끝나면 강사가 내리므로 다음 시간에는 같은 주소로 접속되지 않습니다. 조사 결과는 그날 문서로 정리해 두어야 합니다.

1.4 원격 접속 방법

두 가지 중 하나를 쓰면 됩니다. 설치가 필요 없는 첫 번째 방법을 권합니다.

방법 1 — Windows 기본 ssh (설치 불필요)

⊞ + R 을 누르고 cmd 를 입력해 명령 프롬프트를 엽니다. 다음 형식으로 입력합니다. -p 뒤가 팀별 포트입니다.

C:\Users\hong>ssh survey@192.168.0.10 -p 2201 survey@192.168.0.10's password: (입력해도 화면에 아무것도 나오지 않습니다) Welcome to Ubuntu 22.04.4 LTS (GNU/Linux 5.15.0 x86_64) survey@was-a:~$
참고 — 처음 접속하면 The authenticity of host ... can't be established. 라는 물음이 나옵니다. yes 를 입력하고 Enter 를 누르면 됩니다. 처음 보는 서버인지 확인하는 절차이며, 두 번째부터는 나오지 않습니다.
방법 2 — PuTTY

PuTTY 를 실행하면 아래 창이 열립니다. 채울 곳은 세 군데입니다.

칸입력할 값설명
Host Name192.168.0.10 강사가 알려 준 주소
Port2201 팀마다 다릅니다. 기본값 22 를 지우고 넣습니다
Connection typeSSH 기본값입니다. 바뀌어 있으면 SSH 로 되돌립니다

아래 Open 을 누르면 검은 창이 열립니다. login as: 에 survey, 그다음 비밀번호를 입력합니다. 비밀번호는 입력해도 화면에 나타나지 않습니다.

자주 막히는 곳 — Port 를 22 로 둔 채 접속하면 「Connection refused」가 납니다. 팀 포트로 바꿨는지 먼저 확인하십시오. 주소를 잘못 적으면 한참 기다리다 「Network error: Connection timed out」이 납니다.
실습 1-1 배정받은 서버에 접속하여 운행환경 조사하기

목적 — 남이 만들어 둔 서버에 원격으로 들어가 운행환경 일곱 항목을 알아냅니다. 실무에서 하는 일이 바로 이것입니다. 만든 사람이 알려 주지 않아도 서버에 들어가 직접 확인할 수 있어야 합니다.

준비물 — PC, 강사가 알려 준 주소 · 포트 · 계정

절차 1. 접속하고 서버 이름 확인
접속이 되면 맨 앞에 survey@ 다음으로 서버 이름이 보입니다. 이것이 지금 들어와 있는 서버입니다.

survey@was-a:~$ hostname was-a

절차 2. 운영체제 조사
리눅스는 /etc/os-release 파일에 자기 정보를 적어 둡니다.

survey@was-a:~$ cat /etc/os-release | head -2 PRETTY_NAME="Ubuntu 22.04.4 LTS" NAME="Ubuntu"

절차 3. 미들웨어 조사
Tomcat 에는 버전을 알려 주는 명령이 들어 있습니다.

survey@was-a:~$ /usr/local/tomcat/bin/version.sh | head -2 Server version: Apache Tomcat/8.5.100 Server built: Mar 19 2024 13:54:42 UTC

절차 4. 사용 언어 조사

survey@was-a:~$ java -version openjdk version "1.8.0_402" OpenJDK Runtime Environment (build 1.8.0_402-b06)
참고 — 1.8.0 이 곧 Java 8 입니다. Java 8 은 서블릿과 JSP 로 웹을 만들던 시기의 표준이므로, 조사표에는 「Java 서블릿, JSP 기반」처럼 함께 쓰는 기술까지 적습니다.

절차 5. 데이터베이스 조사 — 여기가 함정입니다
먼저 흔히 쓰는 방법대로 해 봅니다.

survey@was-a:~$ mysql --version mysql Ver 8.0.46-0ubuntu0.22.04.4 for Linux on x86_64 ((Ubuntu))

이 값을 그대로 적으면 틀립니다. 이것은 이 서버에 깔린 접속 도구의 버전일 뿐입니다. 우리가 알아야 할 것은 데이터베이스 서버의 버전이므로, 서버에 직접 물어봐야 합니다.

survey@was-a:~$ mysqladmin -h db-a -uroot -p version | grep -i "server version" Enter password: Server version 5.7.44
주의 — 도구의 버전과 서버의 버전은 다릅니다. 조사표에 적을 것은 서버가 답한 값(MySQL 5.7)입니다. 실무에서도 흔히 하는 실수이며, 이 때문에 「되는 줄 알았던 기능이 안 되는」 일이 생깁니다.

절차 6. 형상 관리 도구 조사

survey@was-a:~$ git --version bash: git: command not found

이 경우 조사표에는 「없음」이라고 적습니다. 빈칸으로 두지 않습니다. 「없다」도 조사 결과이며, 실무에서는 이것이 「형상 관리를 하지 않고 있다」는 문제점으로 이어집니다.

절차 7. 네트워크 환경 조사

survey@was-a:~$ hostname -i 172.20.0.3 survey@was-a:~$ ss -ltnp 2>/dev/null | head -4 State Recv-Q Send-Q Local Address:Port LISTEN 0 128 0.0.0.0:22 LISTEN 0 100 *:8080

서버가 22(원격 접속)와 8080(웹) 두 개만 열어 두고 있습니다. 조사표에는 「내부망, 22 · 8080 포트만 개방」처럼 적습니다.

절차 8. 근거 자료 남기기
조사표는 혼자 제출하지 않습니다. 어디서 나온 값인지 보여 주는 자료가 함께 갑니다. 화면을 ⊞ + Shift + S 로 캡처하거나, 창의 글자를 끌어 선택해 복사해 둡니다.

절차 9. 접속 끊기

survey@was-a:~$ exit logout Connection to 192.168.0.10 closed.

결과 확인 — 다음을 스스로 말할 수 있으면 조사가 끝난 것입니다. 운영체제 · 미들웨어 · 사용 언어 · 데이터베이스(서버가 답한 값) · 형상 관리 도구 · 네트워크 환경.

팀별로 답이 다릅니다 — 예를 들어 B팀 서버를 조사하면 Ubuntu 22.04.5 · Java 17.0.20 · Apache Tomcat 10.1.60 · MariaDB 10.6.28 이 나옵니다. 같은 절차로 다른 답이 나오는 것을 확인하고, 발표 때 서로 비교해 보십시오.
현업에서는 — 조사표 서식은 발주기관이 지정하므로 프로젝트마다 다릅니다. 반면 수집 방법은 대체로 같습니다. 서버에 원격으로 들어가 cat /etc/os-release, java -version 처럼 직접 확인하는 것이 기본이고, 서버가 수십 대를 넘어가면 Ansible 같은 도구로 한 번에 모읍니다. 조직 차원에서는 이 정보를 CMDB(구성관리 데이터베이스)에 등록해 두고 계속 갱신합니다. 상용은 ServiceNow, 공개 도구로는 GLPI · Snipe-IT 가 있습니다.
강사용 — 실습 서버 올리기

강사 PC 한 대에서 팀 수만큼 환경을 올립니다. Docker Desktop 이 설치되어 있어야 합니다. docker-compose.yml · Dockerfile 을 같은 폴더에 두고 그 폴더에서 실행합니다.

C:\lab>docker compose up -d --build Container survey-a Started Container survey-b Started C:\lab>docker compose ps NAME STATUS PORTS survey-a Up 12 seconds 0.0.0.0:2201->22/tcp, 0.0.0.0:18001->8080/tcp survey-b Up 12 seconds 0.0.0.0:2202->22/tcp, 0.0.0.0:18002->8080/tcp C:\lab>ipconfig IPv4 주소 . . . . . . . . : 192.168.0.10 ← 이 주소를 칠판에 적는다

수업이 끝나면 docker compose down 으로 내립니다. 계정은 survey, 비밀번호는 Dockerfile 에서 정합니다. 강의실 안쪽 망 전용이므로 인터넷에 포트를 열지 마십시오.

자원은 환경 하나당 약 160MB(WAS 96MB + DB 64~197MB)를 씁니다. 5개 팀이면 대략 1GB 안쪽이며, 훈련생이 20명 접속해도 부담은 거의 없습니다. 바탕 이미지는 지원이 끝나지 않은 배포판으로 고릅니다 — 지원 종료된 것은 apt 저장소가 사라져 빌드가 실패합니다.

1.5 조사표 작성

수집이 끝났으면 제출 서식으로 옮깁니다. 실제 평가에서 제공되는 도서 대여 시스템을 조사한 예는 다음과 같습니다. 일곱 줄이 모두 채워져야 하며, 각 줄이 채점 항목에 대응합니다.

조사한 값이 조사표의 어느 줄로 가는지는 다음과 같습니다. 이 대응을 알면 옮겨 적는 일은 기계적으로 끝납니다.

조사표 항목서버에서 친 명령 옮겨 적을 때
운영체제cat /etc/os-release 배포판 이름과 판 (예: Ubuntu 22.04)
데이터베이스mysqladmin -h <DB서버> -u root -p version 서버가 답한 값. 도구 버전이 아님 (예: MySQL 5.7)
미들웨어/usr/local/tomcat/bin/version.sh 제품명과 버전 (예: Apache Tomcat 8.5)
사용 언어java -version 함께 쓰는 기술까지 (예: Java 서블릿, JSP 기반)
IDE서버에는 없음. 개발 PC 에서 확인 쓰는 것만 (예: 이클립스, 인텔리제이)
형상 관리 도구git --version 없으면 「없음」. 그것이 곧 문제점이 됨
네트워크 환경hostname -i · ss -ltnp 망 구성과 열린 포트 (예: 내부망, 22 · 8080 개방)
생각해 보기 — 조사표를 채우는 것으로 끝내지 말고, 각 줄에서 무엇이 가능하고 무엇이 불가능해지는지를 함께 생각해 봅니다. DBMS 가 MySQL 5.7 이면 Oracle 전용 함수를 쓸 수 없고, 네트워크가 내부망이면 외부 API 를 호출할 수 없습니다. 이 판단이 이후 「요구사항 확인」과 「분석모델 확인」의 근거가 됩니다.
실습 1-2 운행환경 조사표 작성하기

목적 — 수집한 값을 제출 서식에 맞추어 정리하고 산출물을 완성합니다.

준비물 — 실습 1-1 에서 조사한 값과 근거 자료, 스프레드시트

절차

  1. 스프레드시트를 실행하고 [그림 1-2] 와 같이 「구분 / 조사 결과 / 적는 요령」 세 개의 열을 작성합니다.
  2. 운영체제, 데이터베이스, 미들웨어, 사용 언어, IDE, 형상 관리 도구, 네트워크 환경의 일곱 행을 만듭니다.
  3. 위 대응표를 보며 실습 1-1 에서 조사한 값을 「조사 결과」 열로 옮깁니다. 평가에서는 제공된 현행 시스템의 값을 씁니다.
  4. 데이터베이스는 서버가 답한 값을 적었는지 다시 확인합니다. mysql --version 의 값을 적었다면 틀린 것입니다.
  5. 서버에서 확인할 수 없는 IDE 는 개발 PC 쪽에서 확인해 적습니다.
  6. 일곱 줄 모두 판(버전)이 적혀 있는지 확인합니다. 해당 사항이 없으면 「없음」이라고 적고 빈칸으로 두지 않습니다.
  7. 문서 마지막에 근거 자료를 붙입니다. 근거_01_시스템요약.png 는 그림으로 넣고, 근거_02 · 근거_03 은 필요한 줄만 인용합니다.

제출물 — 운행환경 조사표 1부 (일곱 줄, 판(버전) 포함) + 근거 자료

스스로 확인 — 일곱 줄이 모두 차 있고, 각 줄에 버전이 있으며, 조사 결과마다 어느 근거 자료에서 나온 값인지 말할 수 있으면 완성입니다.

정리 현행 시스템 분석은 운영체제 · 데이터베이스 · 미들웨어 · 사용 언어 · IDE · 형상 관리 도구 · 네트워크 환경의 일곱 항목을 조사하는 작업입니다. 조사 결과에는 종류와 판(버전)을 함께 적습니다. 일곱 줄이 그대로 채점 항목 ① 01 ~ 05 의 25점에 대응합니다.

네 산출물은 앞의 것이 뒤의 것의 재료가 됩니다. 조사표에서 유스케이스가 나오고, 유스케이스의 기본 흐름에서 시퀀스가 나오고, 시퀀스의 메시지에서 API 가 나옵니다. 순서를 건너뛰면 뒤에서 지어내게 됩니다.

목표 시스템 표

현행을 조사했으면 앞으로 어떻게 할 것인지를 적습니다. 수행준거 1.3 이 「명확하고 구체적으로 기술할 수 있다」 로 되어 있습니다. 구체적이라는 말은 제품 이름과 판이 적혀 있다는 뜻입니다.

모든 칸을 「전환」 으로 채울 필요가 없습니다. 데이터베이스를 그대로 쓰기로 했다면 「MySQL 을 그대로 사용」 이라고 적고 그 이유를 「데이터 이관 비용이 크고 현행 구조로 요구사항을 모두 담을 수 있음」 처럼 적습니다.

바꾸는 쪽을 택했다면 왜 지금인지를 적습니다. 「최신이라서」 는 이유가 되지 않습니다. 「인증과 권한 관리를 직접 만들지 않고 쓰기 위해」 처럼 이번 요구사항과 이어야 설득이 됩니다.

해 보기 목표 시스템 표를 다 쓴 뒤 요구사항 두 줄을 다시 읽어 보십시오. 요구사항을 만들기 위해 필요한 것이 목표 시스템에 빠짐없이 들어 있어야 합니다. 인증을 더한다면 인증을 무엇으로 할지가 표에 있어야 합니다.

사전조건과 사후조건

두 칸을 헷갈리는 경우가 많습니다. 기준은 시점입니다.

사전조건 — 시작하기 전에 참이어야 하는 것
「회원이 로그인한 상태이고, 도서 상태가 대여 가능이다」 처럼 상태로 적습니다. 「회원이 로그인한다」 는 동작이므로 사전조건이 아닙니다.
사후조건 — 끝난 뒤에 달라져 있는 것
「대여 신청이 승인 대기로 저장되고 관리자 목록에 나타난다」 처럼 무엇이 바뀌었는지를 적습니다. 화면에 무엇이 보이는지가 아니라 데이터가 어떻게 되었는지를 적는 것이 낫습니다.

기본 흐름의 번호

기본 흐름은 번호를 붙인 문장으로 적습니다. 이 번호가 다음 단계에서 시퀀스 다이어그램의 메시지 번호가 됩니다. 번호가 없으면 시퀀스를 그릴 때 순서를 다시 정해야 하고, 그러면 둘이 어긋납니다.

채점 항목 ② 10 이 「명세서 내용이 현행 시스템의 실제 기능과 일치하는가」 입니다. 조사하지 않은 기능을 흐름에 적으면 여기서 걸립니다. 이를테면 현행에 알림 기능이 없는데 「대여 신청 시 문자를 보낸다」 고 적는 경우입니다.

규칙을 하나 정해 두고 끝까지 지킵니다. 가장 무난한 것은 자원을 명사 복수로 쓰는 방식입니다.

코드뜻이 예제에서 쓸 자리
200잘 됐다조회 · 승인
201새로 만들었다회원가입 · 대여 신청 · 도서 등록

400보낸 값이 잘못됐다필수 항목 누락

여덟 개를 다 쓸 필요는 없습니다. API 한 건에 성공 하나 + 실패 하나나 둘이면 됩니다. 요구사항 명세서의 검증 기준에 적어 둔 거절 상황이 곧 실패 코드가 됩니다.

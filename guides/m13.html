앞 교과 「인터페이스 구현」 에서도 두 시스템을 이었습니다. 그때는 둘 다 우리 것이었고 가운데에 테이블을 두었습니다. 이번에는 한쪽이 남의 것입니다. 고칠 수도 없고 멈추라 할 수도 없는 상대와 맞춰야 합니다.

연계 데이터 구성하기
무엇을 주고받을지 정하는 일입니다. 바깥이 주는 JSON 을 그대로 쓰지 않고 우리 표준으로 옮겨 둡니다. 문서 세 장이 여기서 나오고, 코드는 변환 메서드 둘뿐입니다.
연계 메커니즘 구성하기
어떻게 주고받을지 정하는 일입니다. 무엇으로 부를지, 얼마마다 부를지, 실패하면 어떻게 할지, 아무나 못 부르게 어떻게 막을지 넷입니다.
내외부 연계 모듈 구현하기
정한 대로 만들고 제대로 도는지 확인하는 일입니다. 받아 저장하고, 다시 내주고, 여러 번 받아도 어긋나지 않는지 보고, 시험합니다.
수행준거준거의 말 이 평가에서
1.1외부 및 내부 모듈 간의 데이터 연계 요구사항을 분석 연계 요구사항 분석서를 씁니다
1.2연계가 필요한 데이터를 식별 외부 응답에서 쓸 항목 넷을 고릅니다
1.3연계를 위한 데이터 표준을 설계 PostDTO 로 옮기는 규칙을 정하고 명세서를 씁니다
2.1효율적 데이터 송수신 방법을 정의 RestTemplate 과 UriComponentsBuilder 로 GET
2.2연계주기를 정의 수동 호출 + @Scheduled 60초
2.3데이터 연계 실패 시 처리방안을 정의 못 닿음 · 상태코드 이상 · 본문 없음 셋을 가릅니다
2.4송수신 시 보안을 적용 동기화는 ADMIN · 조회는 인증 · 인증키는 설정 파일로
3.1연계모듈 구현을 위한 논리적 · 물리적 환경을 준비 의존성과 설정 키를 갖추고 외부망을 확인합니다
3.2외부 시스템과의 연계모듈을 구현 받아서 바꿔 저장하는 syncPosts 를 만듭니다
3.3안정적 작동과 연동된 데이터의 무결성을 검증 여러 번 받아도 건수가 늘지 않는 것을 보입니다
3.4테스트 케이스를 작성하고 테스트 조건을 명세화 명세서 표 + JUnit 코드 둘 다 냅니다

준거 열하나가 채점 항목 열다섯으로 쪼개져 있습니다. 「정의할 수 있다」 는 말이 다섯 번 나온다는 점을 보십시오(1.1 · 1.3 · 2.1 · 2.2 · 2.3). 만드는 것만큼 적어 두는 것을 본다는 뜻입니다.

실습 1 무엇을 내야 하는지 정하고, 바깥에 닿는지 확인합니다

목적 — 시작 전에 둘을 못 박습니다. 끝났을 때 무엇이 찍혀 있어야 하는가와 이 과제가 애초에 가능한가입니다. 둘째가 중요합니다 — 이 과제는 남의 서버가 있어야 시작되고, 강의실 방화벽이 막고 있으면 코드를 아무리 잘 써도 아무것도 안 됩니다.

절차 1 — 캡처 네 컷에 «무엇이 보여야 하는지» 적습니다
찍을 것 상태 코드보여야 할 것
1인증 없이 호출401 응답 헤더의 WWW-Authenticate
2user 로 동기화 시도 403 권한이 모자라 막혔다는 것 — 401 과 다릅니다
3admin 으로 동기화 200받아 온 건수
4재제공 API 조회200 저장된 목록 — 우리 형식으로
+콘솔 배치 로그— 숫자가 바뀌는 두 줄 (실습 8)

2번을 빠뜨리기 쉽습니다. admin 으로만 찍으면 「권한을 나눴다」 를 증명하지 못합니다. 막히는 화면이 있어야 채점 항목 10 이 들어옵니다.

네 컷은 지금 찍는 것이 아닙니다. 실습 10 · 12 · 13 에서 하나씩 나옵니다. 지금은 무엇을 찍어야 하는지 적어 두는 것이 전부입니다.

절차 2 — 바깥을 한 줄로 두드려 봅니다

curl -s "https://jsonplaceholder.typicode.com/posts?_limit=1"

이렇게 나오면 됩니다.

[ { "userId": 1, "id": 1, "title": "sunt aut facere repellat provident occaecati excepturi optio reprehenderit", "body": "quia et suscipit\nsuscipit recusandae consequuntur expedita et cum\nreprehenderit molestiae ut ut quas totam\nnostrum rerum est autem sunt rem eveniet architecto" } ]

body 안의 \n 을 눈여겨보십시오. 줄바꿈이 글자 그대로 들어 있습니다. 실습 5 에서 이것이 자료형을 정하는 근거가 됩니다. 지금은 「있구나」 만 기억하면 됩니다.
절차 3 — 상태 코드와 걸린 시간도 같이 봅니다

curl -s -m 12 -w "\nHTTP %{http_code} · %{time_total}s\n" \ "https://jsonplaceholder.typicode.com/posts?_limit=2"

HTTP 200 · 1.028057s

1초 걸렸습니다. 우리 데이터베이스는 0.001초면 답합니다. 훨씬 느린 상대와 맞춰야 한다는 뜻이고, 그래서 뒤에서 시간 제한과 주기를 따로 정합니다 (실습 8 이후).

이 «1초» 는 첫 호출이라 느린 것입니다. 이름을 찾고(DNS) 암호 통신을 여는(TLS) 일이 처음 한 번만 일어납니다. 두 번째부터는 0.2초쯤으로 내려갑니다 — 실습 3 에서 재 봅니다. 그래도 우리 데이터베이스보다 200배 느립니다. 시간 제한은 느린 쪽 값을 기준으로 잡아야 합니다.
절차 4 — 안 되면 어디가 막힌 것인지 가릅니다
나오는 것뜻과 할 일
Could not resolve host 이름을 못 찾습니다 — DNS 또는 아예 인터넷이 안 됩니다
Connection timed out 이름은 찾았는데 막혀 있습니다 — 방화벽·프록시
SSL certificate problem 가운데서 가로채는 장비가 있습니다 — 기관 프록시
HTML 로그인 화면이 나옴 인증 프록시입니다. 브라우저로 한 번 로그인해야 합니다
여기서 막히면 «다른 API 로 바꿀지» 를 오늘 정하십시오. 작업지시서가 공공데이터포털로 교체를 허용해 두었습니다. 그런데 API 를 바꾸면 필드 이름이 전부 달라집니다 — 실습 5 의 매핑표와 DTO 를 통째로 다시 써야 합니다. 마지막 날에 발견하면 손쓸 수가 없습니다.
절차 5 — 몇 건이 오는지 세어 둡니다

curl -s "https://jsonplaceholder.typicode.com/posts" -o posts.json python -c "import json;d=json.load(open('posts.json'));print(len(d),'건 ·',list(d[0].keys()))"

100 건 · ['userId', 'id', 'title', 'body']

100건 · 필드 넷입니다. 이 두 숫자가 실습 4 의 요구사항 분석서와 실습 5 의 매핑표에 그대로 들어갑니다.

제출물 — 캡처 네 컷 계획표 + curl 결과 화면 + 상태 코드와 시간이 찍힌 화면 + 건수·필드 수

스스로 확인 — ⓪ 네 컷에 403 이 들어 있습니까 ① 200 을 받았습니까 ② 응답이 JSON 입니까 (HTML 이면 프록시입니다) ③ 몇 건, 몇 필드인지 세었습니까 ④ 막혔다면 오늘 안에 교사와 대안을 정했습니까

절차 3 — 세 가지를 «구분» 합니다
일어나는 일 고장인가
①아무 주소나 부르면 401, 브라우저로 열면 로그인 창이 뜬다 정상 — security 의존성이 들어 있는데 아직 설정을 안 해서 전부 막힌 상태입니다
②인증을 통과해도 500 이 온다 정상 — 내가 채울 빈 메서드입니다
③기동 자체가 안 됨 고장 — 절차 5 를 보십시오
절차 4 — ① 과 ② 를 직접 받아 봅니다

curl -s -i http://localhost:8077/api/link/posts HTTP/1.1 401 Set-Cookie: JSESSIONID=C62480477BE5B37A17AA8797BC658247; Path=/; HttpOnly WWW-Authenticate: Basic realm="Realm", charset="UTF-8" X-Content-Type-Options: nosniff

WWW-Authenticate 줄이 «로그인 창» 의 정체입니다. 브라우저는 이 줄을 보고 아이디·비밀번호 상자를 띄웁니다. curl 이나 Postman 은 상자를 안 띄우고 401 을 그대로 보여 줍니다. 같은 응답을 도구가 다르게 보여 주는 것일 뿐입니다.

이제 기동 로그의 임시 비밀번호로 다시 부릅니다.

curl -s -u user:7e410ca5-b39f-45ab-b04b-c1bcc908abd4 \ http://localhost:8077/api/link/posts {"timestamp":"2026-09-18T04:53:05.007Z","status":500, "error":"Internal Server Error","path":"/api/link/posts"}

401 이 500 으로 바뀐 것이 «진도» 입니다. 401 은 문 앞에서 막힌 것이고, 500 은 들어와서 안이 비어 있는 것입니다. 두 번째가 내가 채울 자리입니다. 이 둘을 구분 못 하면 보안 설정을 고쳐야 할 때 코드를 뒤지게 됩니다.
절차 5 — 응답에 «예외 이름이 없는 것» 을 확인합니다

위 응답 어디에도 UnsupportedOperationException 이 없습니다. 그것은 서버 콘솔에만 찍힙니다.

임시 비밀번호는 띄울 때마다 바뀝니다. 다시 띄우면 아까 것으로는 401 이 돌아옵니다. 그래서 과제에는 쓸 수 없고, 실습 10 에서 계정 둘(user · admin)을 직접 만듭니다. 여기서 security 의존성을 빼 버리면 안 됩니다 — 채점 항목 10 이 그것으로 받는 점수입니다.
절차 7 — 채울 자리를 «세어» 둡니다

찾을 것 : UnsupportedOperationException 나오는 곳 : 코드 여섯 자리 문서 양식 : docs/산출물_양식/ 아래 세 장

여섯 + 셋이 이 과제의 전부입니다. 문서 셋이 18점이고 양식이 이미 있으니 코드를 시작하기 전에 먼저 끝낼 수 있습니다 (실습 3 · 4 · 6).

제출물 — 기동 로그(임시 비밀번호 줄이 보이게) + 401 헤더 화면 + 500 응답 화면 + 콘솔의 예외 줄 + 채울 자리 목록

스스로 확인 — ① SHOW TABLES 로 표를 봤습니까 ② 401 과 500 이 어떻게 다른지 말할 수 있습니까 ③ 응답에 예외 이름이 없는 것을 확인했습니까 ④ security 를 빼지 않았습니까

3연계의 전체 모습

우리가 부르는 쪽입니다.

연계 둘

받아 오기 · 내주기

방향이 반대입니다

지금까지 만든 것은 전부 남이 우리를 부르는 프로그램이었습니다. 브라우저나 Postman 이 요청을 보내면 우리가 답했습니다. 여기서는 우리가 남을 부릅니다. 그래서 새로 생각할 것이 셋입니다.

  1. 상대가 느릴 수 있습니다. 기다리는 동안 우리 요청도 멈춥니다.
  2. 상대가 멈출 수 있습니다. 우리가 고칠 방법이 없습니다.
  3. 상대가 형식을 바꿀 수 있습니다. 알려 주지 않고 바꿉니다.

이 셋을 어떻게 견딜지가 이 교과의 내용이고, 각각 주기 · 실패 처리 · 표준화 로 대응합니다.

연계가 둘입니다

연계 ID무엇 방향누가 부르는가
IF-001게시글 수신 외부 → 우리우리가 부릅니다 (RestTemplate)
IF-002게시글 재제공 우리 → 클라이언트남이 부릅니다 (REST API)

「통합 구현」 이라는 이름이 여기서 옵니다. 받는 쪽과 주는 쪽을 하나로 잇는 것이 이 교과입니다. 받아 오기만 만들고 내주기를 빠뜨리면 절반입니다.

실습 3 연계 둘을 «표 한 장» 으로 세웁니다

목적 — 이 교과에서 가장 많이 빠뜨리는 것이 IF-002 입니다. 「연계」 라 하면 받아 오는 것만 떠올리기 때문입니다. 여기서 둘이라는 것을 못 박아 두면 뒤의 문서 셋이 저절로 둘씩 나옵니다.

절차 1 — 방향을 화살표로 그려 봅니다

IF-001 게시글 수신 IF-002 게시글 재제공 ───────────────────── ───────────────────── 외부 API ──────────> 우리 서버 ──────────> 다른 시스템 · 화면 (남의 것) 우리가 «부른다» 남이 «부른다» RestTemplate REST API 수동 + 배치 60초 실시간

연계 ID무엇 방향누가 부르는가 주기
IF-001게시글 수신외부 → 우리 우리가 부릅니다수동 + 배치 60초
IF-002게시글 재제공우리 → 클라이언트 남이 부릅니다실시간
「누가 부르는가」 칸이 이 표의 핵심입니다. 지금까지 만든 프로그램은 전부 남이 우리를 부르는 쪽이었습니다. IF-001 은 반대입니다 — 우리가 먼저 말을 겁니다. 부르는 쪽이 되면 새로 생각할 것이 셋이고, 그것이 절차 2 입니다.
절차 2 — 「남의 것」 이라서 생기는 셋을 적습니다
상대가 이럴 수 있다 우리 대응어디서
①느리다 — 기다리는 동안 우리도 멈춘다 시간 제한 · 주기실습 8
②멈춘다 — 우리가 고칠 방법이 없다 실패 처리 · 재시도실습 9
③형식을 바꾼다 — 알려 주지 않고 바꾼다 표준화 (DTO)실습 5

① 의 근거는 실습 1 에서 잰 시간입니다. 얼마인지는 절차 3 에서 다시 재서 정합니다 — 첫 호출과 그 뒤가 다르기 때문입니다. 정한 숫자를 요구사항 분석서에 그대로 적으십시오 (실습 4).

절차 3 — ① 을 «직접» 겪어 봅니다

상대가 느린 것이 왜 우리 문제가 되는지는, 여러 번 불러 보면 압니다.

curl -s -o /dev/null -w "%{time_total}s\n" \ "https://jsonplaceholder.typicode.com/posts/1"

이것을 다섯 번 돌리면 이렇게 나옵니다.

0.254289s 0.173217s 0.243282s 0.240880s 0.178736s

눈여겨볼 것
실습 1 에서는 1.028초였다 첫 호출이라 DNS 조회와 TLS 악수가 함께 들었습니다
지금은 0.17 ~ 0.25초 같은 값도 1.5배까지 흔들립니다
우리 데이터베이스는 0.001초 가장 빠를 때도 200배 느립니다

제일 느린 값을 적어 두는 것이 시간 제한을 정하는 근거가 됩니다. 평균으로 잡으면 절반이 걸립니다.

시간 제한을 안 걸면 «영원히» 기다립니다. 상대가 답을 안 주고 연결만 붙들고 있으면 우리 스레드 하나가 거기 묶입니다. 그런 요청이 쌓이면 우리 서버가 남 때문에 멈춥니다. 남의 장애가 우리 장애가 되는 것 — 이것이 연계에서 가장 흔한 사고입니다. 실습 8 에서 시간 제한을 겁니다.
절차 4 — IF-002 를 빠뜨리지 않았는지 확인합니다
물음
□연계 정의서에 표가 둘입니까 (실습 6)
□IF-002 의 주기를 「실시간」 이라 적었습니까
□IF-001 의 주기를 「수동 + 배치 60초」 라 적었습니까
□둘의 주기가 다른 까닭을 말할 수 있습니까

IF-001 을 「실시간」 이라 적으면 틀립니다. 사람이 /sync 를 눌러야 받아 오고, 그것과 별개로 배치가 60초마다 돕니다. IF-002 만 진짜 실시간입니다 — 누가 부르면 그 자리에서 답합니다.

절차 5 — 한 장으로 옮깁니다

위의 화살표 그림과 표 둘을 한 장에 담습니다. 이 장이 실습 4 · 6 의 첫 페이지가 되고, 발표할 때 맨 처음 보여 줄 그림이 됩니다.

절차 6 — 안 되면 여기를 봅니다
나오는 것볼 곳
시간이 매번 1초 넘게 나옴 회사·학교 프록시를 지나고 있을 수 있습니다. 실습 1 의 curl 응답이 JSON 이 맞는지 다시 보십시오
curl: (28) Operation timed out -m 로 준 시간 안에 못 받았습니다. 그 값이 곧 시간 제한의 하한입니다
다섯 번이 모두 똑같음 가운데서 캐시가 받아 주고 있습니다. 주소 뒤에 ?t=1 · ?t=2 를 달아 다시 재십시오

제출물 — 연계 구성도(화살표) + 연계 목록표(둘) + 「남의 것」 대응 셋 + 응답 시간 다섯 번 측정

스스로 확인 — ① 연계가 둘인 것을 표로 적었습니까 ② 누가 부르는가 칸이 둘 다 채워졌습니까 ③ 느림 · 멈춤 · 형식 변경 셋에 대응을 적었습니까 ④ 응답 시간을 여러 번 재 봤습니까

절차 2 — 6번(오류 · 장애)에 «셋» 을 적습니다
어떤 일어떻게 안다 어떻게 한다
못 닿음연결 예외 · 시간 초과 기록을 남기고 다음 주기에 다시
상태 코드 이상200 이 아님 (404 · 500 …) 같음. 우리 자료는 건드리지 않습니다
본문 없음 · 형식 다름빈 배열 · 변환 실패 건너뛰고 몇 건을 건너뛰었는지 남깁니다

셋 다 「우리가 안 죽는다」 가 공통입니다. 남이 잘못되었다고 우리 서버가 멈추면 안 됩니다. 실습 9 에서 이 셋을 실제로 일으켜 봅니다.

절차 3 — 7번(보안)에 «우리 쪽» 을 적습니다

보안 인증 : HTTP Basic (Spring Security) 권한 : USER = 조회만 → GET /api/link/posts ADMIN = 조회 + 동기화 → POST /api/link/sync 근거 : 동기화는 «외부를 부르고 우리 자료를 바꾸는» 일이므로 관리자만 확인 : user 로 동기화를 시도해 403 이 나오는 화면을 캡처

마지막 줄이 중요합니다. 「관리자만」 이라고 적어 놓고 막히는 화면을 안 찍으면 지켰다는 증거가 없습니다 (실습 1 절차 1 의 2번 컷).

절차 4 — 5번(주기)을 적어 두면 뒤가 쉬워집니다
여기 적은 것뒤에서 저절로 정해지는 것
「수동 + 배치 60초」 실습 8 에서 @Scheduled 를 어떻게 걸지 고민할 것이 없습니다
「동기화는 관리자만」 실습 10 에서 규칙을 어떻게 쓸지 이미 정해져 있습니다

분석서를 먼저 쓰는 까닭이 이것입니다. 「분석서」 라는 말이 거창하지만 하는 일은 정하는 것입니다. 코드를 쓰다가 정하면 정할 때마다 코드를 고치게 됩니다.

왜 그대로 안 쓰는가

외부가 주는 JSON 을 그대로 저장하면 편할 것 같습니다. 그런데 남의 형식에 우리가 매이게 됩니다. 상대가 필드 이름을 title 에서 subject 로 바꾸면 우리 코드 곳곳을 고쳐야 합니다.

가운데에 PostDTO 를 두면 고칠 곳이 한 군데가 됩니다. 변환 메서드 안만 바꾸면 나머지는 그대로입니다. 이것이 「표준을 설계한다」 는 말의 뜻입니다.

@JsonIgnoreProperties(ignoreUnknown = true)    // ★ 이 한 줄이 중요합니다
@Data @NoArgsConstructor @AllArgsConstructor @Builder
public class PostDTO {
    private Long id;          // 외부 식별자
    private Long userId;
    private String title;
    private String body;
    private LocalDateTime createAt;   // 외부에 없음 — 우리가 붙임

    public Post toEntity() { ⋯ }              // DTO → Entity
    public static PostDTO from(Post p) { ⋯ }  // Entity → DTO
}

@JsonIgnoreProperties(ignoreUnknown = true) 는 외부가 필드를 늘려도 우리가 안 터지게 못 박는 한 줄입니다. 다만 「없으면 반드시 터진다」 고 알고 있으면 틀립니다. 터지느냐 마느냐는 Jackson 판과 설정에 달려 있습니다.

FAIL_ON_UNKNOWN_PROPERTIES 기본값모르는 필드가 오면
Jackson 2true UnrecognizedPropertyException 으로 터집니다
Jackson 3false 그냥 통과합니다 — 모르는 필드를 버립니다

이 프로젝트는 Jackson 3 이라 안 터집니다. 스프링 부트도 이 설정을 켜지 않습니다. 그런데도 이 한 줄을 쓰는 까닭은 둘입니다 — ① 설정은 누가 바꿀 수 있고, ② 이 클래스가 무엇을 기대하는지 코드에 남습니다. 실습 5 에서 두 판의 동작을 직접 확인합니다.

createAt 은 왜 있는가

외부 응답에 없는 필드입니다. 우리가 붙입니다. 언제 받아 왔는지를 남겨 두면 「이 자료가 얼마나 오래된 것인가」 를 알 수 있습니다. 연계에서는 자료의 나이가 중요할 때가 많습니다.

절차 1 — 외부가 «실제로» 무엇을 주는지 셉니다

필드 이름만 보고 자료형을 정하면 반드시 틀립니다. 100건을 받아 세어 봅니다.

curl -s "https://jsonplaceholder.typicode.com/posts" -o posts.json

count_fields.py 라는 이름으로 저장하고 돌립니다.

import json d = json.load(open('posts.json', encoding='utf-8')) print('건수', len(d)) for k in ('userId', 'id', 'title', 'body'): v = [x[k] for x in d] if isinstance(v[0], int): print(f'{k:7} 정수 {min(v)} ~ {max(v)}') else: L = [len(x) for x in v] nl = sum(1 for x in v if '\n' in x) print(f'{k:7} 글자 {min(L)} ~ {max(L)}자 · 줄바꿈 든 건수 {nl}/{len(v)}')

python count_fields.py

건수 100 userId 정수 1 ~ 10 id 정수 1 ~ 100 title 글자 12 ~ 79자 · 줄바꿈 든 건수 0/100 body 글자 102 ~ 225자 · 줄바꿈 든 건수 100/100

마지막 줄을 보십시오 — body 는 «전부» 줄바꿈이 들어 있습니다. 100건 중 100건입니다. 우연이 아니라 그렇게 생긴 자료입니다. 이것을 모르고 VARCHAR(100) 으로 잡으면 102자짜리부터 안 들어갑니다 (실습 2 에서 본 Data too long). 화면에 그대로 뿌리면 줄이 안 바뀐 채로 한 줄이 됩니다.
절차 2 — 매핑표를 씁니다
외부 필드우리 필드 우리 자료형정한 근거
ididBIGINT 1~100 이지만 늘어날 수 있어 넉넉히
userIduserIdBIGINT 같음

없음createAt DATETIME 우리가 붙입니다 — 언제 받아 왔는지

「정한 근거」 칸이 점수입니다. VARCHAR(255) 라고만 적으면 「왜 255 인가」 에 답할 수 없습니다. 79자를 세어 봤다는 것이 근거입니다.

절차 3 — createAt 이 왜 있는지 적습니다

외부 응답에 없는 필드입니다. 우리가 붙입니다. 언제 받아 왔는지를 남겨 두면 「이 자료가 얼마나 오래된 것인가」 를 알 수 있습니다. 연계에서는 자료의 나이가 중요할 때가 많습니다 — 「어제 받은 값을 오늘 것처럼 보여 주고 있지 않은가」 를 이 칸으로 봅니다.

절차 4 — 상대가 필드를 늘렸다고 «가정해» 봅니다

연계에서 가장 흔한 사고입니다. 상대가 알려 주지 않고 필드를 늘립니다.

오늘 오는 것 {"userId":1,"id":1,"title":"제목","body":"본문"} 내일 오는 것 {"userId":1,"id":1,"title":"제목","body":"본문", "tags":["공지"],"viewCount":42}

이때 우리가 터지느냐 마느냐는 Jackson 판과 설정에 달려 있습니다. 직접 확인해 보십시오.

Jackson 판 : 3.1.4 기본값 FAIL_ON_UNKNOWN_PROPERTIES = false [A] 기본 설정 통과 [B] 일부러 켰을 때 tools.jackson.databind.exc.UnrecognizedPropertyException Unrecognized property "viewCount" (class StrictProbe$P), not marked as ignorable (2 known properties: "id", "title") [C] 켠 채로 @JsonIgnoreProperties 를 붙이면 통과

Jackson 2 였다면 [A] 에서 이미 터집니다.

Jackson 판 : 2.21.4 기본값 FAIL_ON_UNKNOWN_PROPERTIES = true [A] 기본 설정 · 보호 장치 없는 그릇 UnrecognizedPropertyException Unrecognized field "viewCount" (class J2Probe$P), not marked as ignorable (2 known properties: "title", "id") [B] @JsonIgnoreProperties 를 붙이면 통과

판기본값 모르는 필드가 오면
Jackson 2true 터집니다
Jackson 3 (이 프로젝트) false그냥 통과합니다
그래도 @JsonIgnoreProperties(ignoreUnknown = true) 를 씁니다. 지금 안 터진다고 안 써도 되는 것이 아닙니다 — ① 설정은 누가 바꿀 수 있고, ② 이 클래스가 무엇을 기대하는지 코드에 남습니다. 「기본값이 그러니까」 에 기대는 코드는 판이 올라가면 조용히 깨집니다. 교재나 인터넷 글이 「없으면 터진다」 고 하는 것은 Jackson 2 를 기준으로 쓴 것입니다.

외부 JSON 을 그대로 쓰면가운데 DTO 를 두면
상대가 title 을 subject 로 바꾸는 순간 우리 코드 곳곳을 고칩니다 변환 메서드 안만 바꾸면 나머지는 그대로입니다

이것이 「표준을 설계한다」 는 말의 뜻입니다. 고칠 곳을 한 군데로 모으는 일이지 거창한 것이 아닙니다.

절차 1 — 주소를 없는 곳으로 바꿉니다

이 두 화면이 항목 08 의 증거입니다. 실패했다는 응답 하나, 그래서 자료가 안 망가졌다는 건수 하나입니다. 건수를 안 찍으면 「잡았다」 를 증명하지 못합니다.

다 만들고 나서 찍으려면 주소를 다시 틀려야 합니다. 그때는 이미 자료가 들어 있어 건수가 0 이 아닙니다. 실패 처리를 만든 직후에 바로 찍어 두십시오.

채점 항목

새로 나옴

Spring Security

401 과 403

둘 다 거절이지만 뜻이 다릅니다.

코드뜻언제
401누구인지 모르겠다 아이디와 비밀번호를 안 보냈거나 틀렸습니다
403누구인지는 알겠는데 권한이 없다 로그인은 됐는데 ADMIN 이 아닙니다

제출 캡처에 둘 다 있어야 합니다. 401 만 있으면 「인증을 걸었다」 는 증거이고, 403 이 있어야 「권한을 나눴다」 는 증거가 됩니다. 채점 항목 10 이 보는 것은 후자입니다.

순서가 곧 규칙입니다

.requestMatchers(HttpMethod.POST, "/api/link/sync").hasRole("ADMIN")   // ① 좁은 것
.requestMatchers("/api/link/**").authenticated()                       // ② 넓은 것
.anyRequest().permitAll()                                              // ③ 나머지

requestMatchers 는 위에서부터 차례로 걸립니다. ①과 ②의 순서를 바꾸면 /api/link/sync 가 ②에 먼저 걸려 ADMIN 규칙이 죽습니다. user 로도 동기화가 되어 버리고, 403 캡처를 만들 수 없습니다.

비밀번호를 그대로 두지 않습니다

UserDetails user = User.withUsername("user")
        .password(passwordEncoder().encode("1234"))   // 해시로 바꿔 넣습니다
        .roles("USER").build();

BCryptPasswordEncoder 가 해시로 바꿉니다. 지금은 메모리에 두는 계정이라 대수롭지 않아 보이지만, 습관을 여기서 들입니다.

roles("ADMIN") 로 넣고 hasRole("ADMIN") 로 봅니다. 스프링이 안에서 ROLE_ 를 붙여 주므로 우리가 ROLE_ADMIN 이라고 쓰면 안 됩니다. 두 번 붙어 안 맞습니다.

공공데이터포털로 바꾸면 serviceKey 가 생깁니다. 코드에 박지 마십시오. application-dev.properties 에 두고 그 파일을 저장소에서 뺍니다. 이것도 「송수신 보안」 에 들어갑니다.
실습 10 계정 둘을 만들고, 규칙 순서를 «뒤집어» 봅니다

목적 — 채점 항목 10 · 7점입니다. 보는 것은 「권한을 나눴는가」 이고, 그 증거는 403 한 장입니다. 401 만 있으면 「인증을 걸었다」 까지입니다.

절차 1 — 401 과 403 을 갈라 둡니다
코드뜻언제
401누구인지 모르겠다 아이디·비밀번호를 안 보냈거나 틀렸습니다
403누구인지는 알겠는데 권한이 없다 로그인은 됐는데 ADMIN 이 아닙니다
절차 2 — 계정 둘을 «해시로» 만듭니다

@Bean PasswordEncoder passwordEncoder() { return new BCryptPasswordEncoder(); } @Bean UserDetailsService users(PasswordEncoder pe) { UserDetails user = User.withUsername("user") .password(pe.encode("1234")).roles("USER").build(); UserDetails admin = User.withUsername("admin") .password(pe.encode("1234")).roles("ADMIN").build(); return new InMemoryUserDetailsManager(user, admin); }

roles("ADMIN") 로 넣고 hasRole("ADMIN") 로 봅니다. 스프링이 안에서 ROLE_ 를 붙여 줍니다. 우리가 ROLE_ADMIN 이라고 쓰면 두 번 붙어 안 맞습니다. 메모리에 두는 계정이라 해시가 대수롭지 않아 보여도, 습관을 여기서 들입니다.
절차 3 — 규칙을 «좁은 것부터» 겁니다

http.authorizeHttpRequests(a -> a .requestMatchers(HttpMethod.POST, "/api/link/sync").hasRole("ADMIN") // ① 좁은 것 .requestMatchers("/api/link/**").authenticated() // ② 넓은 것 .anyRequest().permitAll()); // ③ 나머지

절차 4 — 여섯 가지를 «실제로» 부릅니다

인증 없음 GET /api/link/posts → 401 user GET /api/link/posts → 200 인증 없음 POST /api/link/sync → 401 user POST /api/link/sync → 403 ← 항목 10 의 증거 admin POST /api/link/sync → 200 admin(틀린 비번) POST /api/link/sync → 401

마지막 줄을 눈여겨보십시오. 같은 admin 인데 비밀번호가 틀리면 403 이 아니라 401 입니다 — 누구인지 확인이 안 됐으니 권한을 따질 자리까지 못 갑니다.

절차 5 — 순서를 «뒤집어» 봅니다

「순서가 곧 규칙」 이라는 말을 확인합니다. ① 과 ② 를 바꿔 놓고 다시 띄우십시오.

http.authorizeHttpRequests(a -> a .requestMatchers("/api/link/**").authenticated() // 넓은 것을 먼저 .requestMatchers(HttpMethod.POST, "/api/link/sync").hasRole("ADMIN") .anyRequest().permitAll());

user POST /api/link/sync → 200 ← 막혀야 하는데 통과합니다 admin POST /api/link/sync → 200

오류도 경고도 없습니다. 조용히 ADMIN 규칙이 죽습니다. requestMatchers 는 위에서부터 차례로 걸립니다. /api/link/** 가 /api/link/sync 도 먼저 먹어 버려 아래 줄까지 내려가지 않습니다. 기동은 잘 되고 시연도 잘 됩니다 — admin 으로만 눌러 보면 똑같이 200 이기 때문입니다. user 로 눌러 봐야 드러납니다. 확인했으면 순서를 되돌리십시오.
절차 6 — 인증키를 저장소에서 뺍니다

공공데이터포털로 바꾸면 serviceKey 가 생깁니다. 코드에 박지 마십시오. 이것도 「송수신 보안」 에 들어갑니다.

# application-dev.properties ← 이 파일을 .gitignore 에 넣습니다 link.api.key=실제키 # .gitignore application-dev.properties

이미 한 번 커밋했다면 지워도 이력에 남습니다. 그때는 키를 새로 발급받는 것이 유일한 방법입니다.

안 될 때 볼 곳
이런 일이 생기면볼 곳
user 로 동기화가 200 으로 통과 절차 5 의 그 상태입니다. 규칙 순서를 되돌리십시오
맞는 비밀번호인데 401 비밀번호를 해시 안 하고 넣었습니다. pe.encode(...) 를 거쳐야 합니다
모든 요청이 403 roles("ROLE_ADMIN") 이라고 썼습니다. ROLE_ 를 빼십시오
POST 가 403 인데 권한은 맞음 CSRF 입니다. REST API 는 http.csrf(c -> c.disable()) 로 끕니다
브라우저에 로그인 창이 뜸 정상입니다. WWW-Authenticate 헤더를 보고 브라우저가 띄우는 것입니다 (실습 2)
기동 로그에 임시 비밀번호가 계속 찍힘 UserDetailsService 빈을 안 만들었습니다

제출물 — 설정 클래스 + 401 · 403 · 200 세 화면 + 순서를 뒤집었을 때의 200 화면 + 인증키 처리 방침

스스로 확인 — ① 403 화면이 있습니까 (401 만으로는 부족합니다) ② 비밀번호를 해시로 넣었습니까 ③ ROLE_ 를 직접 안 붙였습니까 ④ 좁은 규칙을 먼저 두었습니까 ⑤ 순서를 되돌렸습니까

    return postRepository.findById(id)
            .map(PostDTO::from)
            .orElseThrow(() -> new MyBizException("연계 데이터를 찾을 수 없습니다. id=" + id));
}

컨트롤러가 하는 일이 적습니다

세 메서드 모두 Service 를 부르고 감싸서 돌려주는 것이 전부입니다. 외부 호출도, 변환도, 예외 처리도 없습니다. 업무는 Service 에, HTTP 는 컨트롤러에 — 앞 교과에서 배운 그대로입니다.

예외를 잡지 않습니다

getPost 가 없는 id 를 받으면 Service 가 MyBizException 을 던집니다. 컨트롤러는 가만히 둡니다. 전역 핸들러가 받아 400 으로 내보냅니다.

여기에 try-catch 를 넣으면 오히려 나빠집니다. 전역 핸들러가 있는데 각자 잡으면 응답 모양이 매핑마다 달라집니다.

보안은 여기에 안 씁니다

/sync 가 ADMIN 전용이라는 것을 컨트롤러에는 적지 않습니다. SecurityConfig 한 곳에 모아 둡니다. 권한 규칙이 코드 곳곳에 흩어지면 무엇이 열려 있는지 알 수 없게 됩니다.

14연동 데이터의 무결성

두 번 받아도 건수가 같아야 합니다.

채점 항목

14 · 7점

연계에서 가장 흔한 사고

배치가 60초마다 돕니다. 한 시간이면 예순 번입니다. 한 번에 열 건씩 받아 오는데 그때마다 새로 쌓이면 한 시간 뒤에 600건이 됩니다. 같은 글이 예순 벌씩 있습니다.

이것을 막는 것이 Post 엔티티의 한 줄입니다.

@Entity @Table(name = "tbl_post")
public class Post {
    @Id                        // @GeneratedValue 가 없습니다
    private Long id;           // 외부 시스템의 식별자를 그대로 씁니다
    ⋯
}

save 가 어떻게 아는가

JPA 는 save 를 받으면 먼저 그 id 로 찾아봅니다. 있으면 UPDATE, 없으면 INSERT 를 보냅니다. 콘솔에 select 가 먼저 찍히는 까닭입니다.

Hibernate: select p1_0.id, ... from tbl_post p1_0 where p1_0.id=?
Hibernate: update tbl_post set body=?, create_at=?, title=?, user_id=? where id=?

무엇을 캡처하나

같은 동기화를 두 번 부르고 건수가 그대로인 것을 보입니다.

  1. POST /api/link/sync → {"count": 10}
  2. SELECT COUNT(*) FROM tbl_post; → 10
  3. 다시 POST /api/link/sync → {"count": 10}
  4. SELECT COUNT(*) FROM tbl_post; → 10 (그대로)

네 줄이면 채점 항목 14 의 증거가 됩니다. create_at 만 바뀌는 것을 함께 보이면 더 좋습니다. 덮어쓰기가 실제로 일어났다는 뜻이기 때문입니다.

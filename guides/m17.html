1. 이 교과의 범위

지금까지 배운 것이 다 나옵니다.

능력단위요소

개요 · 설계 · 구축 · 마무리

기술

MySQL · Spring Boot · React · Git

앞 교과 「공공데이터 융합 DBMS 구축」 에서도 공공데이터로 서비스를 만들었습니다. 그때는 주제와 뼈대가 주어졌고, 여기서는 주제부터 팀이 정합니다. 무엇을 만들지 정하는 일이 과제에 들어온다는 것이 가장 큰 차이입니다.

프로젝트 개요 및 수행 전략 수립
공공데이터포털에서 쓸 자료를 찾아 확보하고, 구조와 품질을 진단해 무엇을 만들지 정합니다. 요구사항을 목록으로 뽑고 일정과 역할을 계획서로 묶습니다.
프로젝트 시스템 설계
요구사항을 기능 단위로 정리해 유스케이스와 화면 흐름을 그립니다. 데이터 구조를 분석해 ERD 를 설계하고, 시스템 구성과 API 명세를 문서로 적습니다.
공공데이터 융합 웹서버 구축
설계대로 데이터베이스를 만들고 자료를 정제해 넣습니다. CRUD REST API 와 인증과 예외 처리를 구현하고, 화면에서 그 API 를 불러 실제로 도는 서비스로 잇습니다.
프로젝트 마무리 및 발표
테스트 케이스로 검증하고 오류와 조치를 정리합니다. 결과보고서로 묶어 발표하고, 설계와 구현을 왜 그렇게 했는지 답합니다.
성취기준기준의 말 이 평가에서
1.1 공공데이터포털에서 프로젝트 목적에 적합한 공공데이터를 검색 · 확보하고 출처 · 제공기관 · 갱신주기 · 이용허락범위를 명시 내려받기 화면을 찍고 네 값을 보고서에 적습니다
1.2 확보한 데이터의 구조와 활용 가능성을 분석하여 주제와 목표를 정의하고 요구사항을 도출 컬럼 진단표 · 주제와 목표 · 요구사항 목록 열 건
1.3 개발 범위 · 일정 · 역할분담 · 개발환경을 포함한 수행 전략을 프로젝트 계획서로 작성 일정표와 역할표를 계획서에 묶습니다
2.1 요구사항을 기능 단위로 정리하고 유스케이스와 화면 흐름을 설계 유스케이스 그림과 명세 · 화면 흐름도와 화면 목록
2.2 공공데이터의 구조를 분석하여 테이블 · 관계 · 제약조건을 갖춘 데이터베이스를 ERD 로 설계 표 둘 이상 · 외래키 한 건 이상 · 테이블 정의서
2.3 프론트엔드 · 백엔드 · 데이터베이스의 시스템 구성과 API 명세를 설계 문서로 작성 구성도 한 장과 엔드포인트 여덟 줄
3.1 설계한 ERD 에 따라 데이터베이스를 구축하고 확보한 공공데이터를 정제하여 적재 임시 표를 거쳐 정제한 뒤 적재 건수를 제시합니다
3.2 백엔드에서 REST API 와 CRUD 기능을 구현하고 인증 및 예외 처리를 적용 계층을 나눠 구현하고 조인 조회를 한 건 넣습니다
3.3 프론트엔드 화면에서 API 를 연동하여 조회 · 등록 · 수정 · 삭제가 동작하는 서비스를 통합 구축하고 검증 다섯 화면이 다 도는 장면을 캡처합니다
4.1 구현한 기능을 테스트 케이스에 따라 검증하고 결과 및 오류 조치 내역을 정리 테스트 케이스 표와 오류 조치 표
4.2 프로젝트 수행 과정과 결과물을 결과보고서와 실행화면 캡처로 취합 여섯 절짜리 보고서로 묶습니다
4.3 프로젝트 결과를 발표하고 질의에 대해 설계 · 구현의 근거를 설명 15분 발표와 질의응답

기준 열둘이 채점 항목 스물로 쪼개져 있습니다. 「분석하여」 와 「설계할 수 있다」 가 절반을 차지한다는 점을 보십시오. 만드는 것만큼 왜 그렇게 만들었는지를 본다는 뜻입니다.

2. 산출물 작성 실습

한 예를 끝까지 따라갑니다.

예시 주제

우리동네 주차장 찾기

예시 데이터

전국 주차장 정보 표준데이터

열여섯 단원을 네 묶음으로 나누었고 능력단위요소와 그대로 짝이 맞습니다. 앞 여섯이 개요와 전략, 다음 다섯이 설계, 그 다음 넷이 구축, 마지막 하나가 마무리입니다.

주제는 팀이 정하지만 교안에서는 한 가지 예를 끝까지 따라갑니다. 공공데이터포털의 「전국 주차장 정보 표준데이터」 로 만드는 「우리동네 주차장 찾기」 입니다. 같은 예가 데이터 진단 · ERD · API · 화면까지 이어지므로 앞 단계의 결정이 뒤에 어떻게 나타나는지를 볼 수 있습니다.

여러분의 주제는 저마다 다릅니다. 그래도 뼈대는 같습니다 — 되풀이되는 값을 찾아 표를 나누고, 목록과 상세와 등록과 수정과 삭제를 만들고, 로그인을 걸고, 검색을 붙입니다. 예를 그대로 옮기지 말고 같은 자리에 무엇이 오는지를 보십시오.

단계마다 산출물을 그 자리에서 채우십시오. 마무리에 배정된 시간은 여덟 시간, 하루뿐입니다. 보고서를 그날 쓰기 시작하면 여섯 절 중 서너 절이 빈 채로 나갑니다.

캡처

동작누르면확인할 것
목록로그인 후 첫 화면 총 건수가 수천 이상이고 쪽이 나뉩니다
검색검색어를 넣고 검색건수가 줄어듭니다
상세한 줄을 누름 다른 표에서 온 값이 함께 보입니다

로그아웃 상태로 목록 주소를 쳐 보십시오. 로그인 화면으로 튕겨 나가야 합니다. 그냥 목록이 보이면 인증이 걸리지 않은 것이고, 채점 항목 13 의 8점이 빕니다. 이 장면도 캡처로 남겨 두십시오.

진단이란 세 가지 세기입니다

「분석」 이라는 말에 겁먹을 것 없습니다. 세는 일이 전부입니다.

몇 줄인가
수천 행 조건을 채우는지 봅니다. 엑셀로 열어도 되고 wc -l 로 세도 됩니다.
칸마다 빈 값이 얼마나 되는가
절반 넘게 비어 있으면 그 칸은 안 씁니다. 조금 비어 있으면 채우거나 그 줄을 버립니다.
서로 다른 값이 몇 개인가
18,342줄에 서로 다른 값이 2,180개뿐이면 되풀이되고 있다는 뜻입니다. 나눌 표가 바로 거기 있습니다.
# 되풀이되는 칸 찾기 — 이 한 줄이 ERD 의 출발점입니다
> cut -d, -f11 parking.csv | sort -u | wc -l
2181                     # 머리글 한 줄을 빼면 2,180개

# 값이 몇 가지뿐인 칸 — 검색 조건으로 쓰기 좋습니다
> cut -d, -f3 parking.csv | sort | uniq -c
  11204 공영
   7138 민영
엑셀로 열 때는 CSV 를 그냥 두 번 눌러 열지 마십시오. 한글이 깨지고 앞자리 0 이 사라집니다. 「데이터 → 텍스트 나누기」 로 인코딩을 UTF-8 로 지정해 불러오거나, 메모장에서 한 번 열어 인코딩을 확인하고 여십시오.

표를 나누는 기준

정규화라는 말을 몰라도 됩니다. 같은 값이 되풀이되면 뗀다는 것 하나입니다.

원본 CSV 한 줄나눈 뒤
… 관리기관명 = 대구시설공단, 전화번호 = 053-… 주차장 줄에는 agency_id = 41 만 남고, 이름과 전화번호는 관리기관 표에 한 번만
나누면 좋은 점안 나누면
고칠 곳이 하나 전화번호가 바뀌면 수백 줄을 고쳐야 합니다
자료가 어긋나지 않음 같은 기관인데 이름이 조금씩 달라진 줄이 섞입니다
조인 조회를 넣을 수 있음 구축 요건의 외래키 관계 한 건 이상을 못 채웁니다

원본에 없는 칸을 만들어 넣기

-- 소재지도로명주소 = "대구광역시 달서구 학산로 40"
sido    = SUBSTRING_INDEX(주소, ' ', 1)                             -- 대구광역시
sigungu = SUBSTRING_INDEX(SUBSTRING_INDEX(주소, ' ', 2), ' ', -1)   -- 달서구

지역별 보기를 하려면 주소 전체로 LIKE 검색을 해야 하는데 느립니다. 미리 잘라 칸으로 두고 인덱스를 걸면 빨라집니다. 이렇게 원본에 없는 칸을 만들어 내는 것도 설계입니다. 보고서에 「주소에서 잘라 만든 칸」 이라고 적어 두십시오.

기본키를 원본의 관리번호로 삼지 마십시오. 원본이 갱신되면서 번호 체계가 바뀔 수 있고, 길이도 깁니다. id BIGINT AUTO_INCREMENT 를 기본키로 두고 원본 번호는 code 칸에 UNIQUE 로 남기면 중복 적재도 막고 원본과의 연결도 지킬 수 있습니다.

평문으로 저장하면 데이터베이스를 보는 사람이 모든 비밀번호를 압니다. 해시는 되돌릴 수 없으므로 로그인할 때는 들어온 값을 같은 방식으로 해시해 둘을 견줍니다.

규칙 순서가 곧 규칙입니다

.requestMatchers("/api/auth/**").permitAll()                        // ① 먼저 만난 것이
.requestMatchers(HttpMethod.DELETE, "/api/parking/**").hasRole("ADMIN")
.anyRequest().authenticated()                                       // ③ 마지막 그물

anyRequest() 를 맨 위에 두면 그 아래 줄은 한 번도 쓰이지 않습니다. 좁은 규칙을 위에, 넓은 규칙을 아래에 두십시오.

401 과 403 을 갈라 찍기

코드해 보는 방법무엇을 증명하나
401토큰 없이 /api/parking 호출 로그인 없이는 못 본다
403일반 회원 토큰으로 삭제 호출 권한을 갈라 두었다
400이름을 비우고 등록입력 검증이 돈다
404없는 번호로 상세 호출없는 자원을 가린다

네 화면이 있으면 인증과 예외 처리가 함께 증명됩니다. 채점 항목 13 이 둘을 한 칸에 담았으므로 둘 다 있어야 8점이 채워집니다.

전역 예외 처리의 500 응답에서 예외 메시지를 그대로 내보내지 마십시오. 테이블 이름이나 쿼리가 그대로 나가면 보안 문제가 됩니다. 「서버 오류가 발생했습니다」 로 가리고 자세한 내용은 로그에 남깁니다.

CORS 를 먼저 열어 둡니다

// 화면은 3000번, 서버는 8080번이라 브라우저가 막습니다
@Configuration
public class CorsConfig implements WebMvcConfigurer {
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")
                .allowedOrigins("http://localhost:3000")
                .allowedMethods("GET", "POST", "PUT", "DELETE")
                .allowedHeaders("*");
    }
}

이것을 안 해 두면 서버는 멀쩡히 도는데 화면에서만 안 됩니다. 브라우저 콘솔에 CORS policy 라는 말이 보이면 여기부터 봅니다. 구축 첫날에 열어 두면 나중에 헤매지 않습니다.

검색은 목록과 한 화면에

// 검색어가 바뀌면 첫 쪽부터 다시 불러옵니다
function onSearch(word) {
  setPage(0);          // 이 줄을 빠뜨리면 3쪽에서 검색해 빈 화면이 나옵니다
  setKw(word);
}

검색 화면을 따로 만들 것 없이 목록 화면의 검색 칸이면 됩니다. 서버 쪽 쿼리가 :kw 가 없으면 전체를 주도록 되어 있으므로 같은 API 로 목록과 검색이 다 됩니다.

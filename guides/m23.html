프로젝트 폴더를 그대로 주면

IDE 에서 실행 버튼을 누르면 잘 돌아갑니다. 그 프로젝트 폴더를 통째로 압축해 옆 사람에게 주면 대개 못 돌립니다. IDE 를 안 깔았거나, 깔았어도 프로젝트를 여는 법을 모르거나, 열었어도 JDK 설정이 달라 빨간 줄이 뜹니다.

IDE 는 실행 버튼 하나를 누를 때 뒤에서 여러 일을 합니다. 소스를 찾아 컴파일하고, 결과물을 어디에 둘지 정하고, 클래스패스를 맞추고, 어느 클래스의 main 을 부를지 골라 줍니다. 그 일들이 사라진 상태로 파일만 건네받은 셈입니다.

패키징이 하는 일

소스 .java 파일 여럿 │ 컴파일 ↓ 클래스 .class 파일 여럿 │ 묶기 ↓ 실행 파일 .jar 하나 — 어느 클래스를 부를지도 안에 적혀 있습니다 │ 담기 ↓ 배포본 실행 파일 + 매뉴얼 + 설정 + 실행 스크립트

맨 아래까지 가야 남이 쓸 수 있습니다. 가운데에서 멈춘 것을 주면 받는 쪽이 나머지를 알아서 해야 하고, 그것을 알아서 할 수 있는 사람은 개발자뿐입니다.

실습 1 매니페스트 없이 묶어 보고 안 도는 것을 확인한다

목적 — 묶기만 하면 될 것 같은데 안 됩니다. 한 번 막혀 보면 패키징이 「압축하는 일」이 아니라는 것이 분명해집니다. 이 교과의 첫 오류 메시지를 여기서 만납니다.

절차 1 — 예제를 만든다

src\kr\sport\Main.java package kr.sport; public class Main { public static final String VERSION = "1.0.0"; public static void main(String[] args) { System.out.println("체육시설 예약 " + VERSION); FacilityStore f = new FacilityStore(); ReservationStore r = new ReservationStore(); f.add(1, "중앙체육관", 2000); f.add(2, "달성운동장", 1500); r.add(101, 1, "2026-10-01", 10); System.out.println("시설 " + f.size() + "곳 · 예약 " + r.size() + "건"); } }

FacilityStore 와 ReservationStore 는 각각 맵과 리스트를 하나씩 들고 add 와 size 만 있으면 됩니다. 앞 교과에서 만든 프로그램이 있으면 그것을 써도 됩니다. 클래스가 셋쯤 되어야 묶는 맛이 납니다.

절차 2 — 컴파일한다

> javac -encoding utf-8 -d build\classes src\kr\sport\*.java > dir /b /s build\classes\kr\sport …\build\classes\kr\sport\FacilityStore.class …\build\classes\kr\sport\Main.class …\build\classes\kr\sport\ReservationStore.class

소스 셋에 클래스 셋이 나왔습니다. -d 로 출력 폴더를 따로 준 것에 주의하십시오. 안 주면 소스 옆에 .class 가 쌓여 나중에 묶을 때 골라내야 합니다.

절차 3 — 매니페스트 없이 묶어 본다

> jar cf build\sport-nomanifest.jar -C build\classes . > java -jar build\sport-nomanifest.jar no main manifest attribute, in build\sport-nomanifest.jar

파일은 만들어졌는데 실행이 안 됩니다. 안에 클래스가 다 들어 있지만 어느 클래스의 main 을 불러야 할지 적혀 있지 않기 때문입니다. 묶는 것과 실행 가능하게 만드는 것이 다른 일이라는 뜻입니다.

절차 4 — 매니페스트를 넣어 다시 묶는다

build\MANIFEST.MF Main-Class: kr.sport.Main Implementation-Title: sport-reservation Implementation-Version: 1.0.0 Build-Jdk: 21.0.2

> jar cfm build\sport-1.0.0.jar build\MANIFEST.MF -C build\classes . > java -Dstdout.encoding=utf-8 -jar build\sport-1.0.0.jar 체육시설 예약 1.0.0 시설 2곳 · 예약 1건

이제 돕니다. 달라진 것은 네 줄짜리 텍스트 파일 하나입니다.

절차 5 — 마지막 줄바꿈을 빼 본다

# Main-Class 줄 끝에 줄바꿈이 없는 매니페스트를 만들어 묶습니다 > java -jar build\nonl.jar no main manifest attribute, in build\nonl.jar # 실제로 들어간 매니페스트를 꺼내 보면 Manifest-Version: 1.0 Created-By: 21.0.2 (Oracle Corporation)

Main-Class 줄이 통째로 사라졌습니다. 매니페스트는 마지막 줄도 줄바꿈으로 끝나야 하고, 안 그러면 그 줄을 무시합니다. 오류도 경고도 없습니다. 메모장으로 만들면 이 사고가 자주 납니다. no main manifest attribute 가 나오면 이것부터 보십시오.

# Main-Class: Main 이라고 패키지 없이 적으면 Error: Could not find or load main class Main Caused by: java.lang.ClassNotFoundException: Main

배포본이 어떻게 생겼는지

sport-1.0.0.zip 을 풀면 sport-1.0.0/ bin/ run.bat 눌러서 실행합니다 lib/ sport-1.0.0.jar 프로그램 본체 config/ app.properties 고칠 수 있는 설정 docs/ 설치매뉴얼.md 사용자매뉴얼.md 릴리즈노트.md

매니페스트 파일은 마지막 줄도 줄바꿈으로 끝나야 합니다. 끝에 줄바꿈이 없으면 그 줄이 통째로 무시됩니다. Main-Class 를 맨 마지막에 적어 두고 no main manifest attribute 로 한참 헤매는 일이 흔합니다. 메모장으로 만들 때 특히 그렇습니다.

같은 소스인데 결과물에 다른 숫자가 박힙니다. 52 는 자바 8, 65 는 자바 21 입니다. 낮은 숫자로 만든 것은 높은 판에서도 돌지만 그 반대는 안 됩니다.

받는 쪽 JDK 가 내 것보다 낮으면 UnsupportedClassVersionError 가 납니다. 이것은 코드 문제가 아니라 환경 문제인데, 메시지를 처음 보면 코드를 뒤지게 됩니다. 실행 환경 표에 「JDK 21 이상」이라고 적어 두는 일이 이 사고를 막는 유일한 방법입니다.

내 환경을 확인하는 명령

마지막 두 줄이 다른 것에 주의하십시오. 자바 18 부터 file.encoding 의 기본값이 UTF-8 이 되었지만 윈도우 콘솔은 여전히 MS949 로 찍습니다. 그래서 한글이 깨지는 일이 생깁니다 — 프로그래밍 언어 응용 교과에서 다뤘습니다.

실습 5 클래스 파일에 박힌 버전 숫자를 꺼내 본다

목적 — 실행 환경을 적으라고 하면 대개 「JDK 필요」로 끝냅니다. 판까지 적어야 하는 까닭이 클래스 파일 안에 있습니다. 그 숫자를 직접 꺼내 보면 왜 적어야 하는지가 분명해집니다.

절차 1 — 두 가지 목표로 컴파일한다

> javac --release 8 -encoding utf-8 -d build\c8 src\kr\sport\*.java warning: [options] source value 8 is obsolete and will be removed in a future release warning: [options] target value 8 is obsolete and will be removed in a future release warning: [options] To suppress warnings about obsolete options, use -Xlint:-options. > javac --release 21 -encoding utf-8 -d build\c21 src\kr\sport\*.java

경고가 셋 나오지만 컴파일은 됩니다. 자바 8 이 오래되어 곧 지원이 끊긴다는 안내입니다. 소스는 한 글자도 안 바꿨고 --release 숫자만 다릅니다.

절차 2 — 박힌 숫자를 본다

> javap -v -cp build\c8 kr.sport.Main | findstr version minor version: 0 major version: 52 > javap -v -cp build\c21 kr.sport.Main | findstr version minor version: 0 major version: 65

44 가 자바 1.0 이고 한 판마다 1씩 오릅니다. 8 은 44+8 로 52, 21 은 44+21 로 65 입니다. 이 숫자가 클래스 파일 맨 앞쪽에 박혀 있습니다.

절차 3 — 둘 다 돌려 본다

> java -Dstdout.encoding=utf-8 -cp build\c8 kr.sport.Main 체육시설 예약 1.0.0 시설 2곳 · 예약 1건 > java -Dstdout.encoding=utf-8 -cp build\c21 kr.sport.Main 체육시설 예약 1.0.0 시설 2곳 · 예약 1건

JDK 21 에서는 둘 다 돕니다. 낮은 숫자는 높은 판에서 받아 줍니다. 반대는 안 됩니다. 65 가 박힌 파일을 자바 17 에 주면 거부합니다.

그때 나오는 것이 UnsupportedClassVersionError 입니다. 메시지에 클래스 파일의 숫자와 지금 런타임이 받아 주는 숫자가 같이 나오므로, 절차 2 의 표에 대 보면 어느 판이 필요한지 바로 나옵니다. 코드 문제가 아니라 환경 문제인데 처음 보면 코드를 뒤지게 됩니다. 낮은 판이 깔린 컴퓨터가 있으면 직접 한 번 재현해 보십시오.
절차 4 — 내 환경을 확인한다

마지막 두 줄이 다릅니다. 자바가 파일을 읽고 쓸 때는 UTF-8 을 쓰는데 윈도우 콘솔은 MS949 로 찍습니다. 그래서 한글이 깨지고 -Dstdout.encoding=utf-8 이 필요합니다.

비밀번호는 이 파일에도 넣지 마십시오. 배포본을 받은 사람 누구나 읽을 수 있습니다. 받는 쪽이 설치할 때 직접 넣도록 매뉴얼에 적고, 파일에는 db.password= 처럼 빈 칸만 두십시오. 학습모듈도 설정 파일이 안전한 경로에 저장되는지 확인하라고 적고 있습니다.
실습 6 배포본을 만들어 다른 폴더에서 돌려 본다

목적 — 이 교과에서 가장 중요한 실습입니다. 개발 폴더에서는 되고 다른 곳에서는 안 되는 일이 여기서 갈립니다. 실행 스크립트의 경로 한 줄이 그 차이를 만듭니다.

dist\sport-1.0.0\config\app.properties port=8080 db.url=jdbc:mysql://localhost:3306/sportdb db.user= db.password=

아래 두 줄을 빈 칸으로 둔 것에 주의하십시오. 받는 쪽이 설치할 때 직접 넣습니다. 여기에 값을 적어 배포하면 배포본을 받은 사람 누구나 볼 수 있습니다.

절차 3 — 실행 스크립트를 쓴다

빌드 결과물을 git 에 넣지 않는 까닭이 있습니다. 소스에서 다시 만들 수 있기 때문입니다. .class 와 .jar 를 커밋하면 파일이 바뀔 때마다 통째로 저장되어 저장소가 빠르게 커집니다. .gitignore 에 build/ 와 dist/ 를 적어 두십시오. 배포본 자체는 따로 보관합니다 — 실습 15.
실습 13 저장소를 만들고 무엇을 넣고 뺄지 정한다

목적 — 형상관리는 도구 이야기가 아니라 무엇을 남길지 정하는 일입니다. 소스는 넣고 빌드 결과물은 안 넣습니다. 그 경계를 .gitignore 한 파일이 정합니다.

절차 1 — 저장소를 만든다

> cd 소스 > git init > git config user.name "훈련생" > git config user.email "student@example.com"

이름과 메일은 커밋마다 같이 남습니다. 누가 고쳤는지가 기록되어야 형상관리입니다. 회사 계정이 있으면 그것으로 적습니다.

절차 2 — 넣지 않을 것을 적는다

.gitignore build/ dist/ *.class *.log config/app.properties

왜 빼는가
build/ · *.class 소스에서 다시 만들 수 있습니다
dist/배포본은 releases 에 따로 보관합니다
*.log돌릴 때마다 바뀝니다
config/app.properties 환경마다 다르고 비밀번호가 들어갈 수 있습니다

마지막 줄 대신 app.properties.sample 을 넣어 두는 것이 흔한 방식입니다. 항목 이름은 알려 주되 값은 안 넣습니다.

절차 3 — 첫 커밋을 한다

> git add -A > git commit -m "최초 커밋 — 예약 기능 뼈대" > git log --oneline ea9abf5 최초 커밋 — 예약 기능 뼈대

절차 4 — 무엇이 들어갔는지 확인한다

> git ls-files .gitignore src/kr/sport/FacilityStore.java src/kr/sport/Main.java src/kr/sport/ReservationStore.java

.class 도 build 도 안 들어갔습니다. .gitignore 가 일하고 있다는 뜻입니다. 여기에 클래스 파일이 보이면 무시 규칙이 안 먹은 것입니다.

이미 커밋한 파일은 .gitignore 에 적어도 계속 추적됩니다. 무시 규칙은 아직 추적하지 않는 파일에만 적용됩니다. 실수로 커밋했으면 git rm --cached 파일이름 으로 빼야 합니다. 비밀번호 파일을 커밋한 경우에는 그것만으로 부족합니다. 이력에 남아 있으므로 그 값은 유출된 것으로 보고 바꾸십시오.
절차 5 — 기준선을 그린다

개발 ─────●────────●────────●─────→ │ │ │ 기준선 기준선 기준선 v1.0.0 v1.1.0 v1.2.0 기준선 이후의 변경은 기록하고 승인받아 들어갑니다

기준선은 「여기까지는 확정」이라고 못을 박는 지점입니다. 배포한 판이 곧 기준선이 되는 것이 가장 흔한 방식입니다. 기준선이 없으면 무엇과 견주어 바뀌었다고 말할 기준이 없습니다.

세 가지가 따로 보이지만 원인은 하나입니다. 변경이 기록되지 않아서입니다. 커밋 하나가 이 셋을 다 막아 줍니다.

목적 — 태그를 붙여 두었으면 꺼낼 수 있어야 합니다. 꺼내 본 적이 없으면 붙여만 둔 것입니다. 고객이 옛 판의 문제를 물어 오는 상황을 미리 겪어 봅니다.

절차 1 — 이전 판으로 간다

> git checkout v1.0.0 Note: switching to 'v1.0.0'. You are in 'detached HEAD' state. You can look around, make experimental changes and commit them, and you can discard any commits you make in this state without impacting any branches by switching back to a branch.

긴 안내문이 나오지만 오류가 아닙니다. 지금 어느 브랜치에도 서 있지 않다는 뜻입니다. 들여다보기만 하고 브랜치로 돌아오면 됩니다.

절차 2 — 소스가 바뀐 것을 확인한다

> findstr VERSION src\kr\sport\Main.java public static final String VERSION = "1.0.0"; System.out.println("체육시설 예약 " + VERSION); > git checkout master > findstr VERSION src\kr\sport\Main.java public static final String VERSION = "1.1.0"; System.out.println("체육시설 예약 " + VERSION);

파일을 손대지 않았는데 내용이 바뀝니다. 태그 이름 하나로 그 시점의 소스 전체가 돌아옵니다. 이것이 형상관리가 배포본 관리에 유용하다는 말의 실제 내용입니다.

절차 3 — 이전 판을 다시 빌드해 본다

> git checkout v1.0.0 > javac -encoding utf-8 -d build\old src\kr\sport\*.java > java -Dstdout.encoding=utf-8 -cp build\old kr.sport.Main 체육시설 예약 1.0.0 시설 2곳 · 예약 1건 > git checkout master

예약이 1건입니다. 1.1.0 에서는 2건이었습니다. 그 시점의 프로그램이 그대로 돌아옵니다. 고객이 「1.0.0 에서 나던 문제」를 물어 오면 이렇게 재현합니다.

넷째 줄이 헷갈립니다. 다시 만들 수 있는데 왜 보관하는가. 다시 빌드하면 같은 소스라도 결과 파일의 바이트가 조금 달라집니다. 그러면 해시 값도 달라집니다. 실제로 나간 바로 그 파일이 있어야 「이 파일이 맞습니다」라고 말할 수 있습니다.

두 값이 같으면 백업이 온전합니다. 판을 올릴 때마다 이전 판 하나를 골라 셋을 확인해 보십시오. 오래 안 건드린 백업이 깨져 있는 일이 실제로 있습니다.

비밀번호를 커밋했다가 다음 커밋에서 지워도 이력에는 남습니다. 저장소를 받은 사람은 누구나 git log -p 로 꺼내 볼 수 있습니다. git rm --cached 로 추적을 끊어도 과거 커밋은 그대로입니다. 한 번 올라간 값은 유출된 것으로 보고 바꾸십시오. 이력을 지우는 방법이 있기는 하지만 협업 중이면 쓰기 어렵습니다.

이 교안이 쓰는 것

언어 자바 21 — 앞 교과에서 쓰던 것 그대로 테스트 틀 JUnit 6 — jar 몇 개면 되고 설치가 없습니다 커버리지 직접 셉니다. 도구 없이 손으로 한 번 세어 봅니다 서버 JDK 에 들어 있는 HTTP 서버 — 따로 깔 것이 없습니다 부하 도구 직접 만듭니다. 스레드 여럿으로 동시에 부릅니다 모니터링 jcmd — JDK 에 들어 있습니다 예제 공공 체육시설 예약 — 앞 교과들과 같은 예제

학습모듈은 성능 도구로 JMeter 를, 모니터링 도구로 Scouter 나 Prometheus 를 듭니다. 실무에서는 그쪽을 씁니다. 이 교안이 부하 도구를 직접 만드는 까닭은 따로 깔 것이 없어서이고, 또 하나는 도구가 내놓는 TPS 와 응답 시간이 어떻게 계산된 값인지 한 번 손으로 세어 보기 위해서입니다. 숫자의 뜻을 알면 남의 보고서도 읽을 수 있습니다.

예약 인원이 1명 이상 30명 이하여야 한다는 규칙이 있다고 합시다. 만든 사람은 10을 넣어 보고 「됩니다」라고 말합니다. 테스터는 0 · 1 · 30 · 31 을 넣습니다.

if (headcount < 1) return "인원은 1명 이상이어야 합니다"; if (headcount >= 30) return "정원을 초과했습니다"; return "OK";

둘째 줄이 >= 입니다. > 여야 합니다. 30명은 받아야 하는데 거부합니다. 10을 넣으면 이 결함이 안 나옵니다. 30을 넣어야 나옵니다.

에러 · 오류사람이 저지른 실수 > 를 >= 로 쓴 일

실패 · 문제그 결함이 실행될 때 나타나는 현상 30명이 거부되는 화면

셋을 구별해야 하는 까닭이 있습니다. 실패를 봐야 결함을 찾고, 결함을 봐야 에러를 압니다. 실패가 안 나타나면 결함이 있어도 모릅니다. 30을 안 넣으면 이 결함은 계속 숨어 있습니다.

실습 1 내가 넣어 본 값으로는 못 찾는 결함을 겪어 본다

목적 — 테스트를 잘못 배우면 「돌려 봤다」가 「테스트했다」가 됩니다. 둘이 어떻게 다른지 한 번 겪어 두면 그 뒤로는 값을 고르는 눈이 달라집니다. 이 교과의 첫 결함을 여기서 만납니다.

절차 1 — 시험할 코드를 만든다

src\kr\sport\Reservation.java package kr.sport; public class Reservation { public static String validate(int headcount) { if (headcount < 1) return "인원은 1명 이상이어야 합니다"; if (headcount >= 30) return "정원을 초과했습니다"; return "OK"; } }

요구사항은 「1명 이상 30명 이하」입니다. 지금은 요구사항을 모른다고 치고 코드만 보십시오. 어디가 잘못되었는지 눈으로는 잘 안 보입니다.

절차 2 — 만든 사람처럼 넣어 본다

Try.java import kr.sport.Reservation; public class Try { public static void main(String[] a) { for (String s : a) { int n = Integer.parseInt(s); System.out.printf("validate(%-4d) → %s%n", n, Reservation.validate(n)); } } }

> javac -encoding utf-8 -d build\classes src\kr\sport\*.java > javac -encoding utf-8 -cp build\classes -d build\classes Try.java > java -Dstdout.encoding=utf-8 -cp build\classes Try 10 50 -3 validate(10 ) → OK validate(50 ) → 정원을 초과했습니다 validate(-3 ) → 인원은 1명 이상이어야 합니다

셋 다 맞습니다. 여기까지 해 보고 「됩니다」라고 말하게 됩니다. 세 값이 나쁜 값은 아닙니다. 구간마다 하나씩 잘 골랐습니다. 그런데 이 셋으로는 안 나오는 결함이 있습니다.

절차 3 — 경계를 넣어 본다

> java -Dstdout.encoding=utf-8 -cp build\classes Try 0 1 30 31 validate(0 ) → 인원은 1명 이상이어야 합니다 validate(1 ) → OK validate(30 ) → 정원을 초과했습니다 validate(31 ) → 정원을 초과했습니다

셋째 줄이 틀렸습니다. 요구사항은 30명 이하이므로 30명은 받아야 합니다. > 로 써야 할 것을 >= 로 써서 한 글자가 더 붙었습니다. 이 결함은 10 이나 50 을 아무리 넣어도 안 나옵니다. 30 을 넣어야 나옵니다. 무슨 값을 넣느냐가 결함을 찾느냐 마느냐를 정합니다.
절차 4 — 셋을 구별해 적는다
말이 경우에 해당하는 것
에러 · 오류사람이 > 를 >= 로 쓴 일 머릿속에서 일어난 일
결함 · 버그if (headcount >= 30) 줄 파일에 남아 있는 것

절차 5 — 왜 못 찾았는지 적어 본다

넣어 본 값 10 · 50 · -3 못 찾은 까닭 세 값이 전부 경계에서 멀리 떨어져 있었습니다 10 은 1~29 구간 한가운데 50 은 30 을 한참 넘었고 -3 은 0 을 한참 밑돕니다 찾으려면 0 · 1 · 30 · 31 — 구간이 갈리는 자리 앞뒤

넷째와 다섯째가 짝입니다

결함이 몰려 있다는 것은 거기를 집중해서 보라는 뜻이고, 같은 케이스만 돌리면 안 나온다는 것은 케이스를 바꿔 가라는 뜻입니다. 둘을 같이 쓰면 「결함이 나온 모듈을 새 케이스로 다시 본다」가 됩니다.

1회차 예약 모듈에서 결함 3건, 시설 모듈에서 0건 2회차 예약 모듈을 새 케이스로 다시 봅니다 → 결함 2건 더 3회차 같은 케이스를 또 돌립니다 → 0건 (살충제 패러독스)

일곱째가 가장 어렵습니다

요구사항을 잘못 이해하고 만들었으면 그 잘못된 대로 잘 도는 프로그램이 나옵니다. 테스트는 전부 통과하는데 쓸 수 없는 물건입니다. 그래서 테스트 케이스를 코드가 아니라 요구사항명세서에서 뽑습니다.

코드를 보고 테스트 케이스를 만들면 코드의 잘못을 따라갑니다. >= 로 쓰인 코드를 보고 「30은 초과」라고 케이스를 만들면 그 케이스는 통과하고 결함은 안 나옵니다. 요구사항명세서에 「30명 이하」라고 적혀 있으니 30은 OK 여야 합니다. 실습 4 에서 이 차이를 직접 봅니다.

동치분할

인원은 1명 이상 30명 이하 구간 A … -1, 0 거부되어야 함 구간 B 1 … 30 받아야 함 구간 C 31, 32 … 거부되어야 함 같은 구간 안에서는 어느 값을 넣어도 프로그램이 같게 굴 것이라고 봅니다 → 구간마다 하나씩만 고릅니다: -5 · 15 · 50

무한한 입력값을 셋으로 줄였습니다. 이것이 둘째 원칙 「완벽한 테스팅은 불가능하다」에 대한 답입니다. 다만 이 셋으로는 >= 결함이 안 잡힙니다.

경곗값 분석

구간이 갈리는 자리 앞뒤를 고릅니다 0 1 구간 A 와 B 의 경계 30 31 구간 B 와 C 의 경계 → 0 · 1 · 30 · 31

결함은 경계에 몰립니다. < 와 <=, +1 을 넣을지 말지, for 문의 끝 조건 — 사람이 헷갈리는 자리가 전부 경계입니다. 실습 4 에서 동치분할 케이스는 전부 통과하는데 경곗값 케이스 하나가 실패하는 것을 직접 봅니다. 케이스를 여섯 개만 더 만들면 잡히는 결함입니다.

둘을 같이 쓰면

| 번호 | 입력 | 기대 결과 | 나온 기법 | |------|------|-----------|-----------| | 1 | -5 | 거부 | 동치분할 A | | 2 | 0 | 거부 | 경곗값 | | 3 | 1 | OK | 경곗값 | | 4 | 15 | OK | 동치분할 B | | 5 | 30 | OK | 경곗값 | | 6 | 31 | 거부 | 경곗값 | | 7 | 50 | 거부 | 동치분할 C |

일곱 개로 이 규칙은 거의 다 봅니다. 나온 기법 칸을 적어 두십시오. 케이스를 왜 그 값으로 골랐는지 묻는 자리에 그대로 답이 됩니다.

실습 4 동치분할은 통과하고 경곗값은 실패하는 것을 본다

목적 — 두 기법을 말로 배우면 「둘 다 쓰라」로 끝납니다. 한쪽만 썼을 때 무엇을 놓치는지 직접 보면 왜 둘이 필요한지 분명해집니다. 같은 코드에 두 테스트를 돌려 견줍니다.

절차 1 — 동치분할로 구간을 나눈다

근거

학습모듈 1-1

용어

화이트박스 · 구문 · 분기 커버리지

커버리지가 답하는 물음

「테스트를 충분히 했습니까」에 말로 답하면 설득이 안 됩니다. 커버리지는 그 물음에 숫자로 답합니다. 코드의 몇 퍼센트를 지나갔는지를 셉니다.

구문 커버리지

S1 if (headcount < 1) S2 return "인원은 1명 이상이어야 합니다"; S3 if (headcount > 30) S4 return "정원을 초과했습니다"; S5 return "OK";

넣은 값지나간 구문커버리지
15 하나S1 · S3 · S53 / 5 = 60%
15 · 0S1 · S2 · S3 · S54 / 5 = 80%
15 · 0 · 31전부5 / 5 = 100%

동치분할로 뽑은 세 값이 구문 커버리지 100퍼센트를 만듭니다. 기법이 우연히 맞아떨어진 것이 아니라, 구간을 나누는 일과 분기를 나누는 일이 대개 같기 때문입니다.

구문 100퍼센트가 충분하지 않은 까닭

if (a > 0 && b > 0) { … } a=1, b=1 한 번만 넣어도 이 줄은 「지나갔다」로 셉니다 그런데 a>0 이 거짓인 경우는 한 번도 안 봤습니다

커버리지 종류무엇을 세는가더 엄격한가
구문각 줄을 지나갔는가가장 느슨합니다
분기 · 결정각 if 의 참과 거짓을 다 봤는가 구문보다 엄격합니다
조건&& 로 이어진 조건 하나하나 분기보다 엄격합니다
변경 조건 결정각 조건이 결과를 바꾸는 경우 항공·의료에서 요구합니다

아래로 갈수록 케이스가 많아집니다. 훈련생 과제는 구문과 분기까지면 충분하고, 실무에서도 대개 그 선에서 목표를 잡습니다.

커버리지 100퍼센트가 결함이 없다는 뜻은 아닙니다. 모든 줄을 지나갔어도 그 줄에 넣은 값이 경계가 아니면 결함이 안 나옵니다. 실습 5 에서 구문 커버리지 100퍼센트인데 >= 결함이 안 잡히는 것을 확인합니다. 커버리지는 「얼마나 봤는가」이지 「얼마나 잘 봤는가」가 아닙니다.
실습 5 커버리지 100퍼센트인데 결함이 안 잡히는 것을 본다

목적 — 커버리지를 처음 배우면 100퍼센트가 목표처럼 보입니다. 100퍼센트를 채우고도 결함을 못 찾는 경우를 직접 만들어 보면 이 숫자가 무엇을 재는 값인지 분명해집니다.

절차 1 — 구문마다 도장을 찍는다

cov\kr\sport\CovBug.java static final Set<String> 지남 = new LinkedHashSet<>(); static String validate(int n) { 지남.add("S1"); if (n < 1) { 지남.add("S2"); return "인원은 1명 이상이어야 합니다"; } 지남.add("S3"); if (n >= 30) { 지남.add("S4"); return "정원을 초과했습니다"; } // 버그 지남.add("S5"); return "OK"; }

구문 다섯에 이름을 붙이고 지나갈 때마다 집합에 넣습니다. 집합이라 같은 것을 여러 번 지나도 하나로 셉니다. 실무에서는 도구가 이 일을 자동으로 해 주는데, 손으로 한 번 해 보면 도구가 내놓는 숫자의 뜻을 압니다.

절차 2 — 동치분할 셋만 돌린다

구문 커버리지가 100퍼센트인데 결함은 하나도 안 나왔습니다. 다섯 줄을 전부 지나갔습니다. 그런데 지나갈 때 넣은 값이 경계가 아니었습니다. 커버리지는 「어느 줄을 지나갔는가」를 세지 「그 줄을 제대로 시험했는가」를 세지 않습니다. 100퍼센트를 채웠다고 안심하면 안 되는 까닭입니다.

커버리지는 양쪽 다 100퍼센트로 같습니다. 결함은 두 번째에서만 나왔습니다. 커버리지가 답하는 물음과 결함을 찾는 일이 서로 다른 물음이라는 뜻입니다.

절차 4 — 커버리지가 낮을 때를 본다

① validate(15) 하나만 돌렸을 때 S1 지남 1회 S2 안 지남 S3 지남 1회 S4 안 지남 S5 지남 1회 구문 커버리지 3 / 5 = 60% ② validate(15) 와 validate(0) S1 지남 2회 S2 지남 1회 S3 지남 1회 S4 안 지남 S5 지남 1회 구문 커버리지 4 / 5 = 80% ③ 세 구간을 다 돌렸을 때 구문 커버리지 5 / 5 = 100%

커버리지가 낮으면 확실히 문제입니다. 60퍼센트라면 안 지나간 두 줄에 무엇이 있는지 아무도 모릅니다. 낮은 것은 나쁜 신호이고, 높은 것은 좋은 신호는 아닙니다. 이 비대칭을 기억해 두십시오.

한 문장이 두 가지로 읽힙니다

요구사항 「회원은 시설을 예약하고 관리자가 승인한다」 읽는 법 ① 회원이 신청하면 관리자가 승인해야 확정된다 읽는 법 ② 회원이 예약하면 바로 확정되고, 관리자는 나중에 본다

둘은 전혀 다른 프로그램입니다. ①은 승인 대기 상태가 필요하고 ②는 필요 없습니다. 글로만 주고받으면 개발이 끝날 때까지 이 차이를 모를 수 있습니다.

그림으로 그리면 갈라집니다

① 회원 ──신청──→ (예약을 신청한다) ──대기──→ (승인한다) ←── 관리자 │ 확정 저장 ② 회원 ──신청──→ (예약을 신청한다) ──확정 저장 관리자 ──────→ (예약 현황을 본다)

화살표가 다릅니다. ①은 관리자를 거쳐야 저장되고 ②는 안 거칩니다. 이 그림을 현업에게 보여 주면 「아, 이건 아닌데요」가 나옵니다.

실습 1 한 문장을 둘이 다르게 읽는 것을 직접 본다

목적 — 이 교과가 왜 있는지를 먼저 겪어 봅니다. 그림을 왜 그리는지 모르고 그리면 그리는 시늉만 하게 됩니다. 글로 적은 요구사항 한 문장이 실제로 두 가지 프로그램이 되는 것을 봅니다.

절차 1 — 문장을 받아 적는다

요구사항\애매한문장.md 「회원은 시설을 예약하고 관리자가 승인한다」 「예약은 취소할 수 있다」 「관리자는 시설을 관리한다」

세 문장 다 현업에게서 그대로 들을 법한 말입니다. 읽으면 무슨 뜻인지 알 것 같습니다. 그것이 함정입니다.

절차 2 — 옆 사람과 따로 적어 본다

같은 문장을 보고 각자 종이에 「그래서 화면이 몇 개고 무엇을 저장하는가」를 적습니다. 서로 안 보고 적은 다음 맞춰 봅니다. 혼자 하는 경우에는 두 가지로 읽어 보는 것으로 대신합니다.

요구사항\읽은결과.md 「회원은 시설을 예약하고 관리자가 승인한다」 A 가 읽은 것 회원이 신청하면 «승인 대기» 상태로 저장된다 관리자가 승인해야 «확정» 이 된다 상태가 셋 필요하다 — 대기 · 확정 · 거부 관리자 화면이 따로 필요하다 B 가 읽은 것 회원이 신청하면 바로 «확정» 이다 관리자는 확정된 예약을 나중에 본다 상태가 둘이면 된다 — 확정 · 취소 관리자 화면은 조회만 있으면 된다

절차 3 — 무엇이 달라지는지 센다

A 로 읽으면 B 로 읽으면 ----------- ---------------- ---------------- 상태 값 3개 2개 관리자 화면 승인 + 조회 조회 알림 승인·거부 알림 필요 없음 표 설계 승인자·승인일시 열 없음

표 하나와 화면 하나와 알림 기능이 통째로 붙었다 떨어졌다 합니다. 개발 일정으로 치면 며칠 차이이고, 이것을 만들다가 알아채면 이미 만든 것을 뜯어야 합니다.

절차 4 — 그림으로 갈라 본다

A 회원 ──신청──→ ( 예약을 신청한다 ) ──대기──→ ( 승인한다 ) ←── 관리자 │ 확정 저장 B 회원 ──신청──→ ( 예약을 신청한다 ) ──확정 저장 관리자 ────────→ ( 예약 현황을 본다 )

그림은 두 가지로 읽히지 않습니다. 화살표가 관리자를 거치거나 안 거치거나 둘 중 하나입니다. 현업에게 두 그림을 나란히 보여 주면 「이쪽입니다」가 바로 나옵니다.

절차 5 — 나머지 두 문장도 갈라 본다

「예약은 취소할 수 있다」 ① 언제든 취소할 수 있다 ② 이용일 하루 전까지만 취소할 수 있다 ③ 취소하면 기록이 지워진다 / ④ 취소 상태로 남는다 「관리자는 시설을 관리한다」 ① 시설을 새로 등록할 수 있다 ② 정원을 바꿀 수 있다 ③ 시설을 지울 수 있다 ④ 위 셋 가운데 어디까지인지 이 문장으로는 알 수 없다

둘째 문장은 갈래가 넷입니다. 「관리한다」는 가장 위험한 낱말입니다 — 무엇이든 포함할 수 있고 아무것도 포함하지 않을 수도 있습니다.

이 실습에서 나온 애매한 대목은 버리지 말고 모아 두십시오. 뒤에서 유스케이스를 뽑을 때 「이건 어떻게 하기로 했더라」가 나오는데, 그때 이 파일을 보고 현업에게 물으면 됩니다. 분석 단계에서 물을 것을 적어 두는 일이 분석의 절반입니다.

그래도 구조적 분석을 배우는 까닭

실무에서 새로 시작하는 프로젝트는 대개 객체지향입니다. 그런데 자료 흐름도는 아직 많이 쓰입니다.

실습 4 기법을 고르고 고른 까닭을 적는다

목적 — 평가에서 「왜 그 기법을 골랐습니까」를 묻습니다. 그때 「배워서」라고 답하면 안 고른 것입니다. 시스템의 성격을 재고, 두 기법을 견줘 보고, 근거를 남깁니다.

절차 1 — 시스템의 성격을 잰다

그림\기법선정.md | 재는 것 | 값 | 어느 쪽에 유리한가 | |---------|-----|--------------------| | 개발 방법론 | 객체지향 | 객체지향 분석 | | 프로그래밍 언어 | 자바 | 객체지향 분석 | | 사용자 상호작용 | 많음 — 회원이 직접 예약 | 객체지향 분석 | | 배치 처리 | 적음 — 월말 통계만 | 구조적 분석 | | 시스템 사이 연계 | 없음 | - | | 기존 시스템 파악 | 없음 — 새로 만듦 | - |

여섯 줄 가운데 셋이 객체지향 쪽, 하나가 구조적 쪽입니다. 이렇게 세어 두면 고른 까닭이 저절로 적힙니다.

절차 2 — 두 기법으로 같은 기능을 그려 본다

「예약을 접수한다」를 두 기법으로 구조적 분석 회원 ──예약신청서──→ ( 1.0 예약을 접수한다 ) ──예약기록──→ ╞═ 예약DB ═╡ 보이는 것 : 자료가 어디서 와서 어디로 가는가 객체지향 분석 회원 ─── ( 예약을 신청한다 ) 보이는 것 : 누가 무엇을 하는가. 자료는 안 보입니다

같은 기능인데 보이는 것이 다릅니다. 구조적 분석은 예약DB 가 보이고 객체지향 분석은 안 보입니다. 반대로 객체지향 분석은 회원이 「신청한다」는 것이 한눈에 들어옵니다.

절차 3 — 무엇이 안 보이는지 적는다

구조적 분석으로 그리면 안 보이는 것 누가 이 기능을 쓰는가 — 액터가 자료를 주는 상자로만 나옵니다 권한이 어떻게 나뉘는가 객체지향 분석으로 그리면 안 보이는 것 자료가 어디에 쌓이는가 — DB 가 그림에 없습니다 배치 처리의 흐름 — 사람이 안 누르는 일은 액터가 없습니다

아래쪽이 이 시스템의 약점입니다. 월말 통계는 사람이 누르는 것이 아니라 정해진 때에 도는 일입니다. 유스케이스로 그리면 액터가 없어서 어색해집니다.

절차 4 — 고르고 대안을 적는다

실습 10 포함과 확장을 붙이고 방향을 맞춘다

목적 — 유스케이스 사이의 관계를 그립니다. 포함과 확장을 헷갈리면 그림이 거짓말을 합니다. 반드시 일어나는가 아닌가 하나로 가릅니다.

절차 1 — 공통으로 하는 일을 찾는다

UC-02 예약을 신청한다 → 정원을 확인해야 한다 UC-06 정원을 변경한다 → 이미 찬 예약이 있는지 확인해야 한다 둘 다 «정원을 확인한다» 를 합니다. 같은 일을 두 곳에 적는 대신 하나로 빼냅니다.

이렇게 빼낸 것을 포함 관계로 잇습니다. 빼내면 고칠 때 한 곳만 고치면 됩니다. 정원 계산 방식이 바뀌면 두 유스케이스를 다 고칠 필요가 없습니다.

절차 2 — 조건이 붙는 일을 찾는다

정원이 찼을 때만 → 대기를 신청할 수 있다 취소 수수료가 있을 때만 → 환불액을 계산한다 늘 일어나는 것이 아닙니다. 조건이 맞을 때만 일어납니다. 이런 것은 확장으로 붙입니다.

절차 3 — 방향에 맞춰 그린다

포함 부르는 쪽 ──→ 불리는 쪽 ( 예약을 신청한다 ) ┈┈<<include>>┈┈→ ( 정원을 확인한다 ) ( 정원을 변경한다 ) ┈┈<<include>>┈┈→ ( 정원을 확인한다 ) 확장 붙는 쪽 ──→ 원래 쪽 ( 대기를 신청한다 ) ┈┈<<extend>>┈┈→ ( 예약을 신청한다 ) ( 환불액을 계산한다 ) ┈┈<<extend>>┈┈→ ( 예약을 취소한다 )

왜 남이 봐야 하나

쓴 사람은 자기가 무슨 뜻으로 썼는지 압니다. 그래서 애매한 문장을 애매하다고 못 느낍니다. 남이 읽으면 「이게 무슨 뜻이죠」가 나오고, 그 자리가 고칠 자리입니다.

페이건의 조사에 따르면 동료 검토를 하면 기간이 약 6개월 단축되고 재작업 비율을 25~35% 줄일 수 있습니다

훈련 과정에서는 워크 스루를 합니다. 초안을 놓고 둘이서 보는 것이면 충분하고, 중재자 교육을 받은 사람도 없습니다.

워크 스루에서는 작성자가 진행자와 제출자를 겸합니다. 둘이서 하면 작성자와 검토자 둘이고, 기록은 작성자가 합니다.

검토자는 결함을 찾는 사람이지 고치는 사람이 아닙니다. 「여기를 이렇게 바꾸면 어때요」로 가면 회의가 설계 토론이 됩니다. 「이 부분이 두 가지로 읽힙니다」까지만 말하고 넘어가야 정해진 시간 안에 문서 전체를 볼 수 있습니다. 고치는 것은 작성자가 회의 뒤에 합니다.

실습 13 워크 스루를 계획하고 남에게 읽혀 본다

목적 — 여기부터 능력단위요소 ②입니다. 쓴 사람은 자기 문서의 애매한 곳을 애매하다고 못 느낍니다. 남이 읽어야 「이게 무슨 뜻이죠」가 나오고, 그 자리가 고칠 자리입니다.

절차 1 — 방식을 고른다

인스펙션 워크 스루 ------------ ---------------- ------------------ 형식 공식 비공식 대상 완성된 산출물 초안 진행자 중재자(교육 이수자) 작성자 결함 측정 반드시 보통 안 함 인원 3~7명 (고객 포함) 2명 이상 훈련 과정에서 고를 수 있는 것은 워크 스루입니다 중재자 교육을 받은 사람이 없고, 산출물도 초안이기 때문입니다

절차 4 — 회의를 한다

규칙 셋 ① 검토자는 결함을 «찾는» 사람이지 «고치는» 사람이 아니다 「이 부분이 두 가지로 읽힙니다」까지만 말한다 ② 작성자는 변명하지 않는다 「그건 이런 뜻이었어요」는 문서가 그렇게 안 읽힌다는 증거다 ③ 시간을 지킨다 60분이면 60분에 끝낸다. 남은 것은 다음으로 미룬다

절차 1 — 검사할 규칙을 정한다

절차 2 — 지적이 나온 화면 셋을 확인한다

> dir 화면 /b

01_균형_불균형.png 02_균형_균형.png 03_표기법_지적3건.png 04_표기법_0건.png 05_추적_미통과.png 06_추적_통과.png

여섯 장입니다. 홀수 셋이 지적이 나온 화면입니다. 홀수가 하나라도 없으면 그 검사는 돌렸다는 증거가 없는 것입니다. 지금이라도 돌아가서 일부러 틀린 것을 넣고 한 번 돌리십시오.

절차 3 — 제출 전에 볼 다섯

① 기법을 고른 까닭과 대안이 적혀 있는가 ② 유스케이스 이름이 전부 동사구인가 ③ 지적이 나온 화면이 셋 있는가 ④ 추적 검사를 양방향으로 했는가 ⑤ 명세서가 유스케이스 수만큼 있는가

③이 가장 자주 빕니다. 고치고 나서 0건 화면만 찍는 것입니다. 검사를 돌렸다는 증거는 0건 화면이 아니라 지적이 나온 화면입니다.

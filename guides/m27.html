아래쪽이 설계에서 실제로 다투는 자리입니다. 합성으로 그리면 「회원을 지우면 예약도 지운다」는 뜻이 되고, 구현하는 사람은 그대로 만듭니다. 그런데 공공 시설 예약은 이용 기록을 남겨야 하는 경우가 많습니다. 그러면 합성이 아니라 연관이고, 회원 쪽에 「탈퇴」 상태를 두어야 합니다. 다이아몬드 색 하나가 이만큼을 정합니다 — 요구사항을 보고 그리십시오.

그리는 것은 클래스 다이어그램 하나입니다. 나머지는 있다는 것만 알고 있으면 됩니다. 「왜 시퀀스는 안 그립니까」를 물으면 「시간이 들어가서 동적모델입니다」라고 답합니다.

MVC 의 셋과 분석 클래스의 셋이 거의 그대로 겹칩니다. 이름만 다르고 나누는 기준은 같습니다. 그래서 MVC 를 아는 사람은 이 교과가 쉽고, 여기서 배운 것은 MVC 에 그대로 씁니다.

설계 가이드라인을 먼저 봅니다

설계를 시작하기 전에 확인할 것 □ 설계 패턴 MVC 인가 Layer 계층인가 □ 개발 플랫폼 스프링인가 순수 자바인가 □ DBMS MySQL 인가 오라클인가 □ 패키지 구조 계층별인가 기능별인가 □ 명명 규칙 클래스 · 속성 · 오퍼레이션 이름을 어떻게 짓는가 □ 클래스 다이어그램 작성 단위 □ 용어사전과 업무 규칙

이것을 안 보고 그리면 다 그린 뒤에 다시 그리게 됩니다. 명명 규칙 하나만 어긋나도 클래스 이름을 전부 고쳐야 합니다.

플랫폼마다 이름 규칙이 있습니다

스프링 · MVC 를 쓰는 곳의 흔한 규칙 Controller 업무명 + Controller EmployeeController Service 업무명 + Service EmployeeService VO 테이블명 + VO EmployeeVO DAO 업무명 + DAO EmployeeDAO 요소 사이의 규칙 Client 는 항상 Controller 를 거쳐 Service 를 부른다 데이터베이스와의 관계는 VO 를 거친다 엔티티 클래스는 DAO 와 짝이 된다

이름만 보고 갈래를 알 수 있게 하는 것이 목적입니다. EmployeeService 를 보면 제어 갈래라는 것을 압니다. 이 교안은 순수 자바로 만들므로 패키지 이름으로 갈래를 나눕니다.

이 교안이 쓰는 규칙

설계\설계지침.md | 항목 | 정한 것 | |------|---------| | 설계 패턴 | MVC 를 본떠 경계·제어·엔티티로 나눈다 | | 플랫폼 | 순수 자바 21 (프레임워크 없음) | | 패키지 | boundary · control · entity 셋 | | 클래스명 | 대문자로 시작. 갈래를 뒤에 붙이지 않고 패키지로 나눈다 | | 속성명 | 소문자로 시작. camelCase | | 오퍼레이션명 | 소문자로 시작. 동사 + 명사 | | 가시성 | 속성은 private 이 기본. 오퍼레이션은 필요한 것만 public |

맨 아래 줄을 지키는 것이 이 교과에서 가장 실질적인 이득입니다. 속성을 private 으로 두면 바깥에서 값을 바꿀 수 없고, 값을 바꾸려면 반드시 오퍼레이션을 거치게 됩니다. 그러면 「상태는 신청·확정·취소 셋뿐」 같은 규칙을 지킬 자리가 생깁니다. public 으로 열어 두면 규칙을 지킬 자리가 어디에도 없습니다.
실습 4 설계 지침을 정하고 명명 규칙을 못 박는다

목적 — 설계를 시작하기 전에 정할 것이 있습니다. 어떤 패턴을 쓸지, 이름을 어떻게 지을지, 패키지를 어떻게 나눌지. 이것을 안 정하고 그리면 다 그린 뒤에 전부 고치게 됩니다.

절차 1 — 확인할 것을 훑는다

절차 4 — 이름을 지어 보고 규칙에 걸리는지 본다

| 지어 본 이름 | 규칙에 맞는가 | 왜 | |--------------|---------------|-----| | ReservationService | ○ | 대문자 시작 | | reservationService | ✗ | 클래스인데 소문자 시작 | | ResInfo | ✗ | 「Info」 가 아무 뜻이 없다 | | Reservation_Store | ✗ | 밑줄은 상수에만 | | bookedCount | ○ | 소문자 시작 | | BookedCount | ✗ | 오퍼레이션인데 대문자 시작 | | size | △ | 명사뿐. count 나 getSize 가 낫다 |

맨 아래 줄이 판단이 필요한 자리입니다. 자바의 관례로는 size() 가 널리 쓰이지만 우리가 정한 「동사 + 명사」 규칙에는 어긋납니다. 규칙을 고칠지 이름을 고칠지 정하고 그 판단을 적어 두십시오.

규칙에 예외를 두는 것은 괜찮습니다. 다만 예외를 적어 두지 않으면 다음 사람이 「여기는 왜 다르지」 하고 헤맵니다. 「자바 표준 라이브러리 관례를 따르는 이름은 예외로 둔다 — size · get · toString」 한 줄이면 됩니다.

이름 뒤에 갈래를 붙이는 방식입니다. 패키지로 나누는 방식과 목적이 같습니다 — 이름만 보고 갈래를 알게 하는 것. 실무에서 스프링 프로젝트를 만나면 이 규칙을 따르게 됩니다.

절차 4 — 형식 검증과 업무 규칙을 가른다

절차 3 — 4번을 실제로 대조한다

①을 건너뛰지 말라고 학습모듈이 따로 적고 있습니다. 도구에서 바로 그리면 옮기고 지우는 데 시간을 다 씁니다. 종이에 한 번 그려 보면 시행착오가 크게 줄어듭니다.

그립니다

┌────────────────────────────┐ ┌──────────────────────────┐ │ <<boundary>> │ │ <<control>> │ │ ReservationConsole │ │ ReservationService │ ├────────────────────────────┤ 1 ├──────────────────────────┤ │ - service : Reservation… │───────→│ - facilities : Map │ │ - mail : MailGateway │ 1 │ - store : Reservation… │ ├────────────────────────────┤ ├──────────────────────────┤ │ + request(...) : void │ │ + request(...) : Result │ │ - message(Result) : String │ └────────────┬─────────────┘ └────────────────────────────┘ │ 1 ↓ 1 ┌──────────────────────────┐ │ <<entity>> │ │ ReservationStore │ ├──────────────────────────┤ │ - rows : List<Reser…> │ ├──────────────────────────┤ │ + save(Reservation) │ │ + bookedCount(...) : int │ └────────────┬─────────────┘ │ 1 ◆ * ┌──────────────────────────┐ │ <<entity>> Reservation │ └──────────────────────────┘

다섯째가 가장 자주 빕니다. 선만 긋고 숫자를 안 적는 것입니다. 숫자가 없으면 표를 만들 때 외래 키를 어느 쪽에 둘지 알 수 없습니다.

실습 15 클래스 다이어그램을 그리고 코드와 맞는지 본다

목적 — 지금까지 정한 것을 그림 한 장으로 모읍니다. 속성 · 오퍼레이션 · 가시성 · 관계 · 다중도 다섯이 다 들어가야 합니다. 그리고 그 그림이 실제 코드와 맞는지 한 항목씩 맞춰 봅니다.

절차 1 — 종이에 먼저 스케치한다

종이에 그릴 때 순서 ① 클래스 이름만 여섯 개 적는다 ② 갈래별로 위아래로 늘어놓는다 — 경계 위, 엔티티 아래 ③ 선을 긋는다 ④ 속성과 오퍼레이션은 나중에 채운다

학습모듈이 스케치를 먼저 하라고 따로 적고 있습니다. 도구에서 바로 그리면 상자를 옮기고 선을 다시 긋는 데 시간을 다 씁니다. 종이에 한 번 그려 보면 시행착오가 크게 줄어듭니다.

절차 2 — 상자 하나를 제대로 그린다

┌──────────────────────────────┐ │ <<entity>> │ ← 스테레오타입 │ Reservation │ ← 이름 (대문자 시작) ├──────────────────────────────┤ │ - memberNo : String │ ← 가시성 - 이름 : 타입 │ - facilityCode : String │ │ - useDate : String │ │ - headcount : int │ │ - status : Status │ ├──────────────────────────────┤ │ + getMemberNo() : String │ ← 가시성 + 이름(인자) : 반환형 │ + getStatus() : Status │ │ + confirm() : void │ │ + cancel() : void │ └──────────────────────────────┘

세 칸입니다 — 이름, 속성, 오퍼레이션. 속성 앞의 - 와 오퍼레이션 앞의 + 가 가시성입니다. 이 표기가 그대로 자바의 private 과 public 이 됩니다.

절차 3 — 전체를 그린다

┌────────────────────────────┐ ┌──────────────────────────┐ │ <<boundary>> │ │ <<control>> │ │ ReservationConsole │ │ ReservationService │ ├────────────────────────────┤ 1 ├──────────────────────────┤ │ - service : Reservation… │───────→│ - facilities : Map │ │ - mail : MailGateway │ 1 │ - store : Reservation… │ ├────────────────────────────┤ ├──────────────────────────┤ │ + request(...) : void │ │ + request(...) : Result │ │ - message(Result) : String │ └────────────┬─────────────┘ └─────────┬──────────────────┘ │ 1 │ 1 ↓ 1 ↓ 1 ┌──────────────────────────┐ ┌────────────────────────┐ │ <<entity>> │ │ <<boundary>> │ │ ReservationStore │ │ MailGateway │ ├──────────────────────────┤ ├────────────────────────┤ │ - rows : List<Reser…> │ │ + sendAccepted(String) │ ├──────────────────────────┤ └────────────────────────┘ │ + save(Reservation) │ │ + size() : int │ │ + bookedCount(..) : int │ └────────────┬─────────────┘ ◆ 1 │ * ┌──────────────────────────┐ │ <<entity>> Reservation │ └──────────────────────────┘

저장소와 예약 사이가 찬 다이아몬드입니다 — 합성. 다중도가 1 : * 이므로 저장소 하나에 예약이 여럿입니다. 나머지 선은 실선에 1 : 1 이므로 연관입니다.

절차 4 — 다섯 가지를 점검한다

□ 클래스 이름이 대문자로 시작하는가 여섯 개 모두 ○ □ 속성마다 타입이 붙어 있는가 ○ □ 가시성 기호(+ - #)가 다 붙어 있는가 ○ □ 오퍼레이션에 인자와 반환형이 있는가 ○ □ 관계선마다 다중도가 적혀 있는가 ○

다섯째가 가장 자주 빕니다. 선만 긋고 숫자를 안 적는 것입니다. 숫자가 없으면 표를 만들 때 외래 키를 어느 쪽에 둘지 알 수 없습니다.

절차 5 — 그림과 코드를 맞춰 본다

| 그림에 그린 것 | 코드에서 확인 | 맞는가 | |----------------|---------------|--------| | - status : Status | private Status status | ○ | | + confirm() : void | public void confirm() | ○ | | - message(Result) : String | private String message(...) | ○ | | Store ◆─ Reservation 1:* | private final List<Reservation> rows | ○ | | Console ── Service 1:1 | private final ReservationService service | ○ |

자료형만 봐도 다중도를 알 수 있습니다. List 면 *, 하나면 1 입니다. 그림과 코드가 어긋나면 둘 중 하나가 틀린 것입니다.

그림이 맞는지 확인하는 가장 확실한 방법은 자바로 옮겨 컴파일해 보는 것입니다. private 이라고 그려 놓고 바깥에서 쓰고 있으면 컴파일이 막고, 의존 방향을 거꾸로 그렸으면 import 가 순환합니다. 종이 위의 설계는 틀렸다는 말을 안 해 주지만 컴파일러는 해 줍니다. 설계 교과에서 코드를 쓰는 까닭이 이것입니다.

도구가 없으면 종이 사진이나 텍스트 그림도 됩니다. 다섯 가지가 다 들어 있으면 형식은 상관없습니다. 다만 나중에 고칠 일이 많으므로 도구가 편하기는 합니다.

여덟 가운데 넷이 「적어야 할 것을 안 적었다」입니다. 타입 · 가시성 · 다중도 · 나온 자리. 넷 다 그림을 그리는 데는 없어도 되고, 구현할 때는 없으면 안 되는 것들입니다. 설계서는 읽는 사람이 아니라 만드는 사람이 보는 문서입니다. 만드는 사람이 물어볼 것이 없을 만큼 적혀 있으면 다 된 것입니다.
